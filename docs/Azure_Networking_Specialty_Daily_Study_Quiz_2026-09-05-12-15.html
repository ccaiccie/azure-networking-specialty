1. ExpressRoute Direct MACsec

Inspect both Direct physical links before enabling or rotating MACsec. Replace placeholders with your resources.

az network express-route port show -g <resource-group> -n <expressroute-port>
az network express-route port link list -g <resource-group> --port-name <expressroute-port> -o table
az network express-route port link update --help
Verify: compare Azure link state with customer-router MACsec secure-channel counters. Change one redundant link at a time.

2. Custom VPN IPsec/IKE policy

az network vpn-connection ipsec-policy add \
  -g <resource-group> --connection-name <connection-name> \
  --dh-group DHGroup14 --ike-encryption AES256 --ike-integrity SHA384 \
  --ipsec-encryption AES256 --ipsec-integrity SHA256 \
  --pfs-group PFS2048 --sa-lifetime 27000 --sa-max-size 102400000
az network vpn-connection ipsec-policy list -g <resource-group> --connection-name <connection-name> -o table
Verify: compare negotiated IKE/IPsec SAs on both peers; troubleshoot selectors/NAT/routing separately if IKE is established.

3. ExpressRoute Metro

az network express-route list-service-providers -o table
az network express-route show -g <resource-group> -n <metro-circuit>
az network express-route peering list -g <resource-group> --circuit-name <metro-circuit> -o table
Verify: both metro-diverse paths advertise production prefixes and either surviving path has enough capacity.

4. IPsec over ExpressRoute with Virtual WAN

az network vpn-gateway connection show -g <resource-group> --gateway-name <vwan-vpn-gateway> -n <connection-name>
az network vpn-gateway connection ipsec-policy list -g <resource-group> --gateway-name <vwan-vpn-gateway> --connection-name <connection-name>
Verify in layers: private peer reachability over ExpressRoute → IKE/IPsec SAs → decrypted application routes in Virtual WAN.

5. VNet peering gateway transit

az network vnet peering update -g <resource-group> --vnet-name <hub-vnet> -n <hub-to-spoke> --set allowGatewayTransit=true
az network vnet peering update -g <resource-group> --vnet-name <spoke-vnet> -n <spoke-to-hub> --set useRemoteGateways=true
az network nic show-effective-route-table -g <resource-group> -n <spoke-vm-nic> -o table
Verify: expected on-premises prefixes appear in the spoke NIC effective routes.

6. Standard Load Balancer HA Ports

az network lb rule create -g <resource-group> --lb-name <internal-lb> -n ha-ports-rule \
  --protocol All --frontend-port 0 --backend-port 0 \
  --frontend-ip-name <frontend-ip-config> --backend-pool-name <nva-pool> --probe-name <probe>
az network lb rule show -g <resource-group> --lb-name <internal-lb> -n ha-ports-rule
Verify: both NVAs are healthy and return-path routing preserves stateful symmetry.

7. Azure Public DNS DNSSEC

az network dns zone show -g <resource-group> -n <zone-name>
az network dns zone --help
az network dns zone show -g <resource-group> -n <zone-name> -o json
Verify: the parent contains the correct DS record and a validating recursive resolver confirms the chain of trust.

8. Front Door Premium Private Link origin

az afd origin-group create -g <resource-group> --profile-name <afd-profile> --origin-group-name <origin-group> \
  --probe-request-type GET --probe-protocol Https --probe-path / --probe-interval-in-seconds 60
az afd origin create -g <resource-group> --profile-name <afd-profile> --origin-group-name <origin-group> \
  --origin-name <origin-name> --host-name <origin-fqdn> --origin-host-header <origin-fqdn> --https-port 443 \
  --enable-private-link true --private-link-location <region> --private-link-resource <resource-id> \
  --private-link-sub-resource-type <subresource>
Verify: approve the pending private endpoint connection, then check Front Door origin health.

9. Azure Firewall Premium TLS inspection

az network firewall policy show -g <resource-group> -n <firewall-policy> -o jsonc
az network firewall policy rule-collection-group list -g <resource-group> --policy-name <firewall-policy> -o table
Verify: clients trust the enterprise CA; test HTTPS and correlate firewall/IDPS logs before blaming routing.

10. VNet Flow Logs + Traffic Analytics

az monitor log-analytics workspace create -g <resource-group> -n <workspace> -l <region>
az network watcher flow-log create --location <region> --resource-group <resource-group> --name <flow-log> \
  --vnet <vnet-name> --storage-account <storage-account> --traffic-analytics true --workspace <workspace> --interval 10
az network watcher flow-log show --location <region> --resource-group <resource-group> --name <flow-log>
Verify: storage receives flow records and Traffic Analytics begins ingesting after its normal delay.

11. Network Watcher IP Flow Verify

az network watcher test-ip-flow -g <resource-group> --vm <vm-name> --direction Inbound --protocol TCP \
  --local <vm-private-ip>:443 --remote <client-ip>:50000
az network nic show-effective-nsg -g <resource-group> -n <vm-nic>
Verify: record the access decision and matching rule. If allowed, continue with routing, guest firewall/listener, LB, DNS, or app diagnostics.

12. Azure Private Link Service

az network private-link-service create -g <resource-group> -n <pls-name> --vnet-name <provider-vnet> \
  --subnet <pls-subnet> --lb-frontend-ip-configs <lb-frontend-resource-id> --location <region>
az network private-link-service show -g <resource-group> -n <pls-name>
az network private-link-service connection list -g <resource-group> --name <pls-name> -o table
Verify: approve the intended consumer connection and make sure consumer DNS resolves to the consumer private endpoint.
