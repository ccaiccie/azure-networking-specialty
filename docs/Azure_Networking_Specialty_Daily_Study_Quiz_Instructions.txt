LESSON ORGANIZATION
Required anchor sections:
1. “Why it matters” — concise statement of the design/operational problem and the value of the feature. Do not repeat this content later.
2. “Architecture” — topic-specific architecture, including control plane/data plane where that distinction is useful. The Architecture text must be followed immediately by the lesson’s full-width draw.io/SVG diagram. Mermaid may be included as a complementary view.
3. “Prerequisites and implementation” — only prerequisites not already explained, followed by real implementation. Do not repeat architecture or Why-it-matters facts here.
4. “Verification” — commands and representative expected output/state so the learner knows what success looks like.
5. “Troubleshooting” — commands, likely failure symptoms, and representative expected output/state for common failures.

Optional sections only when they add new information: packet/traffic flow; routing interaction; DNS interaction; NAT behavior; security/inspection interaction; availability/failover; tradeoffs/alternatives; enterprise scenario; documented limits/SKUs/scale/regions/zones/protocols. Never include a catch-all “Routing, DNS, security, and availability interactions” section merely to satisfy a template. Include those topics only if they add material not already covered.

IMPLEMENTATION — HARD GATE
- Every lesson must contain substantially more implementation detail than simple show/list commands.
- Prefer Azure CLI and/or Terraform configuration that creates or changes the relevant architecture. Use PowerShell/Bicep when they are the best official interface.
- Include explicit placeholders such as <resource-group>, <subscription-id>, <location>, <vnet-name>, etc., and explain what to replace.
- Where practical, show prerequisite resource creation plus the feature-specific configuration, not just one isolated command.
- Never invent CLI subcommands, flags, Terraform resources/arguments/defaults/limits/outputs. Verify syntax from current Microsoft Learn/Azure CLI docs and HashiCorp AzureRM docs.
- If the feature lacks a direct Azure CLI/Terraform create/update surface, explicitly state that limitation and show the closest supported automation interface plus CLI verification.

VERIFICATION COMMANDS + EXPECTED OUTPUT — HARD GATE
- The Verification section must show commands plus representative expected output or expected state. Output may be shortened, but it must teach what fields/status values matter.
- Clearly label sample output as representative, not a guaranteed byte-for-byte response.
- Examples: ProvisioningState=Succeeded, peeringState=Connected, connectionStatus=Connected, backend health=Healthy, effective route next hop, NSG rule name/Allow result, DNSSEC validation result, flow-log enabled state, Private Link connection status=Approved.

TROUBLESHOOTING COMMANDS + EXPECTED OUTPUT — HARD GATE
- Troubleshooting must be command-driven and feature-specific. Show the command(s), a representative failing output/state, what it means, and the next corrective action.
- Do not use generic prose such as “check routes and NSGs” without the exact Azure inspection command and the specific output field/state to examine.
