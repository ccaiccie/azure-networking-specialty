ExpressRoute zone-resilient gateways and site failure domains

flowchart LR
DC[On-premises]-->CE[CE routers]
CE-->ER1[ER circuit - site A]
CE-->ER2[ER circuit - site B]
ER1-->GW[Zone-redundant ER gateway]
ER2-->GW
GW-->V[Hub/workload VNets]

Architecture and why it matters

ExpressRoute availability is a chain of independent failure domains. A circuit normally has redundant Microsoft Enterprise Edge connectivity inside one peering location. The Azure virtual network gateway is a separate managed regional component. Zone-redundant gateway instances protect the gateway tier from a single availability-zone failure, while a second ExpressRoute circuit in a different peering location protects against loss of the entire first peering facility. Neither protection replaces the other.

BGP is the hybrid control plane. The customer/provider edge advertises on-premises prefixes toward Microsoft and learns Azure prefixes. The data plane follows the selected route through the circuit, Microsoft backbone, ExpressRoute gateway, and Azure routing fabric. A resilient secondary circuit must advertise the same critical routes and have enough bandwidth for the protected workload; a BGP session that is merely Established is not evidence of usable disaster recovery capacity.

Implementation and verification

Choose a supported zone-capable ExpressRoute gateway SKU, place the gateway in the hub’s GatewaySubnet, and connect the hub to the intended circuits. Treat each peering location as a distinct site-level failure domain. On the customer edge, use BGP policy such as local preference to express primary/secondary intent while preserving the backup routes. If both circuits are active, review whether stateful firewalls or NAT devices require symmetric return paths.

Before production, collect route evidence on both sides. On CE routers, inspect learned and advertised prefixes, AS paths, next hops, and best-path attributes. In Azure, inspect connection state and effective routes on representative NICs. Test failures at different layers: a single BGP adjacency, one circuit path, the Azure gateway tier, and the assumption of complete peering-site loss. For each test record route withdrawal, alternate-path installation, packet loss, application recovery, and backup bandwidth utilization.

Enterprise scenario

A company has primary ExpressRoute connectivity at one metropolitan peering location and a second circuit at another site. Both advertise the same data-center prefixes; policy prefers the primary. A zone-redundant ExpressRoute gateway protects against a single Azure availability-zone issue. If the whole primary peering location becomes unavailable, the second circuit provides the remaining hybrid path. The architecture explicitly separates Azure gateway resiliency from provider/peering-site resiliency.

Troubleshooting and takeaway

One failed BGP session while the partner session on the same circuit remains healthy points toward a link/session problem. Both sessions failing at one peering location suggests a broader circuit/site event. Healthy circuits with unreachable workloads directs attention to gateway connection state, UDRs, route propagation, NSGs, or return-path asymmetry. The exam/interview takeaway is that dual circuit links, zone-redundant gateways, and diverse peering locations solve different failure domains and should be combined according to business RTO/RPO needs.

Custom IPsec/IKE policy and policy-based traffic selectors

sequenceDiagram
participant O as On-prem VPN
participant A as Azure VPN Gateway
O->>A: IKE proposals
A-->>O: Matching IKE policy
O->>A: IKE_AUTH + selectors
A-->>O: CHILD_SA
O->>A: Encrypted user traffic

Architecture

Azure VPN Gateway defaults are intended to interoperate with many devices, but a custom IPsec/IKE policy is necessary when a third-party peer accepts only a specific cryptographic suite or corporate policy requires exact algorithms. The policy controls IKE encryption/integrity, Diffie-Hellman group, IPsec encryption/integrity, PFS group, SA lifetime, and data-size lifetime. Both peers need a compatible set.

IKE creates the authenticated control channel. IPsec then creates the CHILD_SA that carries protected application traffic. A phase-one mismatch prevents IKE from establishing. A phase-two or selector mismatch can leave IKE looking healthy while no useful data passes. This is why tunnel “Up” status must be correlated with SA and byte counters.

Policy-based selectors and implementation

Route-based peers normally rely on routing rather than a large list of exact crypto ACLs. Some policy-based devices require explicit local/remote subnet pairs. Azure supports UsePolicyBasedTrafficSelectors on a route-based connection with custom policy to interoperate with such peers. It alters selector negotiation; it does not convert Azure into a traditional policy-based forwarding device.

Inventory IKE version, encryption/integrity algorithms, DH/PFS groups, lifetimes, peer public IPs, NAT-T behavior, PSK ownership, and local/remote prefixes. Configure a secure common policy on both peers. Azure PowerShell can build the policy with New-AzIpsecPolicy; the portal exposes equivalent fields on the connection. Change control should record the negotiated contract so later crypto hardening is coordinated instead of done independently at each end.

Enterprise scenario

A manufacturing acquisition has an older firewall that requires AES256/SHA384 and explicit traffic selectors. Default Azure proposals do not establish a usable tunnel. The cloud team applies a matching custom policy and enables policy-based selectors for the plant and Azure application networks. IKE establishes, the correct CHILD_SA forms, and traffic begins without replacing the plant firewall.

Troubleshooting and takeaway

If no IKE SA forms, check UDP 500/4500 reachability, NAT-T, peer IP, PSK, IKE version, and phase-one proposal overlap. If IKE forms but traffic fails, check IPsec encryption/integrity/PFS, selector pairs, routes, overlapping prefixes, NSGs, NAT, and return path. One-way bytes commonly point to routing/selectors/NAT rather than IKE. The takeaway is that cryptographic policy and traffic selectors are both part of the VPN interoperability contract.

Virtual WAN route-maps and BGP policy

flowchart LR
B[Branch]-->|Inbound map|H[Virtual hub router]
V[VNet connection]-->|Inbound map|H
H-->BEST[Best-path selection]
BEST-->|Outbound map|E[Branch/ER advertisement]

Control-plane position

Virtual WAN route-maps add route policy to a managed virtual hub. They can match prefixes, BGP communities, and AS paths, then drop routes or modify attributes/prefixes. The most important design concept is direction. Inbound maps process advertisements before routes enter the hub routing table and can therefore affect what the hub learns. Outbound maps process routes after the hub has selected its best path, when it prepares advertisements for a connection.

This means an outbound map is excellent for filtering or summarizing what a branch receives, but it cannot retroactively alter the hub’s best-path decision. If you need to influence what the hub considers, the relevant logic belongs on inbound advertisements or upstream routing policy.

Rule semantics and implementation

Conditions in one rule must all match for its action to apply. Rules execute in sequence. If none matches, the default behavior is allow rather than implicit deny. Modify actions can summarize prefixes or manipulate supported BGP attributes; Drop filters the route. Route aggregation lowers route count but can also advertise reachability for unused component space, so an aggregate needs an intentional discard/black-hole strategy or component-validity design where appropriate.

Use the Route Map dashboard to capture advertisements before change: prefix, direction, AS path, and communities. Build a narrowly scoped map, attach it to the correct connection/direction, and verify the post-policy view. Keep before/after state in change control. Verify current Microsoft limitations for ASN formats, reserved ASNs, attribute behavior, and NAT interactions before relying on a specific manipulation.

Enterprise scenario

A branch router has a route-scale constraint. Several Azure spoke prefixes are contiguous and can be represented safely by an aggregate. The hub retains its granular routes internally, while an outbound map toward that branch advertises a summarized prefix. The branch receives fewer routes without changing how the hub chose its internal best paths.

Troubleshooting and takeaway

If a route vanishes, confirm map attachment and direction, rule order, match conditions, Terminate behavior, and action. If the hub itself chooses an unexpected best path, inspect the route before outbound transformation instead of blaming an outbound map. For summaries, test destinations in each component block. The key takeaway: inbound maps influence learning; outbound maps shape advertisements after best-path selection, and unmatched routes are allowed by default.

VNet peering gateway transit and service chaining

flowchart LR
ON[On-prem]-->GW[Hub VPN/ER gateway]
GW-->H[Hub VNet]
H<-->|Peering|S1[Spoke 1]
H<-->|Peering|S2[Spoke 2]
S1-->|UDR|N[NVA]
N-->S2

Three different mechanisms

VNet peering gives two VNets private Azure-backbone connectivity, but it is non-transitive. Two spokes that each peer to a hub do not automatically route through that hub to each other. Hub-and-spoke designs therefore combine three separate mechanisms: peering for direct VNet adjacency, gateway transit to share a hub VPN/ExpressRoute gateway, and UDR-based service chaining when traffic must pass through an NVA or firewall.

Gateway transit

On the hub-side peering enable Allow gateway transit. On the spoke-side peering enable Use remote gateways. The spoke can then consume on-premises/hybrid connectivity through the hub gateway. Centralized gateway ownership reduces duplicated gateway cost and simplifies hybrid routing for large spoke estates. Gateway configuration and supported transit limitations should be standardized through infrastructure as code.

Service chaining and return path

A spoke UDR can point selected prefixes or a default route to the private IP of an NVA in the hub. The NVA must forward traffic and have routes toward the destination. Stateful appliances also need a return path that sends reverse traffic through the same inspection/state domain. Peering itself does not create this routing logic. Summarized gateway prefixes can help reduce on-premises route scale in supported designs, but aggregates must match genuine reachability.

Enterprise scenario

An enterprise hub contains ExpressRoute and a firewall pair. One hundred spokes use remote gateway transit for on-premises reachability. Default routes in application spokes point to the hub firewall for Internet egress, and selected east-west traffic is also inspected. Standardized peering and UDR modules ensure that new spokes inherit the same architecture.

Troubleshooting and takeaway

For failed on-premises reachability, verify both peering states and the gateway-transit flags, then inspect effective routes on the workload NIC. If a UDR points to an NVA, verify appliance health, IP forwarding, routing table, NSGs, NAT, and return path. If engineers expect two spokes to communicate only because both peer with the hub, remind them that peering is non-transitive. The interview takeaway is: peering connects two VNets; gateway transit shares a hybrid gateway; service chaining deliberately inserts an NVA.

Standard Load Balancer HA Ports for NVAs

flowchart LR
S[Spoke]-->LB[Internal Standard LB HA Ports]
LB-->N1[NVA 1]
LB-->N2[NVA 2]
N1-->D[Destination]
N2-->D
D-->R[Designed return path]

Architecture

HA Ports let an internal Standard Load Balancer distribute broad TCP and UDP traffic to a healthy NVA pool without a separate rule for every application port. The rule uses protocol All with frontend and backend ports set to zero. This is particularly useful for firewalls and routers because they are transit devices rather than single-listener applications.

A typical data path begins with a UDR in a workload subnet pointing toward the load balancer frontend. Standard Load Balancer hashes a new flow to a healthy NVA. The appliance inspects/routes the packet and forwards it toward the destination. Return traffic must follow the vendor-supported topology so stateful session tracking works. HA Ports do not remove the need for correct routing or symmetric state handling.

Health, forwarding, and implementation

The backend health probe should represent forwarding readiness, not merely whether the VM is powered on. An unhealthy backend stops receiving new flows. NVA NICs generally require IP forwarding, and the guest appliance must know how to reach all transit networks. Floating IP is a separate feature used by some vendor designs and explicitly avoided by others; use the vendor reference architecture rather than assuming it is part of every HA Ports deployment.

Validate three layers together: source effective route, Standard Load Balancer backend health, and NVA routing/session state. Test TCP and UDP, new and long-lived sessions, and multiple traffic directions such as spoke-to-Internet and on-premises-to-spoke.

Enterprise scenario

A regional security hub uses two active firewalls behind an internal Standard Load Balancer. Spoke default routes point to the load-balancer frontend. HA Ports distributes new flows to both firewalls and removes a failed backend based on the probe. The design avoids maintaining thousands of per-port load-balancing rules.

Troubleshooting and takeaway

If the NVA sees no packet, verify the UDR next hop, frontend/backend configuration, and health status. If the NVA receives the first packet but the session fails, inspect forwarding, NSGs, NAT, return routes, and symmetry. Existing sessions may reset during backend failure depending on appliance behavior, so test long-lived sessions explicitly. The takeaway: HA Ports scale NVA front ends; probes and routing determine whether that load balancing is operationally useful.

Application Gateway end-to-end TLS and backend trust

sequenceDiagram
participant C as Client
participant G as Application Gateway
participant B as Backend
C->>G: Client TLS
G->>G: Terminate + WAF/L7 routing
G->>B: New TLS + SNI
B-->>G: Certificate
G->>G: Validate chain and hostname
G->>B: HTTPS request

Two TLS sessions

End-to-end TLS on Application Gateway means the client TLS connection terminates at the gateway and a separate TLS connection is established from the gateway to the backend. This is not opaque pass-through. Termination is what allows Application Gateway to apply host/path routing and WAF inspection while re-encryption keeps the backend hop protected.

Backend trust and SNI

The backend setting uses HTTPS. Application Gateway must trust the backend certificate chain and validate the host identity. Publicly trusted certificates work when the configured host matches the certificate. For private PKI, upload the trusted root certificate into backend settings. The host name used for backend requests/probes and SNI must align with the backend certificate and virtual-host behavior. Misalignment is a common reason for unhealthy backends and HTTP 502 errors.

Frontend and backend TLS are independently negotiated. Microsoft retired TLS 1.0/1.1 support for Application Gateway interactions on August 31, 2025, so current designs should use TLS 1.2 or later. Certificate rotation should be managed as an availability process: frontend cert, backend server cert, private root/intermediate chain, and host-name changes all need coordinated lifecycle management.

Implementation

Configure the listener and frontend certificate, backend pool, HTTPS backend setting, host-name behavior, and private root trust where required. Create a health probe that uses the same application hostname/path expected by the backend. Verify DNS resolution from the gateway network context, route/NSG reachability to the backend port, and Backend health before cutover.

Enterprise scenario and troubleshooting

A finance application uses an enterprise CA. Internet clients establish TLS to Application Gateway, WAF inspects the request, then the gateway establishes new TLS to finance.internal.contoso.com. The enterprise root is trusted and the health probe uses the same hostname. If clients get 502, inspect Backend health first, then DNS, TCP reachability, certificate expiration, chain trust, and hostname/SNI. The takeaway is that Application Gateway is a TLS client to the backend, so PKI and DNS are part of the network path.

Traffic Manager probing and nested profiles

flowchart TD
Q[DNS query]-->P[Priority parent]
P-->C[Performance child]
P-->DR[DR endpoint]
C-->E[East US]
C-->W[West Europe]
H[Health probes]-->E
H-->W
H-->DR

Architecture

Traffic Manager is DNS-based steering, not a reverse proxy. It evaluates endpoint health and routing method, returns a DNS answer, and the client connects directly to the selected endpoint. Because Traffic Manager is not in the data path, DNS TTL, recursive resolver caching, operating-system/browser caching, and persistent application connections affect the time users observe a failover.

Health monitoring

HTTP/HTTPS probes request the configured port/path and evaluate the result; TCP probes test connection establishment. A disabled endpoint is intentionally excluded and differs from an enabled but degraded endpoint. A good health endpoint checks enough application dependencies to prove that a region can serve traffic but does not remove an entire region because of an optional subsystem.

Nested profiles

Nested profiles compose routing methods. A Priority parent can prefer a Performance child containing active regions and use a warm DR endpoint as secondary. Within the child, users receive the best healthy region according to performance. If the child has no usable endpoints, the parent can choose DR. Nesting can also create groups with different monitoring settings because probe configuration is profile-wide.

Enterprise scenario and validation

A SaaS service runs active in East US and West Europe with warm standby in Central US. A Performance child contains the active regions; a Priority parent points first to that child and second to Central US. Failure of one active region keeps traffic in the other. Loss of the active group promotes the DR endpoint.

Test failover through multiple recursive DNS resolvers and record both monitor transition and answer changes. If failover appears slow, inspect probe path/port/status, endpoint/profile state, TTL, recursive resolver caches, OS/browser caches, and existing application sessions. The exam takeaway is that Traffic Manager changes future DNS answers; it cannot instantly revoke cached answers that clients already hold.

Lesson 8 · Routing and traffic management

Public IP routing preference

flowchart LR
U[Internet user]-->|Microsoft preference|ME[Microsoft edge]
ME-->MB[Microsoft backbone]
MB-->P[Azure public IP]
U-->|Internet preference|ISP[ISP transit]
ISP-->R[Regional handoff]
R-->P

What changes

Routing preference influences the external path of supported public-IP traffic. The default Microsoft network preference keeps traffic on Microsoft’s global network for more of the trip. Internet routing preference hands traffic to or from ISP networks closer to the Azure region so more of the end-to-end path uses public Internet transit.

This is not private routing policy. It does not replace system routes, UDRs, NSGs, BGP, or private DNS. Engineers should associate routing preference with a public endpoint design rather than trying to use it to solve an internal next-hop problem.

Design and implementation

Use Microsoft network preference for workloads where consistent global backbone handling is valuable, and evaluate Internet preference for cost-sensitive services where the path tradeoff is acceptable. Current documentation should be checked for supported SKU, region, address-family, and incompatible combinations; IPv4 is the documented baseline in the current overview. Create the appropriate Standard public IP and associate it with a supported workload front end.

Measure from representative user networks. Compare latency, jitter, packet loss, and path stability over time rather than one traceroute from one office. Internet transit is dynamic and can change independently of Azure configuration.

Enterprise scenario and troubleshooting

A business separates an interactive customer portal from a bulk-download service. The portal remains on Microsoft network preference. The download endpoint is tested with Internet routing preference because cost matters more than minimum interactive latency. Separate public IP resources let each workload express its own objective.

If the endpoint becomes unreachable, validate public-IP association, load-balancer/listener health, NSGs, UDRs, and application state before blaming preference. If only performance changes, compare external network measurements from several ISPs. The takeaway is that routing preference alters public external transit; Traffic Manager/Front Door still handle global application steering and UDRs still handle private routing.

Private Link Service provider architecture

flowchart LR
C[Consumer VNet]-->PE[Private Endpoint]
PE-->PLS[Private Link Service]
PLS-->|Provider-side NAT|LB[Standard Load Balancer]
LB-->A[Provider application]
OWN[Provider approval]-.->PLS

Architecture and NAT

Private Link Service is the provider-side method for publishing your own application through Azure Private Link. Consumers create private endpoints in their own VNets. The provider application sits behind a Standard Load Balancer whose frontend is associated with the Private Link Service. This provides private service consumption without public exposure or a VNet peering mesh.

The provider backend normally sees source addresses from the Private Link Service NAT pool, not the consumer’s original RFC1918 address. Provider-side NAT is valuable because independent consumer VNets can use overlapping address spaces. If the provider needs consumer connection metadata, Proxy Protocol v2 can be enabled; the backend must understand the header or it can misinterpret the first bytes as application payload.

Approval and scale

Private endpoint connections have an approval lifecycle. Trusted subscriptions can be auto-approved while other requests remain pending for provider review. This creates an authorization boundary around service consumption. NAT IP planning matters because translated connections consume source ports; multiple NAT IP configurations can increase capacity subject to current platform limits. Verify current protocol/address-family and scale limits for the intended service.

Enterprise scenario

A platform team publishes a shared API to dozens of subscriptions, including business units with overlapping 10.0.0.0/8 plans. Each consumer creates a private endpoint. The provider approves the connection and the application sees traffic through the Private Link Service NAT pool. Additional NAT IPs are provisioned after connection-scale testing.

Troubleshooting and takeaway

Walk the chain: consumer private endpoint provisioning and connection state, provider approval, Private Link Service status, Standard Load Balancer frontend/backend health, NAT pool capacity, NSGs, and backend listening. Do not build authorization around the provider-observed NAT source unless that mapping is deliberately managed. The takeaway is that Private Link Service is private service publishing with provider-controlled approval and NAT isolation, not generic routed connectivity between two VNets.

Virtual Network Manager security admin rules

flowchart TD
P[Packet]-->S[Security admin rule]
S-->|Deny|D[Drop]
S-->|Always Allow|AA[Permit]
S-->|Allow|N[Continue to NSG]
N-->W[Workload]

Policy hierarchy

Azure Virtual Network Manager security admin rules let a central security/network team enforce guardrails across network groups while application teams retain NSG ownership. The defining behavior is evaluation before NSGs. This creates a policy hierarchy rather than depending on every subscription to reproduce mandatory controls correctly.

Deny blocks a matching flow and a workload NSG cannot override it. Allow permits the packet to continue to NSG evaluation, where a workload deny can still stop it. Always Allow permits the matching flow despite a lower-level NSG deny. Understanding those three actions is critical because two “allow” choices have very different delegation semantics.

Deployment and governance

Rules live in collections/configurations and target network groups. Group membership can be explicit or policy-driven. Deployments are eventually consistent, so operators should verify deployment state before concluding that a rule is ineffective. Reserve priority bands for emergency security, mandatory platform rules, and broader organization policy. Canary deployment to a small network group reduces the blast radius of a mistaken central deny.

Enterprise scenario

A security team centrally blocks Internet-sourced SSH and RDP to production VNets. Application teams continue managing HTTPS/database flows in their own NSGs. A tightly scoped management system receives centrally approved access using the action that matches the governance model. The rule set is validated in a canary group before organization-wide rollout.

Troubleshooting and takeaway

If an NSG Allow does not work, inspect whether an admin Deny matched first. If an NSG Deny appears bypassed, check for Always Allow. Verify network-group membership, deployment region/state, priority, source/destination/protocol match, and current service-specific exceptions. The takeaway is the evaluation chain: security admin rules first; NSGs second only when the admin action permits continued evaluation.

Network Watcher NSG diagnostics and IP flow verify

flowchart LR
F[Known five-tuple]-->D[IP flow verify / NSG diagnostics]
D-->R[Effective security rules]
R-->|Allow|A[Matching allow]
R-->|Deny|X[Matching deny]
A-->N[Then inspect next hop/routing]

Why simulate policy first

When a failing flow is known—source, destination, protocol, port, and direction—Network Watcher can evaluate the effective Azure security policy and identify whether it should be allowed or denied and which rule wins. This is usually a better first diagnostic than packet capture for a suspected NSG problem.

NSGs can exist at subnet and NIC scopes and include custom priorities, default rules, service tags, and augmented rules. Manual inspection can miss the effective interaction. IP flow verify and NSG diagnostics turn the five-tuple into a deterministic policy question.

Troubleshooting ladder

Start with security simulation. If Denied, correct the identified rule or scope and test again. If Allowed, use Next hop/effective routes to validate the routing decision. If both policy and routing are correct, escalate to Connection troubleshoot, packet capture, virtual network flow logs, guest firewall logs, or application telemetry. This sequence keeps packet capture as evidence collection after simpler policy/routing hypotheses have been tested.

Enterprise scenario

HTTPS works from Spoke A but not Spoke B. Engineers see a broad destination allow and assume the NSG is fine. NSG diagnostics with Spoke B’s source and TCP/443 reveals a higher-priority deny matching that CIDR. The source range is corrected; the simulation reports Allowed; application testing then succeeds.

Operational details and takeaway

Choose the correct NIC and direction on multi-NIC VMs and remember that NSGs are stateful. Simulation says what policy should do; flow logs and packet captures show what actually happened. Current Microsoft guidance states NSG flow logs retire September 30, 2027 and recommends virtual network flow logs. The takeaway: prove security policy, then route selection, then collect packets/application evidence.

Azure Firewall Policy processing order

flowchart TD
P[Packet]-->D[DNAT]
D-->|No match|N[Network rules]
N-->|No match|A[Application rules]
A-->|No match|X[Implicit deny]
D-->|Match|OK[Translate + allow]
N-->|Match|ACT[Collection action]
A-->|Match|ACT

Policy hierarchy and rule types

Firewall Policy organizes configuration into rule collection groups, collections, and rules. Priority determines ordering within the policy hierarchy, but rule-type semantics still matter. Treating every rule as if it participates in one flat priority list leads to incorrect troubleshooting.

For inbound publishing, DNAT rules are processed before network rules. A matching DNAT rule translates and allows the publishing flow under DNAT behavior. Application rules are not applied to inbound connections, so inbound HTTP/S Layer-7 inspection belongs on an appropriate WAF/reverse-proxy service rather than an expectation that Firewall application rules will inspect incoming web requests.

For outbound traffic, network rules are evaluated before application rules. A broad network allow can therefore accept traffic before a restrictive FQDN application rule ever gets a chance to evaluate it. This is one of the most important shadowing behaviors to remember.

Governance and enterprise scenario

Reserve collection-group priority ranges for central security, shared infrastructure, and workloads. Keep DNAT publishing rules narrow and avoid broad network rules that unintentionally bypass application-layer restrictions. A shared firewall might place mandatory DNAT/network policy in high-priority groups and workload application rules later. Infrastructure as code makes priority ownership visible during review.

Troubleshooting and takeaway

Classify the flow before searching rules: inbound/outbound, NAT/non-NAT, transport/IP policy or HTTP/S/FQDN application policy. For inbound publishing inspect DNAT first. For outbound non-web protocols inspect network rules. For outbound FQDN control, check whether a prior network rule already matched. Use firewall logs to identify the actual collection/action, then correlate with effective routes, NSGs, NAT, and backend state. The takeaway is to learn the processing pipeline first and then reason about priority inside that pipeline.
