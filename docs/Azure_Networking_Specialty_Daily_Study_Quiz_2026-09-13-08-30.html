ExpressRoute Direct provisioning and VLAN encapsulation: QinQ versus Dot1Q

Why it matters

ExpressRoute Direct gives an organization dedicated physical ports into Microsoft’s network and direct control over how multiple ExpressRoute circuits are carried over those ports. The design decision that deserves the most attention before ordering the service is the Layer-2 encapsulation mode. Microsoft supports QinQ and Dot1Q. QinQ provides a Microsoft-assigned service tag for each circuit, with customer tags inside the circuit for the individual peerings. Dot1Q uses a single customer-managed VLAN tag and therefore makes the customer responsible for maintaining uniqueness across the entire Direct resource. The choice is not an aesthetic preference: it determines the VLAN registry, troubleshooting method, isolation model, and how easily operations teams can trace a circuit to a physical subinterface.

Encapsulation is selected when the ExpressRoute Direct resource is created and cannot be changed later in place. That makes it a design-time decision rather than a turn-up detail. A team that chooses Dot1Q without a disciplined VLAN registry can accidentally reuse a C-tag and create an outage that looks like a BGP problem. A team that chooses QinQ must ensure its switching and routing equipment can handle stacked 802.1Q tags and the Microsoft-assigned outer tag. In both cases, the two Direct physical links are independent redundant paths and are not an LACP or MLAG bundle.

Architecture

A Direct deployment uses two customer-facing Ethernet ports connected to separate Microsoft edge devices at a supported peering location. Each physical path carries one or more circuit peerings. With QinQ, Microsoft assigns an S-tag to each circuit; the customer uses distinct C-tags for private or Microsoft peering inside that circuit. With Dot1Q, the customer uses C-tags directly and must keep them unique across the whole Direct port pair. The customer edge creates VLAN subinterfaces, assigns the documented peering IP addresses, and forms separate BGP sessions toward the Microsoft Enterprise Edge routers.

The control plane consists of the ExpressRoute port resource, circuit objects, peering objects, VLAN values, peer IP settings, and provisioning state. The data plane is the sequence of Ethernet frames, ARP/neighbor discovery, BGP packets, and workload packets crossing the physical handoff. This distinction matters because Azure Resource Manager can report Succeeded while a BGP adjacency remains Idle if the wrong VLAN tag prevents the peer packets from reaching the MSEE. A healthy circuit object is therefore only one layer of acceptance testing.

Prerequisites and implementation

Confirm that the chosen peering location offers the required port bandwidth and that the subscription is enabled for Direct. Validate optics, cross-connect responsibility, device support for the selected encapsulation, and the number of BGP sessions the customer edge must support. Decide who owns the VLAN registry before the first circuit is created. For QinQ, record the Microsoft S-tag plus the C-tags used for each peering. For Dot1Q, enforce C-tag uniqueness across every circuit and peering on the Direct resource.

az network express-route port location show -l "<peering-location>"
az network express-route port create \
  --name <direct-port> \
  --resource-group <resource-group> \
  --bandwidth 100 gbps \
  --encapsulation QinQ \
  --peering-location "<peering-location>" \
  --location <azure-region>
az network express-route port show \
  -g <resource-group> -n <direct-port> -o jsonc

Replace the placeholders with the Direct resource group, supported Azure region, and peering location. Use Dot1Q instead of QinQ only when that design was selected before deployment. After the provider and Microsoft indicate that both physical ports are ready, create circuits against the Direct resource and configure the appropriate private or Microsoft peerings. Keep a change-controlled table that maps circuit, owner, bandwidth, S-tag when applicable, C-tag, CE subinterface, peer addresses, and both physical paths.

Redundancy and acceptance testing

Do not treat “both ports are up” as proof of end-to-end resilience. Validate each path independently. On path A, check optics and Ethernet counters, confirm the expected tag stack, verify ARP or neighbor discovery, establish BGP, confirm learned and advertised prefixes, and run representative application traffic. Then remove path A and prove path B can carry the same required routes and expected load. Repeat in the opposite direction. This process finds hidden common points such as a single customer switch, one carrier aggregation device, one power feed, or a duplicated VLAN template.

Capacity must also be evaluated during the failure condition. A redundant path that converges but becomes saturated is not sufficient for a critical workload. Document whether the surviving link is expected to carry 100 percent of normal traffic or only a prioritized subset. That decision belongs in both routing policy and incident runbooks.

Changing route filters or BGP attributes cannot repair a Layer-2 tagging error.

ExpressRoute scalable gateway (ErGwScale): fixed capacity and autoscaling

Why it matters

The scalable ExpressRoute virtual network gateway changes capacity planning from choosing one fixed legacy gateway tier to choosing scale units. ErGwScale supports a scale-unit range that can be configured as fixed capacity or as an autoscaling band. When minimum and maximum are equal, the gateway remains at that capacity. When the maximum is greater than the minimum, the service can add capacity as load increases. This model is useful for networks where several ExpressRoute circuits, large route tables, bursty application flows, or regional consolidation make a one-time SKU choice too rigid.

The feature should not be interpreted as permission to stop planning. Minimum scale is always-on capacity and should cover ordinary load plus the failure scenarios you are expected to survive. Maximum scale is both a technical and cost boundary. Microsoft also calls out workload considerations such as Private Link where fixed scaling can be preferred. A gateway can remain provisioned, connected, and fully routed while its forwarding capacity is too small for a traffic burst. In that case, routing changes are the wrong remedy.

Architecture

The ExpressRoute circuit BGP sessions terminate at Microsoft edge routers. The managed ExpressRoute virtual network gateway then forwards between circuit connections and Azure virtual networks. With ErGwScale, forwarding capacity is represented by scale units. The gateway control plane contains the SKU, minimum scale units, maximum scale units, circuit connections, route exchange, and provisioning state. The data plane consists of workload packets traversing the gateway into or out of the VNet.

Autoscaling changes serving capacity without changing the CE-to-MSEE BGP sessions. That separation is operationally useful. If every circuit is Connected, routes remain stable, and latency or drops correlate with sustained gateway load, investigate capacity rather than BGP policy. Conversely, adding scale units cannot fix a missing advertised prefix or a disconnected circuit.

Prerequisites and implementation

Use a supported ExpressRoute gateway design and Standard public IP resources where required by the current deployment guide. Existing ErGw1Az, ErGw2Az, and ErGw3Az deployments have a documented upgrade path, while older gateway SKUs may require the migration process. Verify regional support and current feature limitations before changing production. Inventory circuit count, learned route count, normal throughput, peak throughput, packet rate, and any required single-path failure load.

$RG = "<resource-group>"
$GWName = "<gateway-name>"
$Location = "<azure-region>"
# $ipconf is the documented ExpressRoute gateway IP configuration object.
New-AzVirtualNetworkGateway \
  -Name $GWName \
  -ResourceGroupName $RG \
  -Location $Location \
  -IpConfigurations $ipconf \
  -GatewayType Expressroute \
  -GatewaySku ErGwScale \
  -MinScaleUnit 2 \
  -MaxScaleUnit 10

This example establishes an autoscaling band from two through ten units. For fixed capacity, set -MinScaleUnit and -MaxScaleUnit to the same supported value. The minimum should be based on measured steady-state demand and the business failure model, not on the smallest number the API accepts. After creation or upgrade, connect the intended ExpressRoute circuits and compare the resulting route state with the pre-change baseline.

Capacity planning and failure behavior

Capacity planning should combine traffic and route scale rather than relying on one metric. A gateway may have enough raw throughput but still operate close to a scale boundary because of packets per second, many concurrent flows, or a large route table. Likewise, a quiet circuit can become important after another region or path fails. Model the aggregate traffic that reaches the gateway when one redundant circuit or site is unavailable and reserve enough minimum capacity for the services that must continue.

Autoscaling also has a reaction interval. It should be used for variable demand, not as a substitute for knowingly undersizing the baseline. If a workload regularly sits near the current minimum during business hours, increasing the minimum can make performance more deterministic. If Private Link-heavy traffic is part of the design, follow the current Microsoft guidance for fixed versus autoscaling choices and test that specific path rather than assuming all traffic behaves identically.

NVA forwarding in Azure: NIC IP forwarding, guest forwarding, and UDR insertion

Why it matters

An Azure VM becomes a useful network virtual appliance only when three independent forwarding layers agree. The source subnet must route the packet to the appliance. The Azure fabric must allow the appliance NIC to receive and transmit transit traffic. The guest operating system or vendor appliance must actually forward the packet. Teams often configure only two of these layers and then make broad NSG or routing changes because the symptom is simply “traffic stops at the firewall.” A disciplined design treats each layer as a separate gate with its own command and expected output.

The Azure NIC enableIPForwarding property allows the interface to receive packets whose IP destination is not one of the NIC’s own addresses and to transmit packets whose source address differs from the NIC’s configured address. It does not enable Linux kernel forwarding, a Windows routing role, or a vendor firewall’s transit mode. Likewise, a UDR with VirtualAppliance as the next-hop type steers traffic to the appliance IP but cannot force the guest to route it onward.

Architecture

Consider an application subnet at 10.10.1.0/24, an NVA subnet at 10.20.0.0/24, and a protected subnet at 10.60.0.0/16. The application subnet route table contains 10.60.0.0/16 with next hop VirtualAppliance and next-hop address 10.20.0.4. Azure forwards the original packet to the NVA even though the destination remains 10.60.x.x. The NVA NIC accepts that transit packet because IP forwarding is enabled. Inside the guest, the kernel or firewall policy routes and optionally inspects/NATs the packet before it exits toward the protected network.

The Azure control plane owns route tables, subnet associations, effective routes, NIC configuration, and NSGs. The guest owns kernel forwarding, firewall rules, routing tables, NAT, and session state. Return-path design is equally important for stateful appliances. A forward UDR that sends traffic through the NVA is insufficient if the destination returns directly to the source through a system route or a different appliance that does not own the session.

Prerequisites and implementation

Choose a stable private IP for the NVA next hop, size the appliance for the traffic and session load, and ensure the vendor supports the intended Azure topology. Enable IP forwarding on every NVA NIC that participates in transit. Enable forwarding or routing inside the guest. Create UDRs for the exact prefixes that need service insertion and associate them with the correct source and, when needed, return-path subnets.

az network nic update \
  -g <resource-group> \
  -n <nva-nic> \
  --ip-forwarding true

az network route-table create \
  -g <resource-group> -n <route-table> -l <region>

az network route-table route create \
  -g <resource-group> \
  --route-table-name <route-table> \
  -n to-protected \
  --address-prefix 10.60.0.0/16 \
  --next-hop-type VirtualAppliance \
  --next-hop-ip-address 10.20.0.4

az network vnet subnet update \
  -g <resource-group> --vnet-name <vnet> \
  -n <source-subnet> --route-table <route-table>

For a Linux appliance, verify the vendor-supported method for enabling forwarding; a generic Linux router commonly uses net.ipv4.ip_forward=1, while commercial NVAs often manage forwarding through their own configuration. Do not apply an operating-system command that conflicts with the appliance vendor’s support model. If the NVA performs SNAT, document which flows are translated because that changes return routing and logging.

Packet-path proof

Trace one representative five-tuple through the design. First prove the source NIC has an effective route to the destination prefix through 10.20.0.4. Next prove the NVA NIC has IP forwarding enabled. Then capture or log the packet on the NVA ingress and egress interfaces. Finally, verify the destination sees the expected source address and that the return packet follows the intended symmetric path. This method tells you exactly which layer stops the flow.

For stateful inspection, repeat the test after a route change or failover. A different reverse path can produce resets even though both directions are individually routable. Session synchronization between redundant NVAs must be validated according to the vendor design rather than assumed.

Verification

az network nic show-effective-route-table -g <resource-group> -n <source-vm-nic> -o table
az vm run-command invoke -g <resource-group> -n <nva-vm> --command-id RunShellScript --scripts "sysctl net.ipv4.ip_forward"

Azure Public IP Prefix: stable contiguous Microsoft-owned address blocks

Why it matters

A Public IP Prefix reserves a contiguous range of Microsoft-owned public addresses for one subscription and region. It is useful when partners, SaaS platforms, corporate firewalls, or allowlists need a stable CIDR rather than an ever-growing list of unrelated public IP addresses. The prefix is an allocation and governance resource; it does not forward traffic by itself. Individual Standard static Public IP resources are created from the reserved block and then associated with supported services such as load balancers, NAT Gateway, or other Azure network resources.

The operational advantage is lifecycle stability. If a child Public IP is deleted, the address returns to the reserved block while the prefix remains under the subscription’s control. External organizations can therefore permit the whole prefix once, while the Azure team manages individual child addresses inside it. This is different from Custom IP Prefix or BYOIP, where the organization onboards address space it already owns. A normal Public IP Prefix remains Microsoft-owned space that Azure reserves for the subscription.

Architecture

The prefix has a CIDR length, Azure region, SKU, IP version, and supported zone model. A child Public IP references the prefix resource and receives one address from the reserved range. The child address then attaches to the actual forwarding service. The prefix itself is never a next hop and never performs NAT. This separation is important during incidents: an intact prefix cannot repair an unhealthy load-balancer backend, and a NAT Gateway cannot use an address that was never instantiated as a compatible public IP resource.

Regional public-IP quota is consumed by the reserved block, not only by the child addresses currently in use. Address planning should therefore account for the full prefix size. Use the smallest prefix that provides required growth while meeting documented supported prefix lengths. Keep the prefix in IPAM with owner, region, intended services, external allowlists, and allocated child addresses.

Prerequisites and implementation

Choose the subscription, resource group, region, prefix length, IP version, and Standard SKU according to the current service limits. Confirm that the intended downstream resource supports Public IP Prefix-derived addresses and that its zone behavior is compatible. Coordinate external allowlists before the migration so traffic is not blocked when the service begins using a child address from the new CIDR.

az network public-ip prefix create \
  -g <resource-group> \
  -n <public-ip-prefix> \
  -l <region> \
  --length 28 \
  --sku Standard

az network public-ip create \
  -g <resource-group> \
  -n <child-public-ip> \
  -l <region> \
  --sku Standard \
  --allocation-method Static \
  --public-ip-prefix <public-ip-prefix>

The first command reserves the block; the second allocates a concrete address from it. Record that child IP against the service that consumes it. When automation creates multiple addresses, query the prefix after the deployment and compare the set against the IPAM record instead of assuming allocation order. Prefix ownership is stable, but the exact child address returned after deletion and recreation should not be assumed unless documented and verified.

Address lifecycle and external dependencies

Treat external allowlists as dependencies of the prefix rather than of one child address. If a payment processor allows the /28, a future NAT Gateway or load-balancer address allocated from the same prefix can be introduced without another external firewall request. Conversely, deleting the prefix breaks that guarantee. Do not delete and recreate a prefix expecting Azure to return the same CIDR.

When a service is decommissioned, detach or delete the child Public IP and update the internal allocation table. The address returns to the reserved pool. Before deleting the prefix itself, verify that no child Public IP resources remain. Azure blocks deletion while dependent addresses still reference the prefix, which protects against accidentally releasing a live external identity.

az network public-ip show -g <resource-group> -n <child-public-ip> \
  --query "{ip:ipAddress,prefix:publicIPPrefix.id,sku:sku.name,state:provisioningState}" -o json

Troubleshooting

Standard Load Balancer health probes: application-aware backend eligibility

Why it matters

Azure Load Balancer health probes decide whether a backend instance is eligible for new flows. Probe design is therefore a production availability decision rather than a monitoring afterthought. A TCP probe proves that a port accepts a connection. HTTP and HTTPS probes can query a purpose-built readiness path and use the response to decide whether the instance should remain in rotation. A weak probe can keep a broken application online, while an overly expensive probe can create its own failure load.

Probe state is also different from connection lifetime. When a backend becomes unhealthy, Standard Load Balancer stops assigning new flows to it, but established TCP connections can persist according to connection state, application behavior, and timeout semantics. During maintenance, operators can therefore observe existing sessions on a backend after new sessions have moved elsewhere. That behavior should be distinguished from a load-balancing bug.

Architecture

A frontend and load-balancing rule select members of a backend pool. The rule references a health probe. Azure sends the probe using the documented platform health-probe source, and the backend must allow and answer it on the expected interface, port, and path. For HTTP/HTTPS probes, the endpoint should return success only when the instance can safely process the traffic associated with the rule. A process-only check that always returns 200 can hide a failed dependency; a check that performs a slow database transaction can flap under load.

Multi-NIC NVAs require additional care because the probe has to arrive and return through the expected interface. Do not NAT a probe through an appliance to a remote dependency merely to infer downstream health unless the service design explicitly supports that behavior. A remote outage could otherwise mark a healthy forwarding appliance down and remove capacity that would still be useful for other traffic.

Prerequisites and implementation

Start with a Standard Load Balancer, a backend pool, and a listener on each backend. Decide what “ready” means for the application. For a simple stateless web tier, an HTTP path such as /health can be appropriate if it verifies the web process and only the dependencies required to serve requests. Ensure NSGs and local firewalls permit the Azure health-probe traffic. Align probe interval and threshold with the application’s expected recovery time so short transient delays do not unnecessarily remove capacity.

az network lb probe create \
  -g <resource-group> \
  --lb-name <load-balancer> \
  -n app-health \
  --protocol Http \
  --port 80 \
  --path /health \
  --interval 5 \
  --threshold 2

az network lb rule update \
  -g <resource-group> \
  --lb-name <load-balancer> \
  -n <rule-name> \
  --probe-name app-health

Replace the names and probe path with the actual application configuration. Test the endpoint locally on every backend before relying on Azure. Then deliberately make one backend unhealthy in a maintenance window and confirm that new connections are placed only on the remaining healthy instances.

Probe semantics and maintenance testing

A health probe should be easy to interpret. A 200 response means the instance is eligible; a deliberate 503 can mean “temporarily do not send new work.” Do not overload the endpoint with business logic that creates ambiguous intermittent responses. When the application uses long-lived TCP connections, record the expected behavior of existing sessions when the backend becomes unhealthy so operations does not terminate them unnecessarily.

Monitor probe status together with backend application metrics. If the probe remains healthy while user transactions fail, the readiness path is not measuring the dependency that matters. If the probe fails but local testing succeeds, investigate the network path between Azure’s probe source and the listening interface, including NSG, host firewall, bind address, and asymmetric routing.

Application Gateway connection draining: graceful backend removal during deployments

Why it matters

Rolling upgrades and scale-in events are dangerous when an application has long requests, uploads, downloads, or WebSocket sessions. Removing a backend immediately can interrupt active traffic even though a replacement server is already healthy. Application Gateway connection draining provides a controlled transition: new requests stop being assigned to the deregistering backend while existing connections are allowed to continue for a configured timeout. The setting belongs to the backend HTTP setting, which lets separate applications use different drain durations.

Draining does not migrate a TCP session to another server. If a request is still active when the timeout expires, it can be terminated. The timeout therefore should be based on measured maximum transaction duration, not a convenient default. Microsoft documents values from 1 through 3,600 seconds when draining is enabled, while zero disables it. Sticky-session behavior and long-lived connections must be tested explicitly.

Architecture

Client traffic reaches a listener and routing rule, selects a backend pool, and uses a backend setting that defines protocol, port, request timeout, cookie affinity, and connection-draining behavior. When deployment automation removes an instance from the backend pool, Application Gateway stops assigning new work to that instance. Existing eligible sessions can remain until they finish or the drain timer expires. A health probe is a separate state machine: a backend can be perfectly healthy yet intentionally draining because it is being taken out of service.

This distinction improves incident analysis. A backend that is Unhealthy should be fixed or replaced because it cannot serve traffic. A backend that is Healthy but draining is behaving exactly as the maintenance workflow requested. Deployment dashboards should expose both backend health and registration/draining state so an operator does not cancel a valid drain simply because traffic is still visible on the old instance.

Prerequisites and implementation

Identify the backend setting used by the application and measure the longest transfer or session that must survive a rollout. Verify that replacement backends become Healthy before deregistration begins. Select a drain timeout that exceeds the normal maximum transaction while still bounding how long an old release can remain active. If cookie affinity is enabled, include it in the rollout test because application affinity can affect which backend receives subsequent requests.

az network application-gateway http-settings update \
  -g <resource-group> \
  --gateway-name <application-gateway> \
  -n <backend-setting> \
  --connection-draining-timeout 300

az network application-gateway http-settings show \
  -g <resource-group> \
  --gateway-name <application-gateway> \
  -n <backend-setting> -o jsonc

The example enables a five-minute drain period. If the application can have eight-minute downloads, five minutes is inadequate even though the command succeeds. Test with the actual longest-lived workload and make the timeout part of the deployment specification. A value of zero disables draining and should be intentional.

Rolling-deployment behavior

A useful validation uses two backends and an identifiable response header or hostname. Start a long transfer through backend A, then remove A from the pool while backend B remains healthy. A new request should go to B while the existing transfer to A continues. Observe when A stops receiving new connections and whether the long transaction completes before the timeout. Repeat with a transaction deliberately longer than the timeout so the team recognizes the expected termination signature.

Configuration changes have their own semantics. Microsoft documents a limitation in which a gateway configuration update can terminate ongoing connections after the drain timeout. That means the drain period should be larger than the maximum expected client transfer during changes, not only during backend deregistration.

Verification

az network application-gateway http-settings show \

Network Watcher VPN troubleshoot: platform diagnostics for gateways and connections

Why it matters

VPN incidents frequently begin with an imprecise complaint such as “the tunnel is down” or “one branch cannot reach Azure.” Network Watcher VPN troubleshoot provides an Azure platform diagnostic run against a VPN virtual network gateway or a specific VPN connection. It returns a Healthy or UnHealthy result with action guidance and writes detailed diagnostic files to an Azure Storage container. The tool is valuable because it exposes Azure-side platform evidence that cannot be derived from a single client ping or from the on-premises firewall alone.

The result must be interpreted narrowly. A Healthy VPN troubleshoot result means the selected Azure gateway or connection did not fail the diagnostic checks. It does not prove that every application prefix has a correct route, that an NSG permits the flow, or that the remote application is listening. The diagnostic is one layer in a workflow, not an end-to-end synthetic transaction.

Architecture

Network Watcher must be enabled in the same region as the VPN virtual network gateway. A troubleshooting request targets either the gateway resource or an individual VPN connection and references an Azure Storage account and container path for logs. Azure performs the diagnostic checks, returns status and action text, and stores detailed artifacts. A gateway-level run is appropriate when several connections fail simultaneously; a connection-level run is more precise when one site is affected while other tunnels on the same gateway remain healthy.

The output is primarily control-plane and platform evidence. Pair it with the peer firewall’s IKE/IPsec logs, Azure connection state, BGP state where used, learned routes, and a representative application test. Save the diagnostic output with timestamps so it can be correlated with the peer device and Azure Monitor rather than discussed from memory.

Prerequisites and implementation

Confirm Network Watcher is available in the gateway region, identify whether the incident affects the whole gateway or one connection, and provision a Storage account/container for logs. Retrieve the storage resource ID and choose a storage path that operations can access during the incident. The diagnostic request is long-running; do not cancel it because it does not return immediately.

STORAGE_ID=$(az storage account show \
  -g <storage-rg> -n <storage-account> --query id -o tsv)

az network watcher troubleshooting start \
  --resource-group <vpn-rg> \
  --resource <vpn-connection-name> \
  --resource-type vpnConnection \
  --storage-account "$STORAGE_ID" \
  --storage-path "https://<storage-account>.blob.core.windows.net/<container>"

For a gateway-wide incident, target the virtual network gateway resource using the supported resource type from the current command reference. For one failed branch, use the connection-level form shown above. Keep the diagnostic artifacts for the same timestamp as the peer-device logs so IKE negotiations, disconnects, and Azure actions can be compared precisely.

Diagnostic interpretation

If the result is Healthy while users cannot reach one application prefix, do not rerun the same platform diagnostic repeatedly. Move to routing and policy evidence: check Azure effective routes, BGP-learned prefixes, the remote route table, IP Flow Verify where applicable, and the application listener. If the result is UnHealthy with an actionable connection problem, follow that finding before making unrelated security or DNS changes.

Storage failures are a different fault domain. A diagnostic run that cannot write logs because the storage path or permissions are wrong tells you that the troubleshooting workflow is misconfigured; it does not prove the VPN data plane is unhealthy. Fix log storage and rerun.

Azure Firewall threat intelligence: reputation filtering before ordinary rules

Why it matters

Azure Firewall threat intelligence uses Microsoft threat feeds to identify high-confidence malicious IP addresses and domains. It can be disabled, configured to alert, or configured to alert and deny. The key architectural fact is precedence: threat-intelligence filtering is evaluated before ordinary NAT, network, and application rule processing. A connection can therefore be blocked because of reputation even when a later application rule explicitly allows the FQDN. This ordering is essential for troubleshooting because editing a later rule cannot override an earlier threat-intelligence deny.

Alert-only mode is useful when introducing the feature because it shows which flows would be affected without immediately changing connectivity. Alert-and-deny converts the feed into enforcement. A threat-intelligence allowlist provides an exception mechanism, but it should be treated as security governance rather than as a convenient replacement for investigating the endpoint and destination. Broad exceptions weaken a control specifically intended to stop high-confidence malicious communication.

Architecture

Routing first delivers the packet to Azure Firewall. Threat intelligence compares the source or destination to the current Microsoft feed. In deny mode, a high-confidence match is blocked and logged before the packet reaches the normal rule collections. If there is no threat-intelligence block, processing continues through the normal NAT, network, and application rule logic according to Azure Firewall semantics. The exact traffic path therefore stays the same; the security decision point is added at a higher precedence.

With Firewall Policy, threat-intelligence configuration can be centrally managed and inherited according to policy design. The exception list needs strong ownership because an inherited allowlist entry can affect multiple firewalls. Operations should distinguish a threat-intelligence log event from an ordinary application-rule deny so the remediation goes to the correct control.

Prerequisites and implementation

Confirm traffic is actually routed through Azure Firewall and that logging is enabled to a workspace where security operations can query the relevant events. Select Alert first when introducing the control to an environment with uncertain dependencies; review high-confidence matches, investigate false positives, then move to Deny according to the organization’s risk policy. Keep exception approvals separate from ordinary application-rule changes.

az network firewall update \
  -g <resource-group> \
  -n <firewall-name> \
  --threat-intel-mode Deny

az network firewall show \
  -g <resource-group> \
  -n <firewall-name> \
  --query "{mode:threatIntelMode,state:provisioningState}" -o json

The configuration enables alert-and-deny on the firewall resource. When Firewall Policy is the management plane, apply the corresponding current policy setting instead of creating conflicting resource-level assumptions. Use a controlled Microsoft-documented test indicator where available, not a real malicious destination, to prove the enforcement path safely.

Rule precedence and exception governance

Suppose an application rule allows partner.example, but the resolved destination appears in the threat feed. In deny mode, the connection can be blocked before the application-rule allow becomes relevant. The correct question is therefore “why did threat intelligence classify this indicator?” rather than “why did my allow rule fail?” If the indicator is a verified false positive and business traffic must continue, use the narrowest supported exception and record an expiration/review owner.

When a source inside the network repeatedly contacts malicious destinations, do not focus only on connectivity restoration. The source host may be compromised. Preserve firewall logs, correlate endpoint telemetry, and treat the event as a security incident. Threat intelligence is useful because it can convert network telemetry into an investigation trigger as well as a block decision.

Verification

Azure Front Door WAF rate limiting: fixed-window protection at the edge

Why it matters

A valid HTTP request can still be abusive when it arrives too frequently. Azure Front Door WAF rate-limit rules let the edge count requests that match defined conditions and block additional matching requests from a client socket IP after a threshold is crossed in a fixed time window. This is useful for login endpoints, expensive APIs, promotions, scraping targets, and other paths where the origin can be exhausted by requests that are individually well formed. It is not a replacement for application authentication, user-based quotas, or DDoS protection; it is an additional edge control.

The counting model affects threshold design. Rate limiting is based on the client socket IP and a one- or five-minute fixed window. Distributed Front Door infrastructure means extremely small limits can be less exact than a centralized counter, and clients behind enterprise NAT or carrier-grade NAT may share a public source IP. A threshold that seems generous for one user can become restrictive for hundreds of users behind the same proxy.

Architecture

The client connects to a Front Door edge. The WAF evaluates a custom RateLimitRule and its match conditions, such as Request URI. Matching requests below the threshold continue through normal WAF and routing processing to the origin. After the threshold is exceeded, subsequent matching requests are blocked at the edge for the remainder of the fixed window. The origin never receives those blocked requests, which is why the control can reduce backend resource pressure.

Every useful rate-limit rule should have deliberate scope. A condition matching /api/login protects that endpoint without throttling unrelated static assets. A broad condition can be appropriate for an entire API, but it should be justified with observed traffic. WAF rate limiting does not alter origin health probes, load-balancing priority, or session affinity; allowed traffic follows the same Front Door routing path as before.

Prerequisites and implementation

Select or create a Front Door WAF policy and identify the domain/security policy to which it is associated. Choose the protected path from actual application telemetry and calculate a threshold from normal per-client behavior plus a safety margin. Include shared-NAT clients in the analysis. The example below creates a rate-limit custom rule and then adds a URI condition.

az network front-door waf-policy rule create \
  --name rateLimitLogin \
  --policy-name <waf-policy> \
  --resource-group <resource-group> \
  --rule-type RateLimitRule \
  --rate-limit-duration 1 \
  --rate-limit-threshold 1000 \
  --action Block \
  --priority 1 \
  --defer

az network front-door waf-policy rule match-condition add \
  --match-variable RequestUri \
  --operator Contains \
  --values "/api/login" \
  --name rateLimitLogin \
  --policy-name <waf-policy> \
  --resource-group <resource-group>

Associate the WAF policy with the intended Front Door endpoint/domain using the current Standard/Premium security-policy workflow. Test from a controlled source below the threshold, then above it, and then after the fixed window resets. Query WAF logs and origin request metrics together so you can prove that blocked requests never reached the application.

Threshold design and observability

A one-minute window responds quickly to bursts; a five-minute window is better suited to sustained request rates. Very low thresholds can create false positives because many legitimate clients may share a public IP and because distributed counters are not a billing meter. Use WAF rate limiting as a protective control with a safety margin rather than as an exact per-user contract.

Operational dashboards should include rule name, match condition, client socket IP, action, URI, and origin request volume. If origin load remains high, verify that the abusive path actually matches the condition and that the WAF policy is associated with the active domain. Lowering the threshold does nothing when the requests never match the rule.

Verification

az network front-door waf-policy rule show \
  -g <resource-group> --policy-name <waf-policy> \
  -n rateLimitLogin -o jsonc
Representative expected success

rateLimitDurationInMinutes: 1
rateLimitThreshold: 1000
action: Block
match: RequestUri Contains /api/login
Controlled load below threshold: allowed
After threshold: WAF blocks matching requests
Origin metrics: blocked requests absent

Wait for the next fixed window and verify that matching requests are allowed again. Also test an unrelated URI to confirm the rule is not broader than intended.

Troubleshooting

az network front-door waf-policy rule show \
  -g <resource-group> --policy-name <waf-policy> \
  -n rateLimitLogin -o jsonc
Representative failure

The rule is healthy but the test traffic is outside its match condition. Add or change the condition only if /api/token is also intended to be protected. Recreating the policy or lowering the threshold cannot make a nonmatching URI count toward the rule.

Azure Virtual Network Manager Network Verifier: static reachability analysis as a repeatable control

Why it matters

Network Verifier answers a different question from packet capture or a live connection test. It analyzes Azure network configuration and supported policy to determine whether a precisely defined source should be able to reach a precisely defined destination. The output is a modeled reachability result and the path or blocking step that produced it. This is valuable before a change because it can test intended segmentation without waiting for an outage, and after a change because it can identify the policy object that contradicts the design.

The service does not prove application availability. A static analysis can say that TCP/443 is reachable while the destination process is stopped or a guest firewall blocks the connection. Conversely, NoPacketsReached can be the desired outcome for a negative security assertion such as “internet-facing subnet must not reach management TCP/22.” The value comes from writing precise intents and interpreting the result against the intent’s purpose.

Architecture

Network Verifier is available through an Azure Virtual Network Manager verifier workspace. The workspace contains reachability-analysis intents and the results of analysis runs. An intent defines source resource, destination resource, source and destination IPs, port ranges, and protocols. The parent Network Manager scope defines the network resources available to the analysis. Supported controls include many Azure constructs such as NSGs, security admin rules, route tables, peering, connected groups, Private Endpoints, service endpoints, and supported managed-network paths.

The workspace can also be delegated to teams that need verification rights without full control of the entire Network Manager. That makes it useful for change-control pipelines. A central team can maintain reusable positive and negative intents, run them before and after a change, and retain the JSON results as evidence that the intended path or isolation property still holds.

Prerequisites and implementation

Use a Network Manager whose scope includes the source and destination resources, and confirm Network Verifier regional availability. Install or update the current virtual-network-manager Azure CLI extension when required. Create a verifier workspace, then define an intent with exact resource IDs and traffic parameters. Avoid broad wildcards that make the result difficult to tie to a business requirement.

az extension add --name virtual-network-manager

az network manager verifier-workspace create \
  --name <workspace> \
  --network-manager-name <network-manager> \
  --resource-group <resource-group> \
  --location <supported-region>

az network manager verifier-workspace reachability-analysis-intent create \
  --name web-to-api-443 \
  --workspace-name <workspace> \
  --network-manager-name <network-manager> \
  --resource-group <resource-group> \
  --source-resource-id <source-vm-id> \
  --destination-resource-id <destination-vm-id> \
  --ip-traffic "{source-ips:['10.10.1.4'],destination-ips:['10.20.1.4'],source-ports:['1024-65535'],destination-ports:['443'],protocols:['TCP']}"

Run the intent with the documented analysis-run command from the current extension and save the result. Create at least one complementary negative intent for critical segmentation. For example, web-to-API TCP/443 should be reachable, while web-to-management TCP/22 should be blocked. Running both after a network change catches the common failure where fixing one outage broadens access unintentionally.

Positive and negative intents

For a required positive flow, Reachable or AllPacketsReached is the expected static outcome. For a negative assertion, NoPacketsReached with the intended NSG or security-admin deny can be a successful result. Preserve the intent definition with the result so a future reviewer can understand whether “blocked” represented a failure or the required security state.

When the model says Reachable but users still fail, move to runtime tools: Connection Troubleshoot, packet capture, guest logs, application listener checks, or appliance telemetry. When the model identifies one supported Azure control as the blocker, change only that control and rerun the identical intent. This prevents troubleshooting from becoming a sequence of unrelated policy edits.

Verification

az network manager verifier-workspace reachability-analysis-run show \
  --name <analysis-run> \
  --workspace-name <workspace> \
  --network-manager-name <network-manager> \
  --resource-group <resource-group> -o jsonc
Representative expected success for a positive intent
provisioningState: Succeeded
result.outcome: Reachable / AllPacketsReached
path: source -> routing/peering -> destination subnet
blockingStep: none

The static Azure configuration permits the modeled flow. Follow with a runtime test when the requirement is actual service availability rather than configuration reachability.

Troubleshooting

  --name <analysis-run> --workspace-name <workspace> \

Azure Load Balancer administrative state: controlled backend maintenance overrides

Why it matters

Administrative state lets an operator override the normal health-probe eligibility decision for a specific Load Balancer backend pool instance. The three states are Up, Down, and None. None returns the backend to ordinary probe-driven behavior. Down prevents new connections from being assigned even when the probe reports healthy, which is useful during patching or controlled removal. Up forces the backend to remain eligible even when the health probe reports failure. That last option is powerful but risky because it can intentionally send new traffic to an unhealthy instance.

The feature is different from changing the health endpoint. Health tells the load balancer what the backend reports; administrative state records what the operator wants the load balancer to do. A maintenance workflow can therefore take a healthy server out of new-flow rotation without deliberately making the application fail its probe. Monitoring and runbooks should surface the override so a planned Down state is not investigated as a mysterious load-balancer incident.

Architecture

The backend pool contains individual backend addresses. Each probed load-balancing rule still references its health probe. Administrative state modifies the eligibility interpretation for the selected backend address. With None, health-probe state controls behavior. With Down, no new connections are assigned. Existing TCP connections can persist according to the documented semantics, while UDP behavior differs. With Up, the backend is kept eligible even if the probe would otherwise remove it.

The setting is per backend pool instance. If one VM appears in multiple backend pools, the override on one pool does not automatically change the other. If a pool is used by several rules, the backend instance’s admin state affects its eligibility for those associated rules. Microsoft documents limitations, including that administrative state requires probed load-balancing rules and is not a substitute for inbound NAT-rule behavior.

Prerequisites and implementation

Use a Standard Load Balancer with a backend pool whose load-balancing rules have health probes. Know the backend address name and IP. Before maintenance, verify at least one other backend is Healthy and has enough capacity for the additional new-flow load. Record a baseline of probe status and active application sessions. Then set the selected backend to Down without changing the application health endpoint.

az network lb address-pool update \
  -g <resource-group> \
  --lb-name <load-balancer> \
  -n <backend-pool> \
  --backend-address "{name:<backend-address-name>,ip-address:<backend-ip>}" \
  --admin-state DOWN

# Restore normal health-probe behavior after maintenance.
az network lb address-pool update \
  -g <resource-group> \
  --lb-name <load-balancer> \
  -n <backend-pool> \
  --backend-address "{name:<backend-address-name>,ip-address:<backend-ip>}" \
  --admin-state NONE

Do not use Up as a routine way to suppress probe failures. If a backend is actually unhealthy, forcing Up can make the incident worse by sending new users to it. Reserve Up for a documented test or operational scenario where the probe result is known to be misleading and the backend’s readiness has been proved another way.

Maintenance workflow and connection behavior

A controlled patch sequence is: verify the remaining pool capacity, set one backend Down, confirm that new flows stop, observe expected existing-connection behavior, perform maintenance, validate the service locally, set the backend back to None, and wait for the health probe to re-establish eligibility. Only then move to the next backend. This preserves application availability without falsifying the health endpoint.

TCP and UDP existing-flow behavior should be tested for the application rather than generalized from one protocol. The admin-state feature affects eligibility; it is not a session-migration engine. If the application cannot tolerate existing sessions remaining on a server during maintenance, use application-aware draining or a different deployment method.

Verification

az network lb address-pool show \
  -g <resource-group> --lb-name <load-balancer> \
  -n <backend-pool> -o jsonc
# Review Load Balancer health/Insights plus application connection logs.
Representative expected success during maintenance
backend-01 adminState: Down
backend-01 probe: Healthy
backend-02 probe: Healthy
New connections to backend-01: 0
New connections to backend-02: increasing
Existing TCP session on backend-01: persists as documented

The healthy probe plus Down state proves the removal is intentional rather than an application failure.

Troubleshooting

az network lb address-pool show -g <resource-group> --lb-name <load-balancer> -n <backend-pool> -o jsonc
Representative failure
backend-01 adminState: Up
backend-01 health probe: Unhealthy
New connections: still arriving at backend-01

The load balancer is following the explicit Up override. Set the backend to Down for maintenance or None to return control to the health probe, then investigate why the probe is unhealthy. Rewriting the probe to return 200 would hide the service problem rather than solve it.

Application Gateway custom error pages: controlled gateway-generated failure responses

Why it matters

When Application Gateway itself generates an HTTP error, the default page may be operationally correct but inconsistent with an organization’s user experience, incident messaging, or support instructions. Custom error pages let the gateway return organization-controlled HTML for supported response codes such as 400, 403, 405, 408, 500, 502, 503, and 504. The custom artifact is used for gateway-generated failures; it does not replace an application’s own error responses when the backend actually returns content.

The implementation has an external dependency that is easy to miss: Application Gateway downloads the custom HTML from a publicly accessible URL and caches it. The source must return HTTP 200 and meet the documented file-type and size requirements. If the source is unreachable when configured, the gateway cannot cache the intended page. Updating the source file later also does not automatically mean every gateway immediately fetches the new version.

Architecture

A client connects to the Application Gateway listener. Normal healthy requests follow the listener, routing rule, backend setting, and backend pool. When the gateway itself must generate a supported error—for example a 502 because no healthy backend can serve the request—it can substitute the cached custom HTML associated with that status code and configuration scope. Custom pages can be configured globally or at listener level according to the current service model, which allows different applications on the same gateway to present different incident pages.

The custom-error source is separate from the backend application path. A Blob-hosted or web-hosted file can be available even when the protected application is down, which is the point of the design. But that independence also creates its own dependency: the source URL must be publicly reachable by Application Gateway when it retrieves the file. Relative resource links inside the page are not equivalent to embedding content; referenced images or CSS are fetched separately by the client and should use appropriate absolute URLs.

Prerequisites and implementation

Prepare a simple static HTML page for each required status code. Host it at a publicly accessible URL that returns HTTP 200 without authentication. Keep the file below the documented size limit and use a supported .htm or .html path. Include only information that is safe to expose during an outage; avoid internal hostnames, incident IDs that reveal infrastructure, or debugging details.

$appgw = Get-AzApplicationGateway \
  -Name <application-gateway> \
  -ResourceGroupName <resource-group>

Add-AzApplicationGatewayCustomError \
  -ApplicationGateway $appgw \
  -StatusCode HttpStatus502 \
  -CustomErrorPageUrl "https://<public-host>/errors/502.html"

Set-AzApplicationGateway -ApplicationGateway $appgw

For listener-specific branding, use the corresponding listener-level cmdlet documented by Microsoft. Before applying the gateway configuration, fetch the source URL from an external client and verify status 200, content type, and page size. After applying the change, induce a controlled gateway-generated error in a test environment and verify the client receives the custom artifact.

Scope, caching, and operational design

Choose global versus listener-specific configuration intentionally. A shared corporate 502 page may be appropriate for a single-purpose gateway, while a multi-tenant gateway may need listener-level pages so each application gives users the correct support path. Keep the error page independent of the failing application. If its images, CSS, or scripts are hosted on the same unavailable origin, the custom page may render poorly exactly when it is most needed.

Application Gateway caches the page rather than continuously retrieving the source. When the file is updated, follow the documented method to trigger a gateway configuration refresh and then retest. Treat error-page changes like a deployment: version the artifact, validate externally, update the gateway, and verify the actual response. Do not assume that editing the source object automatically updates the cached response immediately.
