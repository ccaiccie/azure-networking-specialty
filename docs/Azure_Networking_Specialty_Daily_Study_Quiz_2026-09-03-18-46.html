Lesson 1 · Hybrid connectivity and architecture

ExpressRoute Global Reach for private site-to-site WAN transit

Use Global Reach when separate on-premises sites already terminate on ExpressRoute circuits and need private site-to-site connectivity across Microsoft’s backbone.

What you need to know

  • Global Reach links the private peerings of two ExpressRoute circuits so routes from each on-premises site can be exchanged across Microsoft’s global network.
  • Cross-geopolitical-region connectivity requires Premium SKU.
  • The configuration uses a dedicated /29 IPv4 prefix for the circuit-to-circuit link; IPv6 can use /125.
  • Global Reach complements a provider WAN rather than replacing all WAN functions.
  • Validate route advertisements, overlaps, ownership authorization, and peering-location failure domains.
Primary: https://learn.microsoft.com/en-us/azure/expressroute/expressroute-global-reach
Scenario / implementation: https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-set-global-reach
Lesson 2 · Hybrid connectivity and architecture

ExpressRoute BFD and failure-detection boundaries

BFD accelerates CE/PE-to-MSEE link failure detection, but end-to-end convergence still depends on gateway and routing convergence elsewhere.

What you need to know

  • BFD is supported on ExpressRoute private and Microsoft peering.
  • Microsoft enables BFD by default on newly created MSEE peering interfaces, while customer/provider edge devices still require configuration.
  • BFD shortens forwarding-failure detection; it does not make every downstream convergence stage instantaneous.
  • Microsoft notes overall failover between ExpressRoute virtual network gateways and MSEEs can still take up to about a minute.
  • Test primary and secondary paths and verify redundant prefix advertisements during maintenance.
Primary: https://learn.microsoft.com/en-us/azure/expressroute/expressroute-bfd
Scenario / implementation: https://learn.microsoft.com/en-us/azure/expressroute/secure-expressroute
Lesson 3 · Hybrid connectivity and architecture

VPN Gateway NAT for overlapping branch address spaces

VPN Gateway NAT solves overlapping-address connectivity for route-based IPsec connections by translating branch or VNet prefixes at the gateway.

What you need to know

  • Azure VPN Gateway NAT is for overlapping address spaces; it is not Internet breakout and does not provide NAT64.
  • IngressSNAT translates on-premises space as traffic enters Azure; EgressSNAT translates Azure VNet space toward a remote network.
  • Static NAT creates fixed mappings; dynamic NAT uses pool-based translation with directionality constraints.
  • NAT is supported on route-based IPsec/IKE cross-premises connections, not VNet-to-VNet or point-to-site.
  • Associate NAT rules with the intended VPN connection and align route advertisements with post-NAT prefixes.
Primary: https://learn.microsoft.com/en-us/azure/vpn-gateway/nat-overview
Scenario / implementation: https://learn.microsoft.com/en-us/azure/vpn-gateway/nat-howto
Lesson 4 · Routing and traffic management

Virtual WAN routing intent for centralized inspection

Routing intent programs a secured Virtual WAN hub so private and/or Internet traffic classes are steered to a chosen security next hop.

What you need to know

  • Routing intent abstracts route programming into Private Traffic and Internet Traffic routing policies.
  • Policies point to a security next hop such as Azure Firewall, an integrated NVA, or supported security provider in the hub.
  • Private Traffic includes branch and VNet prefixes as one policy class.
  • Because policy is broad, identify flows that need intentional bypass before enabling it.
  • Troubleshoot hub route tables, connection effective routes, next hops, associations, and propagation.
Primary: https://learn.microsoft.com/en-us/azure/virtual-wan/about-virtual-hub-routing
Scenario / implementation: https://learn.microsoft.com/en-us/azure/virtual-wan/how-to-routing-policies
Lesson 5 · Core networking infrastructure

Virtual Network Manager connectivity configurations at scale

Azure Virtual Network Manager creates policy-driven mesh or hub-spoke connectivity across network groups instead of hand-managing large peering sets.

What you need to know

  • Connectivity configurations support mesh and hub-and-spoke topologies across network groups.
  • Mesh uses a connected-group construct; a VNet hub uses peerings; a Virtual WAN hub uses Virtual WAN VNet connections.
  • Direct connectivity can let selected spokes communicate directly and avoid hub hairpinning.
  • Global mesh extends connected-group communication across regions; overlapping addressing still causes routing ambiguity.
  • Dynamic network-group membership plus declarative configuration reduces peer-by-peer drift.
Primary: https://learn.microsoft.com/en-us/azure/virtual-network-manager/concept-connectivity-configuration
Scenario / implementation: https://learn.microsoft.com/en-us/azure/virtual-network-manager/how-to-deploy-hub-spoke-topology-with-azure-firewall
Lesson 6 · Core networking infrastructure

StandardV2 NAT Gateway for resilient dual-stack outbound connectivity

NAT Gateway gives subnet-level, scalable outbound SNAT; StandardV2 adds zone redundancy and IPv6 capability.

What you need to know

  • When associated to a subnet, NAT Gateway becomes the default next hop for Internet-bound outbound traffic without an activation UDR.
  • It performs SNAT for outbound flows and DNAT only for replies to outbound-originated connections; unsolicited inbound is not provided.
  • StandardV2 is zone redundant by default and supports IPv4 and IPv6; Standard is zonal and IPv4-only.
  • Public IP resources contribute SNAT port inventory for large connection scale.
  • Design for public IP capacity, ports, idle timeouts, zones, and firewall-egress requirements.
Primary: https://learn.microsoft.com/en-us/azure/nat-gateway/nat-gateway-resource
Scenario / implementation: https://learn.microsoft.com/en-us/azure/nat-gateway/quickstart-create-nat-gateway-v2
Lesson 7 · Core networking infrastructure

DNS Private Resolver inbound, outbound, and ruleset design

DNS Private Resolver replaces VM-based DNS forwarders for hybrid name resolution using inbound endpoints, outbound endpoints, and forwarding rulesets.

What you need to know

  • Inbound endpoints provide an Azure private IP target for on-premises conditional forwarders.
  • Outbound endpoints plus forwarding rulesets send selected Azure queries toward custom or on-premises DNS servers.
  • Ruleset links apply forwarding behavior to VNets and do not require peering to the resolver VNet.
  • Avoid forwarding loops when a hub-linked ruleset points a namespace back to the same hub inbound endpoint.
  • Design dedicated endpoint subnets, UDP/TCP 53 reachability, redundancy, and observability.
Primary: https://learn.microsoft.com/en-us/azure/dns/private-resolver-endpoints-rulesets
Scenario / implementation: https://learn.microsoft.com/en-us/azure/architecture/networking/architecture/azure-dns-private-resolver
Lesson 8 · Security, monitoring, and private service access

Service endpoint policies as PaaS data-exfiltration guardrails

Service endpoint policies constrain which Azure Storage resources a subnet may reach over service endpoints, reducing data-exfiltration paths.

What you need to know

  • Service endpoints extend VNet identity to supported Azure services over the Azure backbone.
  • A service endpoint policy is an allow policy at the subnet that can restrict Azure Storage access to listed resources.
  • Unlisted resources are denied over the endpoint, so application dependencies must be inventoried.
  • The control applies to traffic from associated Azure subnets, not directly to on-premises-originated traffic.
  • Private Link is often preferred for private access, but endpoint policies remain useful when service endpoints are intentionally selected.
Primary: https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview
Scenario / implementation: https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies
Lesson 9 · Security, monitoring, and private service access

Azure Firewall DNS proxy and FQDN filtering in network rules

For FQDNs in Azure Firewall network rules, DNS proxy keeps client and firewall resolution consistent so non-HTTP/S filtering can follow changing addresses.

What you need to know

  • Network rules can use FQDNs for TCP/UDP such as SSH, RDP, or NTP, but DNS Proxy must be enabled.
  • Clients should use Azure Firewall as DNS proxy so client and firewall resolve the same names consistently.
  • Network-rule FQDN filtering resolves names to IPs and cannot distinguish shared-IP FQDNs using SNI.
  • For HTTP/S and MSSQL, application rules are generally preferable for FQDN semantics.
  • Troubleshoot client DNS, firewall proxy settings, upstream resolver results, rule type, and protocol.
Primary: https://learn.microsoft.com/en-us/azure/firewall/fqdn-filtering-network-rules
Scenario / implementation: https://learn.microsoft.com/en-us/azure/firewall/dns-settings
Lesson 10 · Security, monitoring, and private service access

DDoS IP Protection versus Network Protection

Choose DDoS IP Protection for per-public-IP economics or Network Protection for broader VNet-plan coverage and added value services.

What you need to know

  • Azure DDoS Protection focuses on Layer 3/4 mitigation; Layer 7 protection requires a WAF.
  • DDoS Network Protection is plan-based and can protect VNets across subscriptions in a tenant.
  • DDoS IP Protection is enabled on an eligible public IP and uses a per-protected-IP model.
  • Core mitigation engineering is similar, while value-added support and cost-protection features differ by tier.
  • Validate protection state and telemetry instead of assuming protection from resource existence alone.
Primary: https://learn.microsoft.com/en-us/azure/ddos-protection/ddos-protection-overview
Scenario / implementation: https://learn.microsoft.com/en-us/azure/ddos-protection/manage-ddos-ip-protection-cli
Lesson 11 · Core networking infrastructure

Network Watcher packet capture for evidence-driven troubleshooting

Network Watcher packet capture remotely captures VM/VMSS traffic to local disk or storage for packet-level diagnosis and post-capture analysis.

What you need to know

  • Packet capture can be started remotely through Network Watcher rather than logging into the VM.
  • Sessions can target VMs or scale sets and be started through portal, PowerShell, CLI, REST, or alerts.
  • Filters narrow protocol, IP, and port scope to reduce capture volume.
  • Captured files can reveal latency, unexpected protocols, destination patterns, and request/response behavior.
  • Use packet capture when higher-level route, NSG, DNS, and health views are insufficient.
Primary: https://learn.microsoft.com/en-us/azure/network-watcher/packet-capture-overview
Scenario / implementation: https://learn.microsoft.com/en-us/azure/network-watcher/packet-capture-inspect
Lesson 12 · Security, monitoring, and private service access

Application Security Groups for role-based NSG policy

ASGs let NSG rules target logical workload roles instead of hard-coded IP addresses, making policy easier to scale as NIC membership changes.

What you need to know

  • ASGs group NICs by application role so NSG rules can reference logical source or destination groups.
  • Policies survive workload replacement and scaling without hard-coding every IP address.
  • NICs assigned to an ASG must obey same-VNet constraints.
  • If source and destination are ASGs in one rule, the relevant NICs must be in the same VNet.
  • A scalable model uses role-based ASGs plus explicit NSG rules and representative traffic validation.
Primary: https://learn.microsoft.com/en-us/azure/virtual-network/application-security-groups
Scenario / implementation: https://learn.microsoft.com/en-us/azure/virtual-network/tutorial-filter-network-traffic
