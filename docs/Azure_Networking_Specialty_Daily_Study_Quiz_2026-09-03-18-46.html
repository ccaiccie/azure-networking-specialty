ExpressRoute Global Reach for private site-to-site WAN transit

ExpressRoute Global Reach turns two otherwise separate ExpressRoute private peerings into an inter-site private path across Microsoft’s backbone. The design problem it solves is not VNet-to-VNet connectivity; it is on-premises Site A reaching on-premises Site B when both sites already connect to Microsoft through ExpressRoute.

Why it matters

Enterprises commonly have multiple data centers, colocation sites, campuses, or regional WANs. Each may have its own ExpressRoute circuit for Azure access. Without Global Reach, an ExpressRoute circuit primarily gives the connected on-premises location private reachability to Azure virtual networks associated with that circuit. If two on-premises locations also need to communicate, a carrier WAN, SD-WAN overlay, IPsec mesh, or other private transport usually provides that path. Global Reach adds another option: Microsoft’s global network can carry the traffic between the two ExpressRoute circuits.

The useful mental model is circuit-to-circuit route exchange. Each customer edge advertises on-premises prefixes over ExpressRoute private peering. When Global Reach links the circuits, eligible on-premises prefixes can be exchanged so each site learns how to reach the other through Microsoft.

Architecture and packet flow

flowchart LR
A[Site A LAN 10.10.0.0/16] --> CE1[CE Router A]
CE1 --> ER1[ExpressRoute Circuit A]
ER1 --> GR[Global Reach across Microsoft backbone]
GR --> ER2[ExpressRoute Circuit B]
ER2 --> CE2[CE Router B]
CE2 --> B[Site B LAN 10.20.0.0/16]
ER1 -. Azure private peering .-> VA[Azure VNet A]
ER2 -. Azure private peering .-> VB[Azure VNet B]

A packet from 10.10.5.10 to 10.20.8.20 is routed by the Site A CE toward ExpressRoute because BGP has learned 10.20.0.0/16 through the linked circuit. The frame crosses the provider handoff to the Microsoft Enterprise Edge, traverses Microsoft’s backbone, exits through Circuit B, and reaches Site B. The return path should be deliberately engineered. Pure routing can tolerate some asymmetry, but stateful firewalls and NAT devices often cannot.

Prerequisites and design assumptions

You need two provisioned ExpressRoute circuits with Azure private peering and compatible providers/peering locations. Microsoft requires a dedicated infrastructure prefix for the Global Reach relationship; IPv4 commonly uses a /29. That prefix must not overlap with enterprise or Azure ranges. For connectivity between different geopolitical regions, Premium SKU is required. Always check current location support and provider capabilities before presenting the feature as universally available.

Implementation workflow

  1. Verify both circuits are provisioned and private peering is operational.
  2. Inventory the prefixes each CE advertises and confirm there is no overlap.
  3. Select a dedicated nonoverlapping Global Reach link prefix.
  4. Create the Global Reach connection from one ExpressRoute circuit to the other in the Azure portal or automation tooling.
  5. Verify the relationship on both circuits.
  6. Inspect BGP learned routes on both CE routers and confirm remote-site routes appear through ExpressRoute.
  7. Test both directions and compare the forward and return paths.

BGP policy and coexistence with an existing WAN

Global Reach does not remove normal BGP policy. If an MPLS or SD-WAN path also reaches the remote site, decide which path should win. On your CE devices you can influence routing with local preference, AS-path policy, or other platform-supported attributes. Avoid unintentionally advertising a default route that turns one site into transit for traffic it was never designed to carry. Overlapping RFC1918 prefixes still require renumbering or translation elsewhere; Global Reach cannot make ambiguous routing deterministic.

Enterprise scenario

A company has Los Angeles and London data centers. Each already uses ExpressRoute for Azure. The existing WAN carrier is excellent domestically but expensive internationally. Global Reach provides a private LA-to-London path over Microsoft’s backbone while the carrier WAN remains a backup. The team prefers Global Reach for application prefixes but keeps management traffic on the legacy WAN during migration. Because both sites contain stateful firewalls, the engineers verify that return traffic follows the same inspection domain before moving production flows.

Troubleshooting

  • No remote route: verify both private peerings are up, Global Reach is connected, the remote CE advertises the prefix, and route policy is not filtering it.
  • Route exists but traffic fails: check firewalls, MTU, asymmetric return paths, provider handoffs, and address overlap.
  • Wrong path wins: inspect BGP best-path attributes on the CE and compare alternate WAN routes.
  • Configuration rejected: verify Premium SKU requirements and Global Reach availability at both peering locations.

Exam/interview takeaway

Private peering connects on-premises to Azure; Global Reach extends the private-peering model so two on-premises networks behind separate circuits can communicate through Microsoft’s backbone. Use it when the organization already owns ExpressRoute and wants another private WAN option, not when it needs SD-WAN application steering, deep WAN optimization, or a general-purpose encrypted overlay.

ExpressRoute BFD and failure-detection boundaries

Bidirectional Forwarding Detection (BFD) is the fast failure detector for an ExpressRoute peering path. It can reduce adjacency failure detection from BGP-scale seconds or minutes to subsecond intervals, but it is only the first stage of an end-to-end failover.

The problem BFD solves

ExpressRoute is built around redundant physical and logical connections, but redundancy has value only if a failed path is detected and withdrawn. BGP keepalive/hold timers are intentionally conservative. Microsoft documents MSEE BGP values that are typically 60-second keepalives and 180-second hold time. An intermediate Layer-2 failure can leave the customer router interface electrically up while packets disappear, so plain BGP might wait for the hold timer. BFD exchanges lightweight liveness packets at a much tighter interval so the routing process can react quickly.

sequenceDiagram
participant CE1 as CE Primary
participant M1 as MSEE Primary
participant CE2 as CE Secondary
participant M2 as MSEE Secondary
CE1->>M1: BFD control
M1-->>CE1: BFD reply
Note over CE1,M1: forwarding path fails
CE1-xM1: BFD expires
CE1->>CE1: invalidate BGP next hop
CE1->>CE2: use surviving path
CE2->>M2: existing BGP/BFD stays Up

Detection is not convergence

BFD tells BGP that the adjacency path is unusable. BGP must then invalidate routes, select alternatives, program the forwarding table, and propagate changes. Azure gateways, route servers, firewalls, NAT state, or applications can add additional recovery time. Therefore “BFD is subsecond” must never be translated into “the application will recover in subsecond time.” Measure each stage.

Where it is configured

Microsoft supports BFD on ExpressRoute private and Microsoft peering and enables the MSEE side for supported peerings. The customer/provider side still needs compatible BFD configuration. In a managed Layer-3 offering, the device peering with Microsoft can be carrier-managed, so coordinate with the provider. Router syntax differs by Cisco IOS XE, NX-OS, Junos, Arista EOS, and other platforms, but operationally you need a BFD session associated with each BGP adjacency.

Validation methodology

Do not stop at BGP Established. On the CE, verify the BFD neighbor is Up and inspect negotiated timers, multiplier, interface, uptime, and last failure reason. Then run a maintenance test that interrupts the forwarding path and record four timestamps: BFD Down, BGP route withdrawal, alternate route/FIB installation, and application recovery. That exposes whether the real delay is failure detection or a later convergence stage.

Failure boundaries

BFD proves liveness between BFD endpoints; it does not prove the application beyond the neighbor is healthy. An Azure UDR mistake, DNS problem, broken firewall rule, or failed application can exist while BFD remains Up. Likewise, a failure deeper inside the on-premises network may not affect the ExpressRoute BFD session. Use BFD together with end-to-end path monitoring and application telemetry.

Timer tradeoffs

Aggressive BGP keepalives can also shorten failure detection, but BFD is designed specifically for low-overhead forwarding-path liveliness. Extremely aggressive BFD values can create false positives during congestion or control-plane stress, so use provider- and platform-supported values and test them under realistic load.

Enterprise scenario

A financial company has dual ExpressRoute cross-connects. A Layer-2 optical fault occurs in the primary provider path while the CE interface remains up. Without BFD, the BGP hold timer controls detection. With BFD, the adjacency fails quickly and BGP moves traffic to the secondary path. If users still see a 20-second interruption, the engineer knows to inspect stateful firewall/NAT recovery or downstream convergence rather than assuming BFD itself failed.

Troubleshooting

  • BGP Up/BFD Down: compare BFD support, interface binding, timers, ACL/control-plane policing, and provider configuration.
  • BFD Down/no failover: verify an alternate BGP route actually exists and is eligible.
  • Route switches/application fails: inspect firewall sessions, NAT, DNS, load balancers, and return-path symmetry.
  • Only one circuit advertises a required prefix: BFD cannot manufacture redundancy; fix route advertisement.

Takeaway

BFD accelerates path failure detection; BGP and the rest of the network still perform convergence. Design diverse paths first, then use BFD to detect their failure quickly.

VPN Gateway NAT for overlapping branch address spaces

Azure VPN Gateway NAT solves a specific merger, acquisition, and branch-network problem: two routed networks that must communicate through IPsec use overlapping prefixes. Translation makes the routing view unique without immediately renumbering either network.

Why overlap breaks routing

If Azure VNet 10.0.1.0/24 and a branch also use 10.0.1.0/24, a host cannot unambiguously decide whether 10.0.1.25 is local or across the VPN. The same ambiguity appears in BGP or static routes. VPN Gateway NAT maps one or both original ranges into nonoverlapping translated ranges at the gateway boundary.

flowchart LR
B[Branch real 10.0.1.0/24] -->|IngressSNAT| G[Azure VPN Gateway]
G -->|Branch appears as 192.168.20.0/24| V[Azure VNet real 10.0.1.0/24]
V -->|EgressSNAT if required| G
G -->|Azure appears as 192.168.10.0/24| B

IngressSNAT versus EgressSNAT

An IngressSNAT rule changes the on-premises source address as traffic enters Azure and performs the corresponding reverse destination translation for traffic returning to that branch. An EgressSNAT rule changes the Azure VNet source representation as traffic leaves toward the branch and reverses that mapping for return traffic. You do not create a separate DNAT rule for the reverse direction; the SNAT rule defines the bidirectional mapping relationship.

Static and dynamic translation

Static NAT provides deterministic prefix mapping. A /24 normally maps to another /24 and host offsets remain predictable. It is ideal when both sides initiate connections. Dynamic NAT uses a pool and is stateful, trading deterministic host mapping for address conservation; directionality and capacity matter more. For most certification-style designs, static translation is easier to reason about because routing and logging map clearly to translated prefixes.

Routing interaction

NAT only works when routing uses the translated view. A frequent mistake is creating a NAT rule but continuing to advertise the original overlapping prefix to the peer. All External Mapping ranges across connected networks must be unique. If BGP is used, verify the advertised/learned prefixes after the NAT association; if static routing is used, configure the peer to send traffic to the translated range.

Implementation workflow

  1. Inventory all CIDRs and identify exactly which ranges overlap.
  2. Choose translated ranges that do not overlap anything reachable through the gateway.
  3. Create IngressSNAT and/or EgressSNAT rules with the proper Static/Dynamic type.
  4. Associate the rules to the correct VPN connection; an unassociated NAT rule has no effect.
  5. Update BGP advertisements or static routes for translated prefixes.
  6. Test both initiation directions and document which addresses each firewall and application will see.

What VPN Gateway NAT is not

It is not Internet breakout, not NAT64, and not Azure NAT Gateway. It is for route-based cross-premises IPsec/IKE connectivity and overlapping network remediation. It also cannot automatically repair application protocols that embed literal IP addresses inside payloads.

Enterprise scenario

A company acquires two branches, each using 10.50.0.0/16, while Azure workloads also use part of 10.50.0.0/16. Branch A is presented to Azure as 172.20.0.0/16 and Branch B as 172.21.0.0/16. Azure uses the translated ranges to reach them. If the Azure address space must also appear differently to a branch, EgressSNAT presents Azure through another unique range. The team updates firewall rules to match the post-NAT addresses visible at each inspection point.

Troubleshooting

  • Tunnel Up/no traffic: confirm NAT rule association, translated routes, and NSG/firewall policy.
  • One prefix works/another does not: verify every overlapping prefix has a matching mapping; prefix lengths must be appropriate.
  • BGP shows original range: review NAT/routing configuration and the connection association.
  • Logs show unexpected IPs: identify whether the log point sits before or after translation.

Takeaway

IngressSNAT changes the branch representation entering Azure; EgressSNAT changes the Azure representation toward the branch. The objective is deterministic routing across overlapping networks, not generic outbound NAT.

Lesson 4 · Routing and traffic management

Virtual WAN routing intent for centralized inspection

Routing intent is Azure Virtual WAN’s policy abstraction for steering broad traffic classes through a security next hop in a secured virtual hub. It reduces manual route-table engineering when the goal is consistent centralized inspection.

What routing intent abstracts

Traditional Virtual WAN designs can combine hub route tables, associations, propagations, labels, and static routes. That offers flexibility but can become difficult to operate at large scale. Routing intent instead exposes two high-level policy classes: Private Traffic and Internet Traffic. Each policy can point to an eligible Azure Firewall or supported integrated NVA/security resource in the hub.

flowchart TB
BR[Branches S2S/P2S/ExpressRoute] --> VH[Secured Virtual Hub]
SP[Spoke VNets] --> VH
VH -->|Private traffic policy| FW[Azure Firewall / supported NVA]
VH -->|Internet traffic policy| FW
FW --> PRIV[Other branches / VNets]
FW --> NET[Internet]

Private traffic is intentionally broad

Private Traffic includes branch and VNet prefixes as one routing-intent class. This is useful when the requirement is “inspect all private traffic,” but it also means enabling the policy can redirect flows that previously had direct paths. Before deployment, inventory bypass requirements and confirm the security appliance can handle the aggregate throughput and session scale.

Packet flow

For Branch1 to Spoke2, the packet enters the virtual hub through the branch connection. The destination is classified as private traffic. With Private Traffic routing policy active, the hub sends the packet to the configured security next hop. Azure Firewall evaluates policy and, if allowed, returns the packet into the hub routing domain toward Spoke2. The return flow should follow a compatible inspected path so stateful sessions remain valid.

Implementation sequence

  1. Deploy/validate the Virtual WAN hub and branch/VNet connections.
  2. Deploy the supported security next hop in the hub and confirm health/scale.
  3. Enable Private Traffic and/or Internet Traffic routing policy.
  4. Select the desired security next hop for each class.
  5. Apply the routing intent and inspect effective routes.
  6. Test branch-to-VNet, VNet-to-VNet, branch-to-branch, and Internet flows that matter to the design.

Routing intent does not replace firewall policy

The hub decides the path; the security appliance decides whether a flow is allowed, inspected, or translated. A correctly programmed next hop can still produce an outage if Azure Firewall lacks a rule, DNS cannot resolve a dependency, or return routing bypasses the stateful device.

Routing intent versus custom route tables

Use routing intent when the requirement maps cleanly to broad centralized inspection. Use custom Virtual WAN route tables when you need granular segmentation or exceptions that do not fit the two policy classes. Complex enterprises can still use route tables for segmentation while routing intent handles security steering.

Enterprise scenario

A retailer has 200 branches, 40 Azure spokes, and a mandate that branch-to-cloud and spoke-to-spoke private traffic traverse a central NGFW. Rather than manually managing route-table relationships for every connection, the platform team enables Private Traffic routing intent toward the firewall. Operational focus moves to firewall scale, exception handling, policy, and verification.

Troubleshooting

  • Inspect Virtual WAN connection effective routes and routing-intent status.
  • Verify the intended next hop is healthy and selected.
  • Check firewall network/application/NAT rules and logs.
  • If the firewall forwards but destination fails, inspect spoke UDRs, NSGs, overlapping prefixes, and propagation.
  • If only Internet traffic fails, confirm the firewall has working egress/NAT and DNS.

Takeaway

Routing intent is policy-driven route programming; it is not the security policy engine itself. It is most valuable when consistent inspection is more important than per-connection route customization.

Implementation: Configure routing policies

Azure Virtual Network Manager connectivity configurations at scale

Azure Virtual Network Manager (AVNM) lets you express VNet connectivity as policy across network groups rather than creating and maintaining peerings one VNet at a time.

Why AVNM matters

A large Azure estate can contain hundreds of VNets owned by different teams and subscriptions. Manual peering becomes a lifecycle problem: every new VNet needs connections, gateway-transit decisions, security review, and later cleanup. AVNM introduces network groups, static or dynamic membership, and a connectivity configuration that is deployed as intent.

Topology models

flowchart LR
subgraph HS[Hub and spoke]
H[Hub VNet] --- S1[Spoke 1]
H --- S2[Spoke 2]
H --- S3[Spoke 3]
S1 -. direct connectivity optional .- S2
end
subgraph M[Mesh]
A[VNet A] --- B[VNet B]
B --- C[VNet C]
A --- C
end

A hub-and-spoke configuration peers the hub VNet to spokes. Optional direct connectivity lets spokes in the same network group communicate without hairpinning through the hub. A mesh configuration creates bidirectional connectivity among group members using the connected-group mechanism. Regional connectivity is the default; global mesh can be enabled for supported cross-region designs.

Dynamic membership

Dynamic groups use Azure Policy conditions so membership can follow properties such as subscription, resource group, naming conventions, or tags. A VNet tagged environment=prod can automatically join a production group and inherit the intended topology. This is one of AVNM’s biggest operational benefits because connectivity follows resource lifecycle without a separate peering ticket.

Effective routing

When troubleshooting, inspect VM NIC effective routes. Hub/spoke paths often show next-hop type VNetPeering or GlobalVNetPeering. Direct spoke connectivity created through the connected-group construct can show ConnectedGroup. That tells you whether AVNM’s direct-connectivity path is active.

Implementation workflow

  1. Create AVNM with the appropriate management scope.
  2. Create network groups representing workload/environment boundaries.
  3. Add VNets statically or through dynamic Azure Policy membership.
  4. Create mesh or hub-and-spoke connectivity configuration.
  5. Choose options such as direct connectivity, global mesh, and hub gateway usage.
  6. Deploy the configuration to the required regions; defining it alone does not make it active.
  7. Validate effective routes and application traffic.

Security tradeoff

Direct connectivity removes hub hairpin latency, which is excellent for trusted east-west application flows, but it can bypass a hub firewall if centralized inspection was assumed. Treat it as a routing and security-path decision. If every spoke-to-spoke packet must traverse an NVA, do not enable a direct path that undermines that requirement.

Lifecycle and failure modes

Dynamic membership policy assignments have their own lifecycle. Microsoft notes that Azure Policy artifacts can persist even after AVNM is deleted, so clean them up deliberately. Address overlap can also create ambiguity even when networks are allowed into a group. Gateway-transit options fail if the hub does not actually have a suitable VPN/ExpressRoute gateway.

Enterprise scenario

A SaaS company creates a VNet for each application team. Every production VNet must connect to a shared hub, and trusted production spokes in the same region need low-latency direct communication. A tag-based network group plus hub-and-spoke configuration automates the hub connection while direct connectivity creates the trusted east-west path. Test networks live in a separate group without direct connectivity.

Troubleshooting

  • VNet missing: inspect network-group membership/Azure Policy compliance.
  • Config exists but routes do not: verify regional deployment status.
  • Gateway transit fails: confirm a supported gateway exists in the hub.
  • Unexpected spoke reachability: inspect direct connectivity and group membership.
  • Ambiguous routes: inspect overlapping address spaces.

Takeaway

AVNM is connectivity intent plus group-based lifecycle management. It reduces peering drift but does not remove the need to reason about routing, inspection, overlapping CIDRs, or gateway transit.

Primary: Connectivity configurations
Scenario: Hub-spoke with Azure Firewall

StandardV2 NAT Gateway for resilient dual-stack outbound connectivity

Azure NAT Gateway is a subnet-level outbound SNAT service. It gives private workloads predictable, scalable Internet egress without creating unsolicited inbound access. StandardV2 adds zone redundancy and IPv6 capabilities to the model.

Data-plane behavior

When a NAT gateway is associated with a subnet, eligible Internet-bound TCP/UDP flows use its public IP resources for source NAT. A VM at 10.1.2.4:52000 contacting a public service is translated to a NAT public IP and allocated SNAT port. The mapping is stateful so return traffic is translated back. Unsolicited inbound traffic is not forwarded to the VM.

flowchart LR
VM[Private workload 10.1.2.4] --> S[Subnet]
S --> NAT[StandardV2 NAT Gateway]
NAT --> PIP[Public IPv4/IPv6]
PIP --> NET[Internet]
NET -->|reply to outbound session| PIP --> NAT --> VM

SNAT scale

Microsoft documents 64,512 SNAT ports per associated public IPv4 address for NAT Gateway, with TCP and UDP maintaining separate inventories. Public IP resources can be scaled within service limits, giving NAT Gateway a much larger and more deterministic outbound-port pool than many implicit outbound mechanisms. That matters for VM scale sets, container nodes, proxies, and workloads that open many concurrent Internet connections.

Standard versus StandardV2

Standard NAT Gateway is zonal; if its selected zone is unavailable, associated subnet egress can be affected. StandardV2 is designed to be zone redundant and supports IPv4 and IPv6. Microsoft also documents outbound ICMP Echo support for StandardV2. Check current regional/SKU support because these features evolve.

Routing interaction

NAT Gateway normally does not need an activation UDR. But if a subnet has a default UDR to Azure Firewall or an NVA, that next hop owns the egress path and NAT Gateway is not a substitute for the route policy. Effective routes should be the first troubleshooting check whenever a workload uses the wrong public source IP.

Implementation workflow

  1. Create the appropriate NAT Gateway SKU.
  2. Associate supported public IP resources/prefixes.
  3. Associate the gateway to the target subnet.
  4. Review UDRs to confirm Internet traffic is not intentionally sent elsewhere.
  5. From a test VM, query a trusted external service to confirm the observed public source address.
  6. For StandardV2 dual-stack designs, repeat reachability tests over IPv6.
  7. Monitor flow scale, SNAT usage patterns, and idle behavior.

Operational failure modes

Port exhaustion can still occur if capacity is undersized or an application creates huge numbers of simultaneous flows. Idle timeout can break long-lived but silent sessions; application keepalives are often better than treating an infrastructure timeout as infinite. If the egress IP is unexpected, confirm subnet association, effective routes, and whether traffic leaves through a firewall/NVA instead.

NAT Gateway versus Azure Firewall

Choose NAT Gateway when the primary requirement is scalable deterministic outbound SNAT. Choose Azure Firewall when the requirement includes policy enforcement, logging, threat intelligence, FQDN controls, or centralized inspection. NAT Gateway cannot answer which application destination should be allowed; it translates and forwards outbound sessions.

Enterprise scenario

A large VM scale-set subnet needs outbound access to SaaS APIs whose administrators allowlist a small number of source IPs. NAT Gateway provides predictable egress addresses and a large SNAT pool. If the same application later requires central URL/FQDN filtering, the design may move egress through Azure Firewall because the requirement changed from translation to inspection.

Takeaway

NAT Gateway is an outbound translation/scale service, not a firewall or inbound load balancer. StandardV2 is the important choice when zone redundancy or IPv6 is part of the requirement.

Azure DNS Private Resolver hybrid forwarding architecture

Azure DNS Private Resolver is the managed bridge between Azure-provided/private DNS and custom namespaces such as on-premises Active Directory DNS. It removes the need to run DNS-forwarder VMs merely to exchange queries between Azure and on-premises.

Three core objects

An inbound endpoint listens on a private IP in the resolver VNet so external networks can forward DNS queries into Azure resolution. An outbound endpoint provides the egress path for Azure queries that must be sent to custom DNS servers. A DNS forwarding ruleset maps suffixes such as corp.example.com to target DNS server IPs and is associated with an outbound endpoint.

flowchart LR
ON[On-prem DNS] -->|conditional forward Azure private zones| IN[Resolver inbound endpoint]
IN --> AZ[Azure DNS / Private DNS zones]
VM[Spoke VM] --> RS[Forwarding ruleset]
RS --> OUT[Resolver outbound endpoint]
OUT -->|corp.example.com| ON
RS -. linked .- SP[Spoke VNet]

Ruleset links

A ruleset can be linked to VNets so workloads in those VNets inherit forwarding behavior. The linked spoke does not have to be peered to the resolver VNet solely for the ruleset link. This separates DNS-policy distribution from ordinary data-plane peering. Microsoft documents scale limits including large numbers of rules and VNet links; always verify current limits before a large rollout.

Azure-to-on-premises query flow

A VM asks for sql01.corp.example.com. A forwarding rule matches the suffix and sends the query through the outbound endpoint to the on-premises DNS server. The response returns through the resolver to the workload. In the other direction, on-premises DNS can conditionally forward an Azure private namespace to the resolver inbound IP; the resolver can then use linked Azure Private DNS zones to answer private-endpoint names.

Subnet and network prerequisites

Inbound and outbound endpoints use dedicated delegated subnets. The outbound subnet cannot host arbitrary workloads. Plan address space before deployment and permit UDP/TCP 53 across any NSG, firewall, VPN, or ExpressRoute path to custom DNS targets. Use redundant on-premises DNS servers and hybrid paths when the service-level objective requires them.

Avoid forwarding loops

Suppose Azure forwards corp.example.com to on-premises, while the on-premises DNS server forwards the same suffix back to the Azure inbound endpoint. With no authoritative server in the chain, queries loop until timeout. Document which platform is authoritative for each suffix and configure one directional forwarding relationship.

Implementation workflow

  1. Deploy the resolver in a hub/shared-services VNet.
  2. Create dedicated inbound and outbound subnets/endpoints.
  3. Create a forwarding ruleset on the outbound endpoint.
  4. Add rules such as corp.example.com → 10.20.0.10,10.20.0.11.
  5. Link the ruleset to the spokes that need it.
  6. Link the relevant Private DNS zones to the correct VNet context.
  7. Configure on-premises conditional forwarders to the inbound endpoint for Azure private namespaces.

Verification

nslookup sql01.corp.example.com
Resolve-DnsName sql01.corp.example.com
nslookup mystorage.privatelink.blob.core.windows.net

Record which DNS server answered and which address was returned. If a private-endpoint FQDN resolves to a public IP, investigate DNS before routing. For Azure-to-on-prem failures, verify ruleset link, suffix match, outbound endpoint health, and UDP/TCP 53 reachability. For on-prem-to-Azure failures, verify the conditional forwarder, inbound IP, private zone record, and zone links.

Takeaway

Inbound endpoint = DNS queries entering Azure resolution. Outbound endpoint + forwarding ruleset = selected Azure queries leaving toward custom DNS. The resolver forwards DNS; it is not a generic IP router.

Lesson 8 · Security, monitoring, and private service access

Service endpoint policies for PaaS data-exfiltration control

A service endpoint gives an Azure subnet an identity-aware path to a supported PaaS service. A service endpoint policy adds destination restriction so the subnet can be limited to approved service resources instead of reaching every resource in that service.

The exfiltration problem

A compromised VM might be legitimately allowed to reach Azure Storage. If the network control only says “Storage is allowed,” an attacker could potentially send data to a storage account they control. NSGs are poor tools for naming individual PaaS resources because service addresses are large and dynamic. A service endpoint policy can allowlist approved Storage resources for traffic that uses the service endpoint.

flowchart LR
VM[Workload subnet] --> SE[Microsoft.Storage service endpoint]
SE --> P{Endpoint policy}
P -->|listed| GOOD[Corporate Storage account]
P -->|not listed| BAD[Unapproved Storage account denied]

How it differs from Private Link

Service endpoints do not allocate a private IP for the PaaS resource in your VNet; they extend subnet identity to the service over Azure’s backbone. Private Link/private endpoints allocate a private VNet IP for a specific service resource and can be paired with disabling public network access. If the requirement is “the service must be reachable only at a private IP,” use Private Link. If the architecture intentionally uses service endpoints and needs resource allowlisting, endpoint policies are relevant.

Implementation workflow

  1. Inventory every PaaS resource the application legitimately needs.
  2. Enable the required service endpoint such as Microsoft.Storage on the subnet.
  3. Create a service endpoint policy.
  4. Add policy definitions for approved service resources.
  5. Associate the policy to the subnet.
  6. Confirm the target service’s own networking/firewall settings allow the subnet.
  7. Test an approved resource and deliberately test an unlisted resource to prove denial.

Multiple control planes

The endpoint policy is not a replacement for NSGs, Azure Firewall, PaaS authorization, or identity. The request must still pass network controls, and the application still needs valid identity/RBAC/SAS authorization. Think of the endpoint policy as a network-level destination allowlist for the service-endpoint path.

Enterprise scenario

A regulated analytics subnet may upload results to two corporate storage accounts only. The subnet uses the Microsoft.Storage service endpoint and a policy listing only those accounts. If a VM is compromised and the attacker creates another Azure Storage account, the subnet cannot use the endpoint path to exfiltrate to that unapproved account. Identity and DLP controls remain additional layers.

Verification and troubleshooting

  • Confirm the service endpoint is enabled on the correct subnet.
  • Confirm the endpoint policy is associated to that same subnet.
  • Verify the policy lists the correct resource scope.
  • Verify the service firewall/networking page allows the VNet/subnet.
  • Check DNS to ensure the application is using the intended service-endpoint model rather than a private endpoint/proxy path.
  • If an unlisted destination still works, determine whether traffic bypasses the endpoint policy through an alternate subnet, proxy, NVA, or private endpoint.

Takeaway

Remember the layers: service endpoint = subnet identity/path; service endpoint policy = which service resources are allowed; service firewall/RBAC = whether the resource accepts and authorizes the request.

Azure Firewall DNS proxy and FQDN filtering in network rules

FQDN-based filtering in an Azure Firewall network rule works only when DNS resolution and the firewall’s IP decision stay synchronized. DNS proxy makes Azure Firewall part of the name-resolution path so it can associate a hostname with the addresses the client actually uses.

Why DNS consistency is critical

Packets contain IP addresses, not FQDNs. A client can resolve api.vendor.example to one address while a firewall separately resolves the same name to another because of DNS rotation, geographic responses, or short TTLs. Then a perfectly legitimate client flow can miss the FQDN mapping the firewall expects. With DNS proxy enabled, clients ask the firewall for DNS; the firewall forwards the query to its configured DNS service, records the returned IPs, and returns the same answer to the client.

sequenceDiagram
participant C as Client
participant F as Azure Firewall DNS Proxy
participant D as Upstream DNS
participant S as SaaS endpoint
C->>F: query api.vendor.example
F->>D: forward DNS query
D-->>F: 203.0.113.10
F-->>C: 203.0.113.10
C->>F: TCP/9443 to 203.0.113.10
F->>F: map IP to FQDN network rule
F->>S: allow/forward

Network rules versus application rules

Application rules are generally natural for HTTP/S because Layer-7 context such as host/FQDN is available. Network rules are Layer 3/4 constructs and can handle non-HTTP protocols. FQDN network rules are useful when the business requirement is “allow this changing hostname on TCP/9443” rather than “allow these fixed IPs.”

Configuration pattern

  1. Choose the upstream DNS architecture: Azure DNS, DNS Private Resolver, or custom DNS.
  2. Enable DNS proxy on Azure Firewall.
  3. Configure workload VNets/custom DNS so clients resolve through the firewall private IP when the design requires it.
  4. Create the FQDN-based network rule with the correct protocol/port.
  5. Verify DNS first, then verify the transport flow and firewall logs.

Hybrid/private DNS interaction

If clients need Internet and corporate/private names, the firewall’s upstream resolver must be able to answer or forward both. One design is workload → Firewall DNS proxy → DNS Private Resolver/custom DNS → on-premises DNS for corporate suffixes. Avoid loops such as Firewall → custom DNS → Firewall.

Concrete verification

ipconfig /all
nslookup api.vendor.example
Test-NetConnection api.vendor.example -Port 9443

# Linux
cat /etc/resolv.conf
dig api.vendor.example
nc -vz api.vendor.example 9443

Confirm the workload’s DNS server is the intended firewall/proxy chain and that the returned address matches what the firewall logs associate with the FQDN. Then inspect effective routes to prove the TCP flow crosses the firewall. Rule-collection-group and rule priorities also matter; a different rule can match before the rule being investigated.

Enterprise scenario

A backup system uses a vendor endpoint on TCP/9443 whose public IP changes frequently. Rather than allow broad Internet ranges, the firewall network policy uses the vendor FQDN. Clients resolve through Azure Firewall DNS proxy so the firewall sees the same IP answer. The security team gets a stable hostname policy without manually updating IP lists.

Takeaway

FQDN filtering becomes IP forwarding after DNS resolution. DNS proxy is what keeps the firewall’s hostname-to-IP knowledge aligned with client behavior.

Azure DDoS IP Protection versus Network Protection

Azure DDoS Protection offers two paid protection models with similar core L3/L4 mitigation engineering but different scope, economics, and value-added services. Selecting between them is a design and cost-modeling exercise.

What the service does

Paid DDoS Protection tiers provide always-on traffic monitoring, adaptive traffic profiling, automatic mitigation, telemetry, and enhanced protection for eligible public IP resources. The system learns normal patterns and can mitigate volumetric and protocol attacks when attack thresholds are exceeded. This is principally network-layer availability protection, not an application-layer WAF.

flowchart LR
ATT[Attack traffic] --> EDGE[Azure DDoS detection]
LEG[Legitimate clients] --> EDGE
EDGE --> MIT[L3/L4 mitigation]
MIT --> PIP[Protected public IP]
PIP --> APP[Application]
IP[DDoS IP Protection per-IP model] -. selection .-> PIP
NP[DDoS Network Protection VNet-plan model] -. selection .-> PIP

DDoS IP Protection

IP Protection uses a per-protected-public-IP pricing model and is suitable for smaller deployments with a limited number of public IPs. Microsoft states that it shares the core engineering capabilities of Network Protection but does not include all of Network Protection’s value-added services.

DDoS Network Protection

Network Protection associates a DDoS protection plan with VNets containing supported public IP resources. It is often more appropriate when many public endpoints require protection and includes additional benefits such as DDoS Rapid Response, cost-protection features, and WAF-related discounts as documented by Microsoft. Always perform a current cost comparison rather than assuming one tier is cheaper.

Defense in depth

DDoS Protection addresses L3/L4 attack availability. It does not replace WAF for HTTP application attacks, Azure Firewall for network policy, identity controls, rate limiting, or capacity engineering. A resilient public service may combine DDoS Protection, Front Door/Application Gateway WAF, load balancing, autoscaling, caching, and application-level safeguards.

Deployment and observability

For Network Protection, create/associate the DDoS plan with the VNet that hosts the supported public IP resources. For IP Protection, enable protection on each selected public IP. Then configure diagnostics/monitoring before an attack. Operations should know the normal traffic baseline and where to find DDoS metrics, backend health, firewall/WAF logs, and application saturation data.

Enterprise scenario

A small environment exposes two public management/application IPs; per-IP economics might favor IP Protection. A consumer platform has dozens of protected public IP-backed services, strict SLA requirements, and values Rapid Response/cost protection; Network Protection is likely the stronger operational fit.

Incident runbook

  1. Confirm the attacked public IP is actually protected and identify the tier.
  2. Review DDoS metrics to determine whether mitigation is active.
  3. Check backend health and resource saturation independently.
  4. Inspect WAF/firewall/application telemetry for simultaneous L7 abuse.
  5. For Network Protection, use enhanced response/support services when appropriate.
  6. After the event, compare observed vectors with architecture assumptions and update baselines/runbooks.

Takeaway

IP Protection = per-IP model; Network Protection = broader VNet-plan model plus additional operational/value services. Both belong inside a layered resilience strategy.

Network Watcher packet capture for evidence-driven troubleshooting

Network Watcher packet capture provides packet-level evidence from Azure VMs and VM scale sets. It is especially valuable when high-level health checks suggest the network is fine but an application still experiences resets, timeouts, retransmissions, DNS failures, or intermittent connectivity.

Why packet capture is different

Effective routes tell you what Azure intends to route. NSG diagnostics tell you whether policy should allow a flow. Connection Monitor measures reachability. Flow logs summarize sessions. Packet capture shows the actual packet exchange: TCP flags, retransmissions, source/destination addresses, ports, DNS packets, and MTU symptoms. That lets you distinguish a network drop from an application refusal.

flowchart LR
C[Client] --> N[Azure network path]
N --> VM[Target VM / VMSS]
VM --> CAP[Network Watcher capture]
CAP --> PCAP[PCAP file]
PCAP --> A[Wireshark/tcpdump analysis]

Capture design

Use narrow filters. On a busy server, an unfiltered capture becomes difficult to analyze and can collect sensitive traffic. Filter by source/destination IP, protocol, and port where possible. Configure maximum duration and size, reproduce the problem, and stop the capture. Store the file in an approved location and treat it as potentially sensitive data.

Methodology

  1. Write down the expected five-tuple and expected behavior.
  2. Start a filtered capture on the correct VM/VMSS interface.
  3. Reproduce the failure at a known timestamp.
  4. Stop/download the capture.
  5. For TCP, follow SYN → SYN/ACK → ACK and application data.
  6. Correlate the timestamp with NSG, Azure Firewall, load balancer, DNS, and application logs.

How to read common patterns

SYN leaves, no SYN/ACK returns: investigate downstream routing, firewall/NSG, remote listener, or return path. SYN arrives and server sends RST: the network delivered the packet; the application/OS rejected it. Repeated retransmissions or stalls around large segments: investigate MTU/PMTUD. DNS query leaves and no answer returns: investigate DNS server reachability and UDP/TCP 53 rather than the application service.

Practical filtering

For a failing HTTPS flow from 10.10.1.20 to 10.20.4.50, filter those addresses and TCP/443. For DNS, include UDP and TCP/53 because some DNS transactions fall back to TCP. For intermittent problems, extend the duration but keep the tuple filter narrow.

Enterprise scenario

An Azure VM intermittently fails HTTPS calls to an on-premises API over ExpressRoute. Effective routes look correct and the VPN/ExpressRoute path is up. A capture shows SYN, SYN/ACK, ACK, then an immediate reset from the VM’s local proxy. The packet evidence moves the investigation from ExpressRoute to the host/application stack and prevents hours of unnecessary carrier troubleshooting.

Correlation with other Azure tools

Packet evidence is strongest when paired with effective routes, IP flow verify, NSG diagnostics, Connection Monitor, Azure Firewall logs, and load-balancer probe state. For example, NSG diagnostics might say TCP/443 is allowed while the PCAP proves the remote service never returns a SYN/ACK. Together those facts narrow the fault domain quickly.

Takeaway

Packet capture is the prove it on the wire tool. Start with a hypothesis, capture narrowly, reproduce once, and correlate the packet timeline with Azure control-plane evidence.

Application Security Groups for role-based NSG policy

Application Security Groups (ASGs) let NSG rules reference logical roles such as Web, API, and Database instead of lists of individual IP addresses. Security policy follows NIC membership while workload addresses can change.

Why ASGs improve operations

Suppose ten application servers need TCP/1433 access to six database servers. An IP-based rule becomes brittle when servers scale or are redeployed. With ASGs, the source can be ASG-App and destination ASG-DB. New NICs join the appropriate group and the rule remains stable.

flowchart LR
W1[Web NIC 1] --> WEB[ASG-Web]
W2[Web NIC 2] --> WEB
A1[API NIC] --> API[ASG-API]
D1[DB NIC] --> DB[ASG-DB]
WEB -->|NSG allow TCP/8443| API
API -->|NSG allow TCP/1433| DB
WEB -. no direct DB rule .-> DB

ASG versus NSG

An ASG is not a firewall. It is an object referenced by an NSG rule’s source or destination. The NSG remains the enforcement point at a subnet and/or NIC. NSG priority, stateful behavior, service tags, default rules, and effective-rule evaluation still apply.

Concrete policy example

Source: ASG-Web
Destination: ASG-API
Protocol: TCP
Port: 8443
Action: Allow
Priority: 200

Source: ASG-API
Destination: ASG-DB
Protocol: TCP
Port: 1433
Action: Allow
Priority: 210

This is far easier to audit than a rule containing ten source IPs and six destination IPs because it states application intent directly.

Implementation workflow

  1. Create ASGs representing stable workload roles.
  2. Associate VM NIC IP configurations with the appropriate ASG(s).
  3. Create NSG rules using ASGs as source/destination selectors.
  4. Attach the NSG at the subnet/NIC according to design.
  5. Validate with Network Watcher effective security rules, IP flow verify, or flow logs.

Infrastructure as code

Define ASGs, NSG rules, and NIC membership together in Bicep/Terraform/ARM so a scale-out operation adds a VM to the right security role without editing rules. The security team reviews stable role-to-role relationships while the platform pipeline owns membership.

Design guidance

Use a small number of meaningful roles rather than creating an ASG for every host. Web, API, Database, Management, and Monitoring are understandable. Combine ASGs with service tags where policy also references Azure platform services. Scope constraints and current ASG service limits should be checked for the deployment.

Troubleshooting

  • Verify both source and destination NIC IP configurations are actually in the referenced ASGs.
  • Check rule priority; an earlier rule can determine the outcome.
  • Inspect both subnet-level and NIC-level NSGs because both may apply.
  • Use IP flow verify/effective rules to identify the exact matching rule.
  • Confirm the tested IP belongs to the NIC IP configuration with the ASG association.

Enterprise scenario

A platform deploys dozens of ephemeral application VMs daily. Database access is permitted only from the API tier. Each new API NIC joins ASG-API automatically; a single NSG rule permits ASG-API to ASG-DB on TCP/1433. The policy does not change as instances scale.

Takeaway

ASGs make NSG policy role-centric instead of address-centric. They simplify rule maintenance but do not change how NSGs enforce traffic.
