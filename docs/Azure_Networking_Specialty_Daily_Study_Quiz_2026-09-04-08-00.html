ExpressRoute zone-resilient gateways and site failure domains

flowchart LR
DC[On-premises]-->CE[CE routers]
CE-->ER1[ER circuit - peering site A]
CE-->ER2[ER circuit - peering site B]
ER1-->GW[Zone-redundant ExpressRoute gateway]
ER2-->GW
GW-->V[Hub/workload VNets]

Why the design matters

ExpressRoute resiliency is not one checkbox. It is a stack of failure domains: the customer edge, provider path, Microsoft Enterprise Edge connections, ExpressRoute peering location, the Azure virtual network gateway, and the workload routing domain. A circuit is already built with redundant Microsoft-side connections inside one peering location, but that does not protect you from loss of the entire peering facility. Likewise, a zone-redundant gateway protects the Azure gateway layer from a single availability-zone failure but cannot resurrect a failed remote peering site. High availability therefore comes from combining independent protections.

Control plane and data plane

BGP is the control plane between the customer/provider edge and Microsoft. Critical on-premises prefixes should be available across both intended hybrid paths. The data plane follows the selected BGP route through the ExpressRoute circuit, Microsoft backbone, virtual network gateway, and Azure routing fabric. A well-designed secondary circuit is not merely “up”; it advertises the required routes and has enough bandwidth to carry production traffic after failure.

In a dual-site design, customer-edge local preference can make one circuit primary while retaining the other as an immediately usable backup. If both paths are active, validate that stateful firewalls and NAT devices can tolerate the resulting symmetry or asymmetry. Do not infer application resilience from BGP adjacency alone.

Implementation and verification

Deploy a zone-capable ExpressRoute gateway SKU in a supported region, connect the hub to both circuits when the architecture calls for it, and document the peering locations as separate failure domains. Before production, capture BGP routes on both customer-edge routers and effective routes on representative Azure NICs. During a controlled test, withdraw or disable one path, verify the surviving path installs the same critical prefixes, and watch latency, packet loss, and application transactions. Then test the assumption that a complete peering site is unavailable rather than only one BGP neighbor.

In the Azure portal, review ExpressRoute connection state and gateway health. On the network devices use platform-specific BGP commands to inspect learned prefixes, best-path attributes, next hops, and flap history. Network Watcher effective routes can confirm that Azure workload NICs still resolve on-premises prefixes toward the expected gateway.

Enterprise scenario and troubleshooting

A company places a primary ExpressRoute circuit in Los Angeles and a second in another peering location. Both advertise the same data-center routes; policy prefers Los Angeles. A zone-redundant gateway protects the Azure regional gateway tier. If one gateway instance is lost, the service continues. If the entire Los Angeles peering site is lost, the secondary circuit becomes the surviving hybrid path. This architecture explicitly protects two different failures.

When troubleshooting, classify the fault first. One BGP session down while its mate on the same circuit remains up suggests a connection-level issue. Both sessions at one peering site down suggests a broader circuit or site issue. Healthy circuits with unreachable VMs points toward gateway connection state, UDRs, NSGs, route propagation, or return-path asymmetry. The interview-level takeaway is simple: dual links inside one circuit, zone-redundant gateways, and geographically diverse circuits solve different problems and should not be conflated.

Custom IPsec/IKE policy and policy-based traffic selectors

sequenceDiagram
participant O as On-prem VPN device
participant A as Azure VPN Gateway
O->>A: IKE proposals
A-->>O: Matching IKE policy
O->>A: IKE_AUTH and selectors
A-->>O: CHILD_SA
O->>A: Encrypted ESP/NAT-T traffic

Why custom policy exists

Azure’s default VPN proposals are designed to interoperate with a broad set of devices. Custom IPsec/IKE policy is needed when a third-party peer supports only a specific cryptographic combination or when an organization mandates exact algorithms. The policy defines IKE encryption and integrity, Diffie-Hellman group, IPsec encryption and integrity, PFS group, security-association lifetime, and data-size limits. Both peers need at least one compatible proposal.

Negotiation and selector behavior

IKE builds the authenticated control channel. The IPsec CHILD_SA then protects user traffic. If phase-one parameters do not overlap, IKE does not establish. If IKE is healthy but phase-two parameters or traffic selectors do not match, the tunnel may appear partially established while data never moves. That distinction is one of the most useful troubleshooting heuristics.

Azure route-based gateways normally use broad selector behavior and let routing decide which prefixes enter the tunnel. Some legacy or policy-based peers insist on explicit local/remote prefix pairs. Azure can enable UsePolicyBasedTrafficSelectors on a route-based connection with a custom policy to improve interoperability. This changes selector negotiation; it does not make Azure a classic policy-based routing appliance.

Implementation and change control

Inventory the peer’s supported IKE version, encryption/integrity algorithms, DH/PFS groups, SA lifetimes, selector model, and whether NAT-T is required. Select one secure common policy. Apply the custom policy to the Azure VPN connection and configure matching settings on the peer. In PowerShell, New-AzIpsecPolicy creates the policy object that is associated with the connection. In the portal, the same values are entered on the site-to-site connection’s IPsec/IKE configuration.

Treat crypto changes as an interface contract. Record old and new proposals, change both ends in a coordinated window, and verify IKE state, IPsec SAs, bytes in/out, and actual application reachability. Where the peer supports multiple proposals, stage the new compatible option first so you do not create a simultaneous hard cutover.

Enterprise scenario and troubleshooting

A newly acquired manufacturing site uses a firewall that requires AES256/SHA384 and exact subnet selectors. Default negotiation fails. The Azure team creates a matching custom policy and enables policy-based selectors for the plant prefixes. IKE establishes, a CHILD_SA forms for the intended subnets, and the plant reaches its Azure application without replacing the firewall.

If the tunnel never forms, check UDP 500/4500 reachability, peer IP, pre-shared key, IKE version, and phase-one proposal overlap. If IKE is established but traffic fails, inspect IPsec proposal/PFS, selector pairs, routes, NAT, NSGs, overlapping ranges, and return-path routing. One-way byte counters often indicate a routing, NAT, or selector problem rather than IKE itself. The key takeaway is that cryptography and traffic selectors are both part of the VPN interoperability contract.

Virtual WAN route-maps and BGP policy control

flowchart LR
B[Branch]-->|Inbound route-map|H[Virtual hub router]
V[VNet connection]-->|Inbound|H
H-->BEST[Hub best-path selection]
BEST-->|Outbound route-map|E[ExpressRoute/branch advertisement]

Where policy is applied

Virtual WAN route-maps bring policy-based route manipulation to the managed virtual hub. They can match prefixes, BGP communities, and AS paths, then drop or modify advertisements. Common designs include aggregation, selective filtering, AS-path prepending, and community tagging. The most important concept is the relationship between route-map direction and the hub’s own best-path decision.

An inbound route-map is evaluated before routes enter the virtual hub router’s routing table, so it can influence what the hub learns. An outbound route-map is evaluated after the hub has already selected its best paths, when it prepares routes for advertisement to a connection. Therefore, an outbound policy can shape what a branch receives but cannot retroactively change the hub’s already-completed best-path selection.

Rule semantics and limitations

Match conditions within a route-map rule are conjunctive: the route must satisfy the configured conditions for the rule to act. Rules are processed in sequence. When no rule matches, the default result is allow, not implicit deny. Actions include dropping a route or modifying attributes/prefixes. Route summarization can reduce route scale, but a summary can cover destinations that are not truly reachable, producing a black hole if the aggregate is advertised without component-path validity.

Microsoft documents constraints around AS-path/community manipulation, supported ASN formats, reserved Azure ASNs, and interactions with NAT. Engineers should verify the current limits before standardizing a policy. When summarization changes the route, associated BGP attributes may not survive in the way an engineer expects, so observe the post-policy advertisement rather than assuming it.

Implementation and verification

Start with the Route Map dashboard and capture the current advertisements for the target connection: prefix, AS path, community, and direction. Create a narrowly scoped policy and attach it only to the intended connection/direction. Then inspect the dashboard again to confirm the transformed route set. Keep a before/after table in change control, especially when a summary replaces multiple routes.

Enterprise scenario and troubleshooting

A global enterprise has a branch whose edge router can accept fewer routes than the Virtual WAN hub normally advertises. Several contiguous spoke prefixes can safely be summarized. An outbound route-map toward that branch aggregates them. The hub retains granular internal routes and best paths, while the branch receives the smaller route table. If one component prefix later moves or becomes unreachable, the network team must ensure the aggregate is still operationally valid.

If a route disappears unexpectedly, verify the connection and direction first, then the rule order, match values, and drop/modify action. If the hub chooses an unexpected best path, do not troubleshoot an outbound map as if it were an inbound policy—inspect the route before outbound transformation. Verify representative destinations inside every aggregate. The core takeaway is: inbound maps influence what the hub learns; outbound maps shape what the hub advertises after best-path selection.

VNet peering gateway transit and NVA service chaining

flowchart LR
ON[On-premises]-->GW[Hub VPN/ER gateway]
GW-->H[Hub VNet]
H<-->|Peering|S1[Spoke 1]
H<-->|Peering|S2[Spoke 2]
S1-->|UDR|N[NVA/firewall]
N-->S2

Peering is connectivity, not automatic transit

VNet peering creates high-bandwidth private connectivity across Azure’s backbone between two virtual networks, but peering is non-transitive. Two spokes that each peer to a hub do not automatically gain spoke-to-spoke transit through the hub. Hub-and-spoke architectures therefore combine peering with gateway transit, UDR-based service chaining, or direct spoke peering depending on the requirement.

Gateway transit

Gateway transit allows a spoke to use a VPN or ExpressRoute gateway located in the hub. On the hub-to-spoke peering, enable Allow gateway transit. On the spoke-to-hub peering, enable Use remote gateways. The spoke can then learn or use hybrid routes through the hub gateway. This centralizes expensive gateway infrastructure and simplifies branch/on-premises connectivity for many spokes.

A spoke that uses the remote hub gateway cannot simply treat its own gateway as an equivalent simultaneous transit gateway for the same design. Plan the gateway ownership and failover model deliberately. If the hub advertises many spoke prefixes back on premises, summarized gateway prefixes may reduce route scale in supported designs, but any summary must correspond to real reachable address space.

NVA service chaining

Service chaining deliberately sends traffic through an NVA in a peered VNet. A spoke route table can point a destination—often 0.0.0.0/0 or selected private ranges—to the private IP of a hub firewall/router. The NVA must have IP forwarding and platform/vendor routing configured. Return-path route tables must be designed with the appliance’s state model in mind.

Enterprise scenario and troubleshooting

An enterprise has one regional hub with ExpressRoute and a firewall pair. One hundred spokes use remote gateway transit for on-premises routes. Spoke default routes send Internet traffic to the hub firewall, and selected spoke-to-spoke flows are also inspected. The team templates peering flags and route-table associations in infrastructure as code and validates a test NIC in each spoke class using effective routes.

When a spoke cannot reach on premises, first confirm both peering states and the gateway-transit flags, then inspect effective routes. If a UDR sends the traffic to an NVA, verify the appliance route table, IP forwarding, health, NSGs, and return path. If spoke-to-spoke reachability was expected “because both spokes peer with the hub,” remember that peering is non-transitive. The interview takeaway is to distinguish three mechanisms: peering connects two VNets, gateway transit shares a hybrid gateway, and service chaining forces selected traffic through a routing/security appliance.

Standard Load Balancer HA Ports for NVAs

flowchart LR
S[Spoke traffic]-->ILB[Internal Standard LB HA Ports]
ILB-->N1[NVA 1]
ILB-->N2[NVA 2]
N1-->D[Destination]
N2-->D
D-->R[Return-path design]

What HA Ports solves

Most application load-balancer rules bind a frontend port/protocol to a backend port. Network virtual appliances must often forward arbitrary TCP and UDP applications, so defining hundreds or thousands of individual rules is impractical. An HA Ports rule on an internal Standard Load Balancer uses protocol All with frontend and backend ports set to zero, allowing the load balancer to distribute broad transport traffic to healthy NVA backends.

Data path and symmetry

A common hub design has a spoke UDR whose next hop is the internal load balancer frontend. The load balancer hashes a new flow to a healthy NVA. The NVA applies security/routing policy and forwards the packet onward. For a stateful appliance, the return path must follow a supported topology so the appliance can associate reverse packets with the existing session. HA Ports distributes flows but does not magically solve every asymmetric-routing scenario.

Health and implementation

The backend health probe is operationally critical. A probe should represent forwarding readiness, not just whether the VM process is alive. When a backend is unhealthy, Standard Load Balancer stops selecting it for new flows. The NVA NIC generally needs IP forwarding enabled, and the appliance must have routes for the transit networks. Floating IP is a separate feature: some vendor clustering patterns require it, others explicitly do not. Follow the vendor’s Azure reference architecture.

A production validation should look at three views simultaneously: Standard Load Balancer backend health, effective routes on the source workload NIC, and the NVA’s own routing/session table. Test TCP and UDP, long-lived and new sessions, on-premises-to-Azure and Azure-to-Internet flows. A topology that is symmetric in one direction might not be symmetric for a hybrid flow.

Enterprise scenario and troubleshooting

A security hub uses two active firewalls behind an internal Standard Load Balancer. All spokes steer Internet traffic to the load-balancer frontend. HA Ports removes per-application rule sprawl and allows the probe to remove a failed firewall from new-flow distribution. During a failure exercise, new sessions move to the healthy firewall while existing sessions are observed for resets according to vendor behavior.

If traffic never reaches an appliance, check the source NIC’s effective route and the load-balancer frontend/backend configuration. If the backend is unhealthy, troubleshoot the health probe and appliance listener. If the appliance receives the first packet but the session fails, inspect forwarding, NSGs, NAT, return routes, and symmetry. The core takeaway: HA Ports provides scalable transport-level distribution for NVAs; routing, health, and stateful symmetry remain separate design responsibilities.

Application Gateway end-to-end TLS and backend trust

sequenceDiagram
participant C as Client
participant G as Application Gateway
participant B as Backend
C->>G: TLS/HTTPS
G->>G: Terminate, route, WAF inspect
G->>B: New TLS session + SNI
B-->>G: Server certificate
G->>G: Trust + hostname validation
G->>B: HTTPS request

Two independent TLS sessions

End-to-end TLS on Application Gateway is not transparent pass-through. The client establishes TLS to the gateway’s frontend listener. Application Gateway terminates that connection so it can perform Layer-7 routing and WAF processing. It then acts as a TLS client and creates a separate encrypted session to the backend. This gives application visibility while keeping the backend hop encrypted.

Trust, hostname, and SNI

The backend setting is configured for HTTPS. Application Gateway validates the backend certificate chain and hostname. Publicly trusted certificates normally work when the identity matches the expected backend host. For a private PKI, upload the trusted root certificate into the backend setting. The hostname sent in the request/SNI must align with the certificate identity and the backend’s virtual-host configuration. A wrong host override or missing private root commonly appears as an unhealthy backend and a 502 to clients.

Frontend TLS policy is independent from backend TLS. Microsoft retired TLS 1.0/1.1 support for Application Gateway interactions on August 31, 2025, so current designs should use TLS 1.2 or later. Certificate rotation also needs a runbook: track frontend certificate expiration, backend certificates, private CA roots/intermediates, and host-name changes.

Implementation and verification

Configure the frontend listener/certificate, backend pool, HTTPS backend settings, and host-name behavior. If the backend uses a private CA, upload the root certificate. Build a custom health probe using the same host name/path the application expects. Verify DNS resolution from the gateway’s network context, route/NSG reachability to the backend, backend health, and then TLS trust.

Enterprise scenario and troubleshooting

A finance application has an Internet-facing WAF listener and internal application servers whose certificates are issued by the enterprise CA. Application Gateway decrypts the client request, applies WAF/routing, then re-encrypts to finance.internal.contoso.com. The enterprise root is trusted in backend settings and the health probe uses that same hostname.

If clients get 502, do not immediately change routes. Backend health often tells you whether the issue is DNS resolution, TCP connectivity, certificate expiration, untrusted chain, or hostname mismatch. Test the layers in order: resolve the backend name, verify TCP port reachability, confirm the backend listens, inspect health status, then validate certificate identity and chain. The takeaway: in end-to-end TLS, Application Gateway is a TLS server to the client and a separate TLS client to the backend, so backend PKI is a network-availability dependency.

Traffic Manager health probing and nested profiles

flowchart TD
DNS[Client DNS query]-->P[Parent Priority profile]
P-->C[Child Performance profile]
P-->DR[DR endpoint]
C-->E[East US]
C-->W[West Europe]
HP[Health probes]-->E
HP-->W
HP-->DR

DNS steering, not proxying

Traffic Manager is a DNS-based steering service. It evaluates profile routing method and endpoint health and returns an answer. The client then connects directly to that endpoint; Traffic Manager does not sit in the application packet path. That architecture is why DNS TTL and resolver/client caching are part of failover time.

Monitoring semantics

HTTP/HTTPS health probes send requests to the configured port/path and evaluate the response. TCP monitoring tests connection establishment. A disabled endpoint is intentionally excluded and is not the same as an enabled endpoint whose monitor state is degraded. A profile can continue steering to healthy members based on the selected routing method.

Nested profiles

Nested profiles let you compose routing methods. A Priority parent can point first to a Performance child containing two active regions and second to a warm disaster-recovery endpoint. Inside the child, users receive the lowest-latency healthy region. If the child has no usable members, the parent can choose the DR endpoint. Nesting can also separate probe settings because monitor configuration is profile-wide.

Implementation and failure testing

Design a health endpoint that proves the region can serve real requests without making every optional dependency a reason to remove the whole region. Choose a TTL that balances DNS query volume with failover responsiveness. In a maintenance window, disable an endpoint intentionally and observe DNS answers through multiple recursive resolvers. For failure tests, make the probe fail and record both monitor-state transition and the time different clients stop using cached answers.

Enterprise scenario and troubleshooting

A SaaS application runs active in East US and West Europe and has a warm standby in Central US. A Performance child contains the active regions. A Priority parent selects that child first and Central US second. If East US fails, the child sends traffic to West Europe. If the active child becomes unusable, the parent selects Central US.

When a failover is slower than expected, separate probe detection from DNS behavior. Check probe protocol, port, path, TLS, expected status, endpoint configured state, profile state, TTL, recursive resolver cache, browser/OS cache, and persistent application connections. The interview takeaway is that health monitoring changes future DNS answers; it cannot revoke an answer a client already cached.

Public IP routing preference

flowchart LR
U[Internet user]-->|Microsoft preference|EDGE[Microsoft edge]
EDGE-->MS[Microsoft global backbone]
MS-->P[Azure public IP]
U-->|Internet preference|ISP[ISP transit]
ISP-->REG[Regional Internet handoff]
REG-->P

What the feature changes

Routing preference influences how supported public-IP traffic uses Microsoft’s global network versus ISP transit. The default Microsoft network preference keeps traffic on Microsoft’s backbone for more of the journey. Internet routing preference hands traffic to or from ISP networks nearer the Azure region, leaving more of the end-to-end path on the public Internet.

This is not a UDR and it does not change private VNet route selection. System routes, UDRs, NSGs, private peering, and Azure DNS remain separate. Routing preference is associated with public connectivity, so it should not be used to solve an internal routing problem.

Design tradeoffs

The Microsoft global network path can provide more consistent backbone handling for latency-sensitive applications. Internet preference can be attractive for cost-sensitive workloads where the tradeoff is acceptable. Current Microsoft documentation should be checked for supported public IP SKU/address family/regions and incompatible combinations before deployment. IPv4 support is the documented baseline for this feature in the current overview.

Implementation and measurement

Create a supported Standard public IP with the required routing preference, then associate it with the workload front end according to the service’s supported model. Tag the resource so operations can see that the external path choice is intentional. Measure latency, jitter, packet loss, and path stability from representative user ISPs rather than one office. External transit can change independently of Azure.

Enterprise scenario and troubleshooting

A company has an interactive customer portal and a high-volume software-download endpoint. The portal remains on Microsoft network preference for consistent latency. The download service is tested with Internet routing preference because bandwidth cost is more important than minimum interactive latency. The workloads use separate public IP resources so their goals do not conflict.

If reachability breaks, verify the ordinary stack before blaming routing preference: public IP association, load-balancer/listener health, NSGs, UDRs, and application state. If performance changes while reachability remains, compare traceroutes/synthetic measurements from multiple networks to determine whether ISP transit changed. The key takeaway: routing preference influences the public external path; it does not replace Front Door/Traffic Manager for global steering or UDRs for private routing.

Private Link Service provider architecture

flowchart LR
C[Consumer VNet]-->PE[Private Endpoint]
PE-->PLS[Private Link Service]
PLS-->|Provider-side NAT|LB[Standard Load Balancer]
LB-->A[Provider application]
OWN[Provider approval]-.->PLS

Provider versus consumer side

Private Link Service is the provider-side construct for publishing your own service through Azure Private Link. A consumer creates a private endpoint in its VNet and connects to the provider’s Private Link Service. The provider application sits behind a Standard Load Balancer whose frontend is associated with the service. No VNet peering mesh or public service endpoint is required.

Provider-side NAT

One of the defining behaviors is source translation. The provider backend normally sees a Private Link Service NAT IP rather than the consumer’s original RFC1918 address. This allows unrelated consumers with overlapping address spaces to use the same service safely. If the provider needs consumer connection metadata, Proxy Protocol v2 can be enabled, but the backend must understand the header or it may treat it as invalid application data.

Approval and scale

Private endpoint connections have an approval lifecycle. Trusted subscriptions can be configured for automatic approval while other requests remain pending for provider review. This separates connectivity intent from raw network routing. Provider NAT IP sizing also matters: many concurrent translated connections consume source ports, so additional NAT IP configurations may be needed within current platform limits. Always check documented address-family/protocol and scale limits for the service before standardizing a design.

Enterprise scenario and troubleshooting

A central platform team publishes an internal API to dozens of application subscriptions, some owned by other business units and using overlapping address ranges. Each consumer creates a private endpoint. The platform team approves the connection and the service receives traffic through its Standard Load Balancer. Several provider NAT IPs are configured to support connection scale.

When a consumer cannot connect, follow the object chain: private endpoint provisioning/connection state, provider approval, Private Link Service association, load-balancer frontend/backend health, NAT subnet/IP capacity, NSGs, and backend application listening. Do not expect provider logs to show the consumer’s original source IP unless the architecture deliberately uses supported metadata such as Proxy Protocol v2. The takeaway: Private Link Service provides private service publishing and isolation, not arbitrary routed connectivity between VNets.

Virtual Network Manager security admin rules

flowchart TD
P[Packet]-->SAR[Security admin rules]
SAR-->|Deny|D[Drop]
SAR-->|Always Allow|AA[Permit without NSG deny]
SAR-->|Allow|N[Continue to NSG]
N-->W[Workload]

Central guardrails above workload NSGs

Azure Virtual Network Manager security admin rules let a central networking/security team enforce policy across network groups while leaving day-to-day NSG ownership with workload teams. Their critical property is evaluation before NSGs, which creates a hierarchy of policy rather than requiring every workload subscription to reproduce the same mandatory rules.

Action semantics

Deny blocks a matching flow immediately. A workload NSG cannot override that deny. Allow allows evaluation to continue, so a downstream NSG can still deny the flow. Always Allow permits the matching flow even if a lower-level NSG would otherwise deny it. These distinctions support patterns such as global high-risk-port blocking, centrally approved platform-management traffic, and delegated application policy.

Rules are organized in collections/configurations and deployed to network groups. Network-group membership can be explicit or policy-driven. Deployment is eventually consistent, so operators should check configuration deployment state rather than expecting an instantaneous global change. Priority ranges should be documented to prevent teams from colliding.

Enterprise scenario and change safety

A security team blocks inbound RDP and SSH from Internet sources to all production network groups. Application teams remain free to manage HTTPS and database rules in their NSGs. A narrowly scoped management service is permitted using the action that matches the governance requirement. The central configuration is first deployed to a canary network group and validated before expansion because a mistaken central deny can have organization-wide blast radius.

Troubleshooting

When an NSG Allow seems ineffective, check whether an earlier security admin Deny matched. When an NSG Deny seems ineffective, check whether an Always Allow rule matched. Verify the VNet belongs to the expected network group, the configuration is deployed to the correct region, the rule priority, protocol/source/destination match, and the action semantics. Microsoft documents service-specific exceptions, so verify the current support matrix for special network-intent-policy or private-endpoint cases. The takeaway is the evaluation chain: admin guardrails first, workload NSGs second when the admin action permits continued evaluation.

Network Watcher NSG diagnostics and IP flow verify

flowchart LR
F[Known five-tuple]-->V[IP flow verify / NSG diagnostics]
V-->R[Effective NSG evaluation]
R-->|Allow|A[Allowed + matching rule]
R-->|Deny|D[Denied + matching rule]
A-->NH[Then verify routing/next hop]

Deterministic policy analysis

When you know the exact flow—source, destination, protocol, port, direction—Network Watcher can evaluate Azure security policy and tell you whether the flow should be allowed or denied and which rule is responsible. This is usually a better first step than packet capture when the likely problem is an NSG priority or source/destination match.

NSGs can exist on both subnet and NIC scopes, with default rules, user priorities, service tags, and augmented rules. Manually reasoning through all effective rules is error-prone. IP flow verify and NSG diagnostics reduce that ambiguity by evaluating a modeled flow against the effective security policy.

A troubleshooting ladder

Use policy simulation first. If it reports Denied, correct the identified rule or network scope and re-run the diagnostic. If it reports Allowed, inspect Network Watcher Next hop/effective routes. If security and routing both look correct, escalate to Connection troubleshoot, packet capture, virtual network flow logs, guest firewall/application logs, or load-balancer diagnostics. This sequence helps keep packet capture as evidence collection rather than a first reflex.

Enterprise scenario

An HTTPS application works from Spoke A but fails from Spoke B. The workload team sees a broad allow in the destination NSG and assumes networking is fine. NSG diagnostics for the exact Spoke B source and TCP/443 identifies a higher-priority deny that matches Spoke B’s CIDR. The team corrects the source range, re-runs the diagnostic, and confirms Allowed before testing the application again.

Operational details

Choose the correct NIC and traffic direction, particularly for multi-NIC VMs. Remember that Azure NSGs are stateful, so established return traffic is not analyzed like a brand-new independent flow. Also distinguish policy simulation from observed telemetry: the diagnostic says what Azure policy should do; flow logs and packet captures show what traffic actually occurred. Current Microsoft guidance states that NSG flow logs retire September 30, 2027 and recommends migration to virtual network flow logs. The core takeaway: prove security policy first, then routing, then packets/application behavior.

Hierarchy and processing pipeline

Firewall Policy organizes configuration into rule collection groups, rule collections, and individual rules. Group/collection priority makes large policies governable, but rule-type processing semantics are just as important. Engineers often troubleshoot the wrong rule because they think “priority” means every rule type competes in one flat list.

DNAT, network, application

For inbound publishing, DNAT rules are processed before network rules. A matching DNAT rule translates the destination and permits the translated flow under the DNAT behavior; you should not design a second network rule expecting it to re-authorize the same matched publishing flow. Application rules do not apply to inbound connections, so inbound HTTP/S Layer-7 inspection belongs on a WAF-capable front end when that control is required.

For outbound traffic, network rules are evaluated before application rules. This can create a shadowing effect: a broad network allow may accept traffic before a restrictive FQDN application rule can evaluate it. Therefore, if an application rule seems ineffective, inspect earlier network rules and their scope before editing the application collection.

Governance and implementation

Reserve documented rule collection group priority ranges for central security, shared infrastructure, and workload teams. Keep DNAT rules narrow, avoid overly broad network allows, and use logs/policy analytics before adding exceptions. Infrastructure as code makes priority ownership visible and reviewable and prevents portal-only drift.

Enterprise scenario and troubleshooting

A shared firewall publishes several inbound services and governs outbound egress. A high-priority group contains centrally managed DNAT and mandatory network policy. Lower groups contain workload network rules and FQDN application rules. An engineer adds a restrictive application rule but sees traffic still allowed. Logs reveal that a broad network rule matched first. Tightening that network rule allows the intended application-layer policy to become effective.

Troubleshoot by classifying the flow first: inbound or outbound, NAT or non-NAT, transport/IP policy or HTTP/S/FQDN application policy. For inbound, inspect DNAT first. For outbound non-HTTP protocols, network rules are normally the relevant layer. For outbound FQDN control, confirm no earlier network rule matched. Correlate firewall logs with effective routes, NSGs, and backend state. The takeaway is to learn the processing pipeline before reasoning about collection-group priority.
