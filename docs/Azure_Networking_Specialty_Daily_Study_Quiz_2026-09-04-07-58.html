Lesson 1 · Hybrid connectivity and architecture

ExpressRoute zone-resilient gateway architecture and site-level failure domains

Architecture / traffic flow

flowchart LR
DC[On-prem DC] --> CE[CE router pair]
CE --> ER1[ER circuit - Site A]
CE --> ER2[ER circuit - Site B]
ER1 --> GW[Zone-redundant ER gateway]
ER2 --> GW
GW --> HUB[Azure hub VNet]

ExpressRoute reliability is best designed as several independent failure domains rather than one “redundant circuit.” A circuit has two Microsoft Enterprise Edge connections inside a peering location. The Azure virtual network gateway is a different regional component. Zone-redundant gateway instances protect the Azure gateway layer from a single availability-zone failure, while a second circuit in a different peering location protects against loss of the peering facility itself. These protections complement each other; neither substitutes for the other.

For packet flow, an on-premises host sends traffic to its customer-edge router, which selects one of the private-peering paths. Microsoft carries the packet from the peering site to the ExpressRoute virtual network gateway and then into the hub or workload VNet. If a gateway instance fails, the service uses surviving instances. If the entire peering site fails, the surviving Azure gateway still needs a reachable second circuit or alternate hybrid path. This is why a single circuit’s dual links do not equal metro-level or site-level diversity.

Implementation starts with route symmetry and diversity. Advertise every critical on-premises prefix through both intended circuits, connect the hub VNet to both circuits where the design requires it, and use customer-edge policy to express primary/secondary intent without making the backup unusable. Validate gateway connection state in Azure, inspect effective routes on workload NICs, and compare BGP learned routes, AS paths, communities, and local preference on the customer edge. Do not call the architecture resilient until you have tested both link failures and full-site failure assumptions.

A common enterprise design uses a primary ExpressRoute circuit at one metro and a second circuit at another peering location. Both advertise the same data-center prefixes; local preference favors the primary. During a zone event, the zone-redundant gateway maintains Azure-side connectivity. During a peering-site outage, the second circuit keeps hybrid reachability. The two events exercise different layers, which is exactly why both layers must be engineered.

Troubleshooting should identify the failing layer before changing routing. One BGP session down with the other session in the same circuit still healthy suggests a connection-level issue. Both sessions at one site failing suggests circuit or peering-location impact. Healthy circuits with unreachable workloads points toward gateway state, route propagation, UDRs, NSGs, or return-path problems. The core design takeaway is: use zone-redundant gateways for Azure regional gateway resiliency and separate peering locations for site resiliency.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Implementation should be documented as a failure-domain matrix. Record the CE device pair, provider circuits, peering locations, gateway SKU, gateway zone model, and route advertisements. In the portal, review each ExpressRoute connection and gateway status; on network devices, capture show bgp/vendor-equivalent output before and after maintenance. For infrastructure as code, keep connections and gateway resources declarative and avoid making emergency portal-only changes without later reconciling state.

Capacity planning matters during failure. A backup circuit or gateway path must have enough bandwidth for the full protected workload, not merely enough to establish BGP. During a controlled exercise, drain or disable one path, verify that critical prefixes remain installed, observe application latency and packet loss, and confirm the return path uses the surviving architecture. A successful BGP failover with overloaded backup bandwidth is not a resilient application design.

Custom IPsec/IKE policies and policy-based traffic selectors

Architecture / traffic flow

sequenceDiagram
participant CE as On-prem VPN
participant AZ as Azure VPN Gateway
CE->>AZ: IKE proposals
AZ-->>CE: Select matching policy
CE->>AZ: IKE_AUTH + selectors
AZ-->>CE: CHILD_SA
CE->>AZ: ESP-protected traffic

Azure VPN Gateway default proposals simplify most site-to-site deployments, but custom IPsec/IKE policy becomes important when a peer firewall supports only a specific cryptographic set or when corporate standards mandate exact algorithms. A custom policy controls IKE encryption and integrity, Diffie-Hellman group, IPsec encryption and integrity, PFS group, security-association lifetime, and data-size limits. Both peers must agree on a usable proposal.

IKE creates the authenticated control channel. IPsec then establishes the CHILD_SA that protects application traffic. A mismatch in IKE values normally prevents phase 1 from forming. A phase-2 mismatch can leave IKE established while no useful data passes. That distinction matters during troubleshooting because “VPN connection exists” is not enough evidence that selectors and IPsec proposals are correct.

Traffic selectors are another interoperability boundary. Route-based peers generally use broad selectors and rely on routing tables. Some policy-based devices expect exact local and remote subnet pairs. Azure supports UsePolicyBasedTrafficSelectors when a custom policy is present, allowing a route-based Azure gateway to interoperate with devices that require policy-style selectors. This changes selector behavior; it does not turn the Azure gateway into a classic policy-based routing platform.

A disciplined implementation inventories the peer’s supported IKE version, crypto suites, DH/PFS groups, and selector model, chooses one secure common policy, applies it to the Azure connection, and mirrors the values on the peer. In PowerShell, New-AzIpsecPolicy builds the policy object and the connection cmdlets apply it. In the portal, custom policy fields are configured on the connection. After the change, verify IKE state, IPsec SAs, bytes in/out, and actual application reachability.

Consider a manufacturing site with an older firewall that requires AES256/SHA384 and explicit traffic selectors. Azure defaults fail. The network team creates a matching custom policy and enables policy-based selectors for the plant prefixes. The tunnel then negotiates without replacing the site appliance. Troubleshooting begins with UDP 500/4500 reachability, NAT-T, PSK, and IKE proposals; if IKE is up but traffic fails, inspect PFS, IPsec proposals, selectors, routes, NSGs, and overlapping prefixes. The takeaway is that crypto parameters and selectors are part of the connectivity contract, not a cosmetic security setting.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

For change control, treat the negotiated proposal as a versioned interface between organizations. Capture IKE encryption/integrity, DH group, IPsec encryption/integrity, PFS, lifetime, traffic selectors, PSK ownership, and peer public IPs in the deployment record. When rotating algorithms, add a compatible proposal on both sides where the peer supports multiple proposals, validate negotiation, and only then remove the old option. This avoids simultaneous “big bang” crypto changes that are difficult to diagnose.

Operational verification should include tunnel state and real traffic counters. A tunnel that is Up but has zero or one-directional byte counters is often a selector, route, NAT, or return-path issue rather than an IKE issue. If NAT exists upstream of the peer, verify NAT-T and UDP 4500 behavior. If multiple tunnels exist, confirm that the remote prefix is actually routed toward the connection whose crypto policy you changed.

Virtual WAN route-maps for aggregation, filtering, AS-path, and community control

Architecture / traffic flow

flowchart LR
B1[Branch] -->|Inbound map| HUB[Virtual hub router]
V[VNet] -->|Inbound map| HUB
HUB --> BEST[Best path]
BEST -->|Outbound map| ER[ExpressRoute]
BEST -->|Outbound map| B2[Branch 2]

Virtual WAN route-maps add policy control to a managed virtual hub. They can match route prefixes, BGP communities, and AS paths, then drop or modify matching advertisements. Typical uses are route aggregation, filtering, AS-path prepending, and community tagging. The critical mental model is where inbound and outbound route-maps sit relative to the hub’s own best-path decision.

An inbound route-map processes advertisements before they enter the virtual hub router routing table. It can therefore affect what the hub learns. An outbound route-map processes routes only after the hub has already selected best paths and is preparing advertisements toward a connection. It can change what a branch or ExpressRoute connection receives, but it cannot retroactively influence the hub’s best-path selection. This is a frequent design and exam trap.

Match conditions within a rule must all be satisfied. Multiple rules are evaluated in sequence. If no rule matches, the default outcome is allow rather than deny. Actions include Drop and Modify. Modify can summarize route prefixes or change BGP attributes. Microsoft documents additional constraints: summarization can strip AS-path/community information, only 2-byte ASNs are supported for route-map manipulation, reserved Azure ASNs should not be prepended, and the same prefix cannot be modified by both NAT and a route-map.

A safe workflow is observe, define, attach, verify. First use the Route Map dashboard to capture current prefix, AS-path, and community state. Build narrowly scoped match rules. Attach the map to the correct connection and direction. Then use the dashboard again to confirm the exact result. Route policy should be treated like code: version the intended state and test one connection before broad rollout.

In a multi-hub enterprise, Branch 1 advertises several contiguous /24s while Branch 2 has a route-count constraint. An outbound route-map toward Branch 2 summarizes those routes to a /16. The hub keeps its internal best paths, while the branch receives a smaller route set. If the summary is broader than actual reachability, however, traffic for unused space can black-hole. Troubleshooting therefore starts by verifying direction, match logic, Terminate behavior, and whether the route exists before policy. The takeaway: inbound route-maps can alter what the hub learns; outbound maps shape advertisements after best-path selection.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Before deploying a route-map, create a before/after advertisement table for every affected connection. Include prefix, AS path, community, direction, and expected action. This is especially important when a match condition is broad or when a summary replaces several routes. In automation, separate route-map definition from attachment so a policy can be created and reviewed before it changes any live advertisements.

Failure testing should include both policy correctness and reachability. A summarized route can look perfect in the dashboard while hiding a failed component subnet. Verify representative destinations inside every aggregate. Likewise, when filtering, verify that the dropped route is truly unwanted and that no dependent return path disappears. Route policy is control-plane configuration with data-plane consequences, so both must be tested.

Lesson 4 · Hybrid connectivity and architecture

VNet peering gateway transit, service chaining, and summarized gateway prefixes

Architecture / traffic flow

flowchart LR
ONP[On-prem] --> GW[Hub VPN/ER Gateway]
GW --> HUB[Hub VNet]
HUB <-->|Peering| S1[Spoke 1]
HUB <-->|Peering| S2[Spoke 2]
S1 -->|UDR| NVA[NVA in hub]
NVA --> S2

VNet peering provides direct Azure-backbone connectivity between two virtual networks, but peering is non-transitive. If two spokes each peer to the hub, they do not automatically route through the hub to each other. Hub-and-spoke designs therefore combine peering with gateway transit, UDR-based service chaining, or direct spoke peering depending on the traffic requirement.

Gateway transit lets spokes share a VPN or ExpressRoute gateway in the hub. On the hub-to-spoke peering, enable Allow gateway transit. On the spoke-to-hub peering, enable Use remote gateways. The spoke can then learn on-premises routes through the shared gateway. A spoke that uses a remote gateway cannot simultaneously use its own gateway for the same transit role, so this decision belongs in the architecture, not in ad-hoc troubleshooting.

Service chaining is explicit routing through an NVA in a peered VNet. A spoke UDR can point to the private IP of a hub firewall or router. Traffic crosses the peering to the NVA, is inspected or routed, and then continues toward another spoke, a gateway, or the Internet. Because stateful NVAs care about return paths, corresponding UDRs and appliance routing must preserve the intended symmetry.

Large gateway-transit environments can advertise many spoke prefixes back on premises. Azure supports summarized gateway prefixes in supported designs so the gateway advertises aggregates rather than every individual spoke route. Summarization reduces scale pressure but must match actual reachable space; a summary that covers unused or misrouted subnets can create black holes.

A typical enterprise has a hub with ExpressRoute, a firewall cluster, and 100 spokes. Spokes use remote gateway transit for on-premises connectivity and UDRs toward the firewall for outbound and selected east-west traffic. The team validates effective routes on a representative NIC in every route-table pattern and checks that on-premises routers learn the intended aggregates. Troubleshooting starts with peering state and flags, then effective routes, then NVA forwarding and return path. The takeaway is to keep the concepts separate: peering connects two VNets, gateway transit shares hybrid gateways, and service chaining deliberately forwards through an appliance.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Implementation at scale benefits from standardized hub and spoke modules. A spoke module can create bidirectional peering with consistent allowForwardedTraffic, remote-gateway settings, and route-table associations. The hub module owns the gateway and NVA. After deployment, query effective routes on a test NIC in each spoke class and verify that on-premises prefixes, default routes, and spoke-specific routes have the expected next-hop type.

Design for dependency boundaries. A single hub simplifies governance but concentrates gateway and inspection dependencies. A regional hub pair can reduce blast radius, but then you must decide whether spokes peer to both hubs, how on-premises routes are advertised, and how failover changes default-route symmetry. Peering itself has excellent bandwidth and latency, but it does not give you a transit routing protocol among spokes; that still requires deliberate architecture.

Lesson 5 · Core networking infrastructure

Standard Load Balancer HA Ports and flow symmetry for NVAs

Architecture / traffic flow

flowchart LR
S[Spoke] --> ILB[Internal Standard LB - HA Ports]
ILB --> F1[NVA 1]
ILB --> F2[NVA 2]
F1 --> D[Destination]
F2 --> D
D --> ILB

HA Ports let an internal Standard Load Balancer distribute essentially all TCP and UDP flows across a healthy backend pool. Instead of defining one rule per application port, an HA Ports rule uses protocol All with frontend and backend ports set to 0. This is particularly useful for network virtual appliances, which must forward arbitrary application traffic rather than serve one fixed listener.

The data path commonly starts with a UDR in a workload subnet pointing toward an internal load balancer frontend. The load balancer hashes the new flow to a healthy NVA. The NVA inspects and forwards the packet. The return path must follow the vendor-supported topology so a stateful appliance sees a valid session. HA Ports can help create symmetric designs, but they do not automatically solve every asymmetric-routing problem.

Health probing is the operational heart of the pattern. The probe must represent appliance forwarding health rather than merely prove that the VM is powered on. When a backend becomes unhealthy, Standard Load Balancer stops assigning new flows to it. The NVA NIC must have IP forwarding enabled where required, and the appliance itself must have routes and policy for transit traffic.

Floating IP is a separate design choice. Some NVA clustering patterns use it; others use HA Ports with Floating IP disabled. The choice affects how frontend addresses are treated and which additional load-balancing rules can coexist. Follow the appliance vendor’s reference architecture instead of assuming Floating IP is always required for high availability.

An enterprise hub has two active firewalls behind an internal Standard Load Balancer. Every spoke default route steers Internet-bound traffic to the load-balancer frontend. HA Ports distributes new connections across both firewalls and the health probe removes a failed instance. During testing, engineers verify TCP, UDP, return path, and stateful failover. Troubleshooting starts with backend health, then UDR next hop, NIC IP forwarding, appliance routes, NSGs, and symmetry. The key takeaway: HA Ports remove per-port rule sprawl and scale NVA front ends, but sound routing and health design remain mandatory.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

A production HA Ports deployment should have at least three validation views: Standard Load Balancer backend health, Azure effective routes on a source workload NIC, and the NVA session/routing table. When all three agree, troubleshooting is straightforward. When they disagree, determine whether the failure is before the load balancer, at backend selection, or after the appliance. Use Network Watcher next-hop and connection troubleshooting to validate the Azure portion of the path.

Session behavior during failure deserves explicit testing. New sessions are redirected when a backend is unhealthy, but existing stateful sessions may reset depending on the appliance and topology. Test failure with long-lived TCP sessions as well as new connections. Also test asymmetric inputs such as traffic arriving from on premises and returning through another interface, because a topology that works for outbound Internet flows may fail for hybrid east-west flows.

Application Gateway end-to-end TLS, backend SNI, and certificate trust

Architecture / traffic flow

sequenceDiagram
participant C as Client
participant AG as App Gateway
participant B as Backend
C->>AG: TLS + HTTPS
AG->>AG: Decrypt / L7 policy
AG->>B: New TLS with SNI
B-->>AG: Certificate
AG->>AG: Validate trust + hostname
AG->>B: HTTPS request

Application Gateway can terminate TLS at the frontend and establish a second TLS session to the backend. End-to-end TLS therefore means two independent encrypted connections, not one opaque TLS session passing through the gateway. This lets Application Gateway perform Layer-7 routing and WAF inspection while keeping traffic encrypted on the backend network.

To enable backend TLS, configure the backend setting for HTTPS. Application Gateway must then trust the backend certificate and validate the hostname. Publicly trusted certificates work when the certificate identity matches the configured backend host. For private PKI, upload the trusted root certificate to the backend setting. SNI and host-name behavior must align with the backend certificate; many 502 errors are actually hostname or trust failures.

The frontend TLS policy controls client-facing protocol and cipher behavior. Microsoft retired TLS 1.0 and 1.1 support for Application Gateway interactions on August 31, 2025, so current designs should use TLS 1.2 or later. Backend TLS is negotiated separately and must be validated independently. A healthy frontend listener does not prove the backend TLS session works.

A robust implementation configures the listener certificate, backend pool, HTTPS backend settings, host override or target-derived host behavior, trusted roots for private CAs, and a custom health probe using the same host name the application expects. Check Backend health before production cutover. If an application uses an internal FQDN, ensure the gateway resolves it through the intended DNS path.

A finance application uses an enterprise CA. Internet clients negotiate TLS to Application Gateway, WAF inspects the request, and the gateway reconnects to finance.internal.contoso.com over TLS. The enterprise root CA is trusted in backend settings and the probe uses the same host name. Troubleshooting a 502 checks backend DNS, route/NSG reachability, listening port, certificate chain, expiration, and hostname/SNI mismatch. The takeaway: Application Gateway acts as a TLS client to the backend, so backend trust and name validation are first-class design requirements.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Certificate operations should be part of the network runbook. Track frontend listener certificate expiration, backend server certificate expiration, private root/intermediate CA rotation, and the host names used by backend settings and probes. When a private CA rotates, stage the new trust chain before replacing backend certificates. Otherwise every backend can become unhealthy at once even though routing and application processes are fine.

For troubleshooting, separate the layers with targeted tests: resolve the backend FQDN from the gateway’s DNS environment, verify TCP reachability to the backend port, inspect Backend health, then inspect TLS certificate name and chain. A route or NSG failure often shows as connection timeout; a certificate validation failure produces a different backend-health reason. This distinction prevents teams from changing UDRs when the real problem is PKI.

Traffic Manager health probing and nested profiles for composite DNS steering

Architecture / traffic flow

flowchart TD
Q[DNS query] --> P[Parent Priority profile]
P --> C[Child Performance profile]
P --> DR[DR endpoint]
C --> E1[East US]
C --> E2[West Europe]
M[Health probes] --> E1
M --> E2
M --> DR

Traffic Manager is DNS-based steering, not a reverse proxy. It answers DNS queries based on routing policy and endpoint health, after which the client connects directly to the selected endpoint. Health monitoring and nested profiles are what allow sophisticated failover logic without putting Traffic Manager in the application data path.

HTTP/HTTPS probes send requests using the configured port and path and evaluate the returned status. TCP probes test connection establishment. Endpoint configured status and monitor status are different: a disabled endpoint is intentionally excluded and is not probed, while a degraded endpoint is enabled but failing health checks. Profile status also affects whether endpoints can be returned.

Nested profiles compose routing methods. A parent Priority profile can prefer a child Performance profile containing two active regions and use a separate DR endpoint as secondary. Within the child, users are sent to the lowest-latency healthy region. If the child no longer has usable endpoints, the parent can fail over to DR. Nesting can also separate monitoring settings because probe configuration is profile-wide.

Failover time includes DNS TTL and client/resolver caching. A probe can mark an endpoint unhealthy quickly, yet clients with cached answers may keep using the old endpoint until TTL expires. Application connection pooling may extend that behavior. Therefore, real testing must include resolver behavior, not merely watch the portal status turn red.

An enterprise SaaS platform runs active in East US and West Europe with warm standby in Central US. The active regions live under a Performance child profile. A Priority parent points first to that child and then to Central US. During maintenance, one active endpoint can be disabled without deleting it. Troubleshooting checks probe protocol, path, status code, port, TLS, endpoint status, profile status, and DNS cache. The takeaway: Traffic Manager steers DNS answers; nested profiles let you combine routing policies into a decision tree.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Design probe endpoints specifically for Traffic Manager. A health URL should validate enough dependencies to prove the region can serve traffic, but it should not be so deep that a minor optional dependency removes the entire region. Use an application health endpoint with a predictable status code and monitor it separately from user traffic. Where child profiles need different paths or ports, nesting provides the separation because monitor settings are profile-wide.

During failover exercises, query the Traffic Manager name through multiple recursive resolvers and record returned endpoints over time. This exposes the effect of TTL and caching. Also test the “all endpoints degraded” behavior so operators understand the DNS response under total failure. DNS steering is eventually observed by clients, so an operational dashboard should combine Traffic Manager monitor status with actual synthetic client resolution and application probes.

Lesson 8 · Routing and traffic management

Azure public IP routing preference: Microsoft global network versus Internet transit

Architecture / traffic flow

flowchart LR
U[Internet user] --> I[ISP]
I -->|Internet preference| R[Regional handoff]
R --> PIP[Azure public IP]
U -->|Microsoft preference| EDGE[Microsoft global edge]
EDGE --> BACKBONE[Microsoft backbone]
BACKBONE --> PIP

Routing preference controls how supported public-IP traffic traverses Microsoft’s network versus ISP transit. The default Microsoft network preference keeps traffic on Microsoft’s global backbone for more of the path. Internet routing preference hands traffic to or from ISP networks closer to the Azure region, so the public Internet carries more of the journey.

This setting is not a UDR and does not alter private VNet routing. It is associated with public-IP connectivity. Internal system routes, UDRs, NSGs, private peering, and DNS continue to work normally. Engineers should avoid using routing preference to solve a private routing problem because it operates at a different layer of the design.

With Microsoft network preference, inbound traffic can enter a Microsoft edge close to the user and cross Microsoft’s backbone to the service region. With Internet preference, the path may remain on ISP networks longer. The difference can influence latency consistency and cost. Measure from representative user networks instead of assuming one path is always superior.

Internet routing preference is configured on a supported Standard public IP, for example with Azure CLI using the routing-preference IP tag. Current Microsoft documentation describes IPv4 support and compatibility limitations, including unsupported combinations that should be checked before architecture standardization. Regional availability should also be verified.

A bulk-download service prioritizes cost over minimum latency. Engineers test both preferences from major customer ISPs and select Internet routing preference for the download endpoint while leaving the interactive portal on Microsoft network preference. Troubleshooting first confirms the public-IP property, then validates the ordinary reachability stack—association, load-balancer/listener health, NSGs, and UDRs—before blaming external transit. The takeaway: routing preference influences the external public path; it does not replace Traffic Manager, Front Door, or VNet routing.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Implementation should begin with a workload classification. Latency-sensitive interactive services generally benefit from the Microsoft global network, while cost-sensitive bulk transfer may be a candidate for Internet preference. Create separate public IP resources when workloads need different behavior rather than trying to make one endpoint serve conflicting goals. Use tags and policy to make the chosen preference visible to operations teams.

Validate from the outside in. Use distributed synthetic probes or traceroutes from representative customer networks and compare latency, jitter, packet loss, and path stability over time. Internet routing can vary with ISP policy, so a single office test is not representative. If performance changes suddenly, compare the external path before modifying Azure routing because the cause may be ISP transit rather than the VNet.

Private Link Service provider architecture, NAT pools, and connection approval

Architecture / traffic flow

flowchart LR
C[Consumer VNet] --> PE[Private Endpoint]
PE --> PLS[Private Link Service]
PLS -->|Provider NAT| SLB[Standard Load Balancer]
SLB --> APP[Provider backends]
PLS -. approval .-> OWN[Provider]

Private Link Service is how a service provider publishes its own application through Azure Private Link. The consumer creates a private endpoint in its VNet. The provider places the application behind a Standard Load Balancer and associates a Private Link Service with a frontend configuration. Consumers can then connect privately without VNet peering or public exposure.

Provider-side NAT is a defining behavior. Consumer traffic appears to the provider backend as coming from the Private Link Service NAT IP pool rather than directly from the consumer’s original address. This removes address-overlap problems between independent tenants. If the provider needs consumer connection metadata, TCP Proxy Protocol v2 can be enabled and the backend application or proxy must understand the header.

The packet travels from the consumer to the private endpoint’s private IP, through Azure Private Link to the provider service, through destination-side translation, and then to the Standard Load Balancer backend pool. Connection approval is controlled by the service provider. Trusted subscriptions can be auto-approved; others can remain pending until reviewed.

NAT IP sizing matters for scale because translated connections consume source ports. Multiple NAT IP configurations increase available ports, subject to current service limits. The provider should monitor connection volume and backend health and should not assume one NAT IP is sufficient for high-connection SaaS workloads. Current documentation also describes protocol/address-family limitations that must be verified for the intended application.

A platform team publishes a shared API to dozens of subscriptions, some with overlapping RFC1918 ranges. Each subscription creates a private endpoint. No peering mesh is required. The provider approves connections and uses several NAT IPs for scale. Troubleshooting starts with private-endpoint connection state, then service-to-load-balancer association, NAT subnet capacity, load-balancer backend health, NSGs, and application listening. The takeaway: Private Link Service is private service publishing with provider-controlled approval and NAT, not general-purpose routed connectivity.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Provider operations should track three different identities: the consumer subscription/private-endpoint connection, the Private Link Service connection object, and the translated source observed by the backend. Approval workflow answers who is allowed to connect; NAT addresses answer what the backend sees. Do not build authorization solely from provider-side source IP unless the NAT design and consumer identity mapping are intentionally maintained.

Capacity testing should generate realistic concurrent connections and watch NAT port consumption, load-balancer backend health, and application connection pools. Adding NAT IPs can expand scale, but the service also has idle-timeout behavior that applications should accommodate with appropriate keepalives. When Proxy Protocol v2 is enabled, validate every backend path because a server that does not understand the header can treat the first bytes as invalid application data.

Virtual Network Manager security admin rules as organization-wide guardrails

Architecture / traffic flow

flowchart TD
P[Packet] --> SAR[Security admin rules]
SAR -->|Deny| DROP[Drop]
SAR -->|Always Allow| PASS[Permit]
SAR -->|Allow| NSG[Evaluate NSG]
NSG --> DEST[Workload]

Security admin rules give a central team policy authority across network groups while leaving NSGs under workload ownership. Their distinguishing behavior is evaluation before NSGs. This lets security enforce non-negotiable guardrails across many VNets rather than relying on every application team to reproduce the same rule correctly.

The three actions have different semantics. Deny blocks the matching flow immediately. Allow permits the flow to continue to NSG evaluation, so a local NSG can still deny it. Always Allow permits the flow regardless of lower-level NSG denies. This supports patterns such as global high-risk-port blocks, centrally approved management traffic, and workload-level application rules.

Rules live in collections inside a security admin configuration and target network groups. Network groups can use explicit or policy-driven membership. After deployment, policy reaches the VNets through an eventual-consistency model, so there can be propagation delay. Priority planning matters because a lower number is evaluated earlier.

An enterprise security team denies inbound SSH and RDP from Internet sources across all production VNets but allows a tightly scoped management service. Application teams still manage HTTPS and database flows in their own NSGs. The central team uses staged deployment because a mistaken global deny has a much larger blast radius than one NSG rule.

Troubleshooting must check both layers. If a security admin Deny matched, adding an NSG Allow cannot fix the flow. Inspect VNet membership, deployed configuration, region, rule priority, and action. Microsoft documents service-specific exceptions and special handling for certain network-intent-policy services, and security admin rules do not universally apply to every private endpoint scenario. The takeaway is the evaluation chain: security admin rules first, then NSGs if the action semantics allow evaluation to continue.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Governance works best when priority ranges and ownership are documented. Reserve a high-priority band for emergency security controls, another for mandatory platform guardrails, and leave lower ranges for broader organization policy. Changes should be deployed first to a small network group, validated with test flows, and then expanded. Because deployment is eventually consistent, record the deployment state before concluding that a newly created rule failed.

Use effective policy analysis before changing workload NSGs. If the admin action is Deny, a local team cannot override it. If the action is Allow, the workload still needs an NSG allow. If the action is Always Allow, the local NSG cannot block that matching flow. These semantics support separation of duties, but they can surprise engineers who assume every “allow” means the same thing.

Network Watcher IP flow verify and NSG diagnostics for deterministic policy analysis

Architecture / traffic flow

flowchart LR
F[Known five-tuple] --> DIAG[IP flow verify / NSG diagnostics]
DIAG --> RULE[Effective NSG evaluation]
RULE -->|Allow| A[Allowed + matching rule]
RULE -->|Deny| D[Denied + matching rule]

Network Watcher diagnostic tools can answer whether Azure security policy should allow a specific flow before you spend time on packet capture. IP flow verify and NSG diagnostics simulate a source, destination, protocol, port, and direction and report whether the flow is allowed or denied plus the rule responsible for the decision.

This is powerful because NSGs can be attached to both subnets and NICs. Effective behavior may involve several rule sets, priorities, service tags, and augmented rules. Reading every rule manually is slower and more error-prone than asking Azure to evaluate the same five-tuple that the application is trying to use.

A practical workflow is policy first, routing second, packets third. Simulate the failing flow. If Azure says Denied, fix the identified security rule. If it says Allowed, inspect Next hop and effective routes. If both policy and path look correct, move to Connection troubleshoot, packet capture, flow logs, or application logs. This progression avoids using high-cost evidence collection for a simple rule-priority problem.

Suppose HTTPS works from one spoke but not another. NSG diagnostics shows a higher-priority deny matching the second spoke’s CIDR even though a broad allow exists lower in the list. The engineer corrects the source prefix, re-runs the diagnostic, and confirms Allowed before retesting the application. No packet capture was needed.

When using these tools, choose the correct NIC and direction, especially on multi-NIC VMs. Also remember stateful NSG behavior when modeling return traffic. Microsoft’s current Network Watcher guidance notes that NSG flow logs retire September 30, 2027 and recommends migration to virtual network flow logs. The takeaway: use deterministic policy simulation to identify the winning NSG rule, then escalate to routing and packet evidence only when policy is not the blocker.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

A good incident worksheet records the exact five-tuple, direction, source NIC, destination, expected route, and expected security policy. Run IP flow verify or NSG diagnostics using those exact values. Then run Next hop for the same destination. This produces a concise proof of both filtering and routing decisions before packet-level troubleshooting begins.

Simulation is not a substitute for telemetry. It tells you what Azure policy should decide at evaluation time, while flow logs and packet captures tell you what traffic actually occurred. An application may never send the packet you think it sends, or a host firewall may block it after Azure allows it. Use deterministic simulation to narrow the problem domain and observed telemetry to prove the remaining hypotheses.

Azure Firewall Policy rule collection groups and processing order

Architecture / traffic flow

flowchart TD
P[Packet] --> DNAT[DNAT processing]
DNAT -->|No match| NET[Network rules]
NET -->|No match| APP[Application rules]
APP -->|No match| DENY[Implicit deny]
DNAT -->|Match| OK[Translate + allow]
NET -->|Match| ACT[Collection action]
APP -->|Match| ACT

Firewall Policy organizes rules into rule collection groups, rule collections, and rules. The hierarchy makes large policies manageable, but engineers must understand both priority and rule-type processing. Collection-group priority alone does not erase the platform’s DNAT, network, and application-rule semantics.

For inbound publishing, DNAT rules are processed before network rules. If a DNAT rule matches, the firewall translates the destination and allows the translated flow without sending the same match through a later network-rule decision. Application rules are not applied to inbound connections, so inbound HTTP/S Layer-7 inspection belongs on a WAF-capable service rather than an application rule expectation.

For outbound traffic, network rules are evaluated before application rules. This creates a common policy-shadowing issue: a broad network allow can accept traffic before a restrictive FQDN application rule ever gets a chance to evaluate it. When an application rule appears ineffective, search for earlier network rules before changing the application collection.

Custom rule collection groups let organizations reserve priority bands for platform, security, and workload teams. A shared firewall might have high-priority groups for mandatory denies and DNAT governance, followed by infrastructure network rules and then workload application rules. Version-controlled policy and documented priority ranges reduce accidental collisions.

Troubleshooting starts by classifying the flow: inbound or outbound, NAT or non-NAT, network-rule eligible, or application-rule eligible. Then inspect Azure Firewall logs for the actual rule collection and action. If no expected application rule matches, check earlier network rules. If DNAT works but the application still fails, inspect translated destination reachability, NSGs, UDRs, and backend listening. The takeaway is to learn the processing pipeline first and then use collection-group priority to organize policy within that pipeline.

Operational checklist

  • Verify prerequisites and supported SKU/region behavior before deployment.
  • Validate effective routes, health state, logs, and return path after every policy change.
  • Test one controlled failure mode at a time so the failed layer is unambiguous.
  • Keep automation and intended state under version control.

Implementation depth and failure validation

Policy engineering should reserve documented priority ranges for central security, shared infrastructure, and workload teams. Keep DNAT publishing rules narrowly scoped to known Internet sources where possible, and avoid broad network allows that unintentionally supersede application-layer restrictions. Use Firewall Policy analytics and logs during rule cleanup so you can remove shadowed or unused rules rather than simply adding more exceptions.

When troubleshooting, write the flow as source, translated destination if any, protocol, port, and intended policy type. For inbound flows, inspect DNAT first. For outbound non-HTTP protocols, network rules are normally the relevant layer. For outbound HTTP/S FQDN control, confirm no earlier network rule already matched. Then correlate firewall logs with effective routes and backend NSGs. Processing order is the map that tells you where to look.
