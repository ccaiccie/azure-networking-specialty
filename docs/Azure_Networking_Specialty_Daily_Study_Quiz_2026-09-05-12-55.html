ExpressRoute Direct MACsec: encrypting the Direct physical handoff

Why it matters

ExpressRoute is private connectivity, but its routed traffic is not automatically encrypted simply because it avoids the public Internet. If your compliance boundary says the Ethernet handoff between your router and Microsoft must be cryptographically protected, ExpressRoute Direct MACsec is the control that addresses that specific boundary. It is not a substitute for application TLS and it is not an IPsec overlay. MACsec protects Ethernet frames on the physical Direct links, which means the operational evidence you use—secure-channel state, MACsec counters, CAK/CKN alignment, cipher choice—is different from the evidence you would use for VPN Gateway.

The most important operational design choice is to preserve the native Direct redundancy while adding encryption. ExpressRoute Direct exposes two physical links. Treat those links as separate change units. Enable or rotate one link, validate the MACsec secure channel and BGP, then change the second. If you modify both before validating either, a single bad key, cipher mismatch, SCI mismatch, or Key Vault access issue can remove both paths at once.

Architecture

At the bottom is the physical Ethernet cross-connect. MACsec establishes a secure channel between the customer edge and Microsoft Enterprise Edge. Above that, Azure private peering runs BGP. Above BGP, application traffic follows normal routing. This ordering explains a common symptom: the ExpressRoute port resource can show Succeeded while BGP is down, because Azure Resource Manager successfully accepted the configuration but the Layer-2 secure channel is not passing frames.

The key model uses a Connectivity Association Key and CKN. Microsoft’s workflow integrates the Azure side with Key Vault/managed identity. Cipher availability depends on Direct port speed; Microsoft documents XPN variants for high-speed Direct ports. Secure Channel Identifier requirements can vary with the router/MSEE combination. Those are not cosmetic settings: a mismatch prevents frames from decrypting and every higher layer disappears.

Prerequisites and implementation

Use this design only when you own ExpressRoute Direct ports; a normal provider-provisioned ExpressRoute circuit does not expose the Direct port MACsec configuration to you. Confirm both links are operational before adding encryption, verify Key Vault permissions/identity, choose a supported cipher for the Direct speed, and record the current BGP state so you know what “good” looked like before the change.

az network express-route port show \
  --resource-group <rg> \
  --name <expressroute-direct-port> \
  --output jsonc

az network express-route port link list \
  --resource-group <rg> \
  --port-name <expressroute-direct-port> \
  --output table

# Inspect the exact current MACsec update parameters before applying secrets.
az network express-route port link update --help

The MACsec update command is the feature-specific Azure CLI surface. Do not paste CAK/CKN values into a generic script or invent flags: prepare the Key Vault-backed values using the current Microsoft procedure, then use the parameters shown by the installed CLI version. Apply link 1, verify, then apply link 2.

Packet path and failure boundary

Consider a packet from on-premises 10.10.10.10 to an Azure VM at 10.50.10.20. The CE routes it toward the private peering. Before the IP packet can reach the MSEE BGP/routing layer, its Ethernet frame must be successfully encrypted and accepted by the remote MACsec secure channel. If MACsec fails, there is no IP packet for BGP or Azure to process. That is why a simultaneous BGP drop immediately after MACsec change is strong evidence to inspect Layer 2 first rather than altering route advertisements.

VPN Gateway custom IPsec/IKE policy: make negotiation deterministic

Why it matters

A site-to-site VPN is only as interoperable as the proposal set shared by both peers. Azure defaults are intentionally broad enough for common devices, but real enterprises often need a specific cryptographic baseline: AES-256 instead of older ciphers, a particular DH group, PFS, or explicit SA lifetimes. A custom policy makes those requirements visible and deterministic. It also makes failure analysis easier because you know exactly what Azure is offering rather than guessing which default proposal was selected.

The second reason to understand custom policy is traffic-selector interoperability. Route-based Azure VPN gateways normally support broad selectors, but some third-party devices insist on policy-style prefix pairs. Azure supports policy-based traffic selectors for this interoperability case; when you enable that behavior, the custom IPsec/IKE policy is part of the design. An IKE SA can be healthy while no usable CHILD_SA exists for the application prefixes, so tunnel-state and data-state must be verified separately.

Architecture

IKE Phase 1 is the secure control relationship. The peers authenticate, agree on IKE encryption/integrity and DH, and create an IKE SA. Phase 2/CHILD_SA then negotiates IPsec transforms, PFS and traffic selectors that protect actual user packets. A mismatch in the first set produces NotConnected. A mismatch in selectors can produce a more confusing condition: the IKE relationship is up, but traffic for a particular source/destination pair never gets an IPsec SA.

SA lifetime is also operationally relevant. Both devices rekey periodically; if the peers disagree badly about rekey behavior or one side has a software defect, intermittent drops can appear at lifetime boundaries even though the initial tunnel looked perfect.

Prerequisites and implementation

Start with a route-based VPN Gateway, local network gateway, and connection. Collect the third-party firewall’s supported proposal matrix before changing Azure. If NAT is present, write down the prefixes the peers actually see after translation; those may differ from the original application CIDRs and therefore affect selectors.

az network vpn-connection ipsec-policy add \
  --resource-group <rg> \
  --connection-name <s2s-connection> \
  --dh-group DHGroup14 \
  --ike-encryption AES256 \
  --ike-integrity SHA384 \
  --ipsec-encryption AES256 \
  --ipsec-integrity SHA256 \
  --pfs-group PFS2048 \
  --sa-lifetime 27000 \
  --sa-max-size 102400000

az network vpn-connection ipsec-policy list \
  -g <rg> --connection-name <s2s-connection> -o table

Configure the corresponding proposal on the remote firewall in the same change window. If you are using policy-based traffic selectors, also enable/configure them according to the Microsoft procedure and the exact prefix pairs the peer expects.

What happens to one packet

A branch host 10.20.1.10 sends to Azure 10.50.1.20. Routing sends the packet to the branch firewall. The firewall finds a matching CHILD_SA selector, encrypts the packet, and sends ESP/IPsec to Azure VPN Gateway. Azure decrypts it and routes the original packet into the VNet. The return packet must match the reverse selector and SA. If IKE is up but that prefix pair is absent from Phase 2, the application traffic is discarded or never encrypted even though the connection appears administratively healthy.

Verification

az network vpn-connection show -g <rg> -n <s2s-connection> \
  --query "{status:connectionStatus,egress:egressBytesTransferred,ingress:ingressBytesTransferred}" -o json
Representative successful state:
{
  "status": "Connected",
  "egress": 1843200,
  "ingress": 2050048
}

IPsec SA: UP
Local selector: 10.20.0.0/16
Remote selector: 10.50.0.0/16
The combination of Connected + increasing bytes + matching peer SAs proves more than a portal green check.

Troubleshooting

Failure A — proposal mismatch:
connectionStatus: NotConnected

Compare IKE encryption/integrity, DH and authentication. Failure B — selector mismatch:

Do not change IKE parameters when Phase 1 is already healthy. Correct selectors/NAT representation or routing so the intended flow maps to a CHILD_SA.

ExpressRoute Metro: survive loss of one metro peering location

Why it matters

Standard ExpressRoute provides redundant logical connections, but those connections are still associated with a peering location. If that entire facility or peering location becomes isolated, both normal circuit paths can be affected. ExpressRoute Metro expands the Microsoft-side failure domain by dual-homing connectivity across two distinct ExpressRoute peering locations within the same metropolitan area.

The subtle point is that Azure cannot manufacture end-to-end diversity on your behalf. Metro gives two Microsoft peering sites, but the carrier path from your routers to those sites must also be physically and logically diverse. If both customer access links share the same fiber entrance, carrier aggregation device or WAN core, your actual business failure domain can still be much larger than the Azure diagram suggests.

Architecture

Each Metro side terminates at a different Microsoft peering location. Your CE routers exchange BGP routes across both. You can run both paths active, or prefer one with normal BGP attributes while keeping the other eligible. The core design test is not “does the circuit show Provisioned?” but “if one entire peering-site path disappears, does the surviving path carry all required routes and production load?”

Metro can be delivered through an ExpressRoute provider or ExpressRoute Direct depending on the location/design. Migration from an existing standard circuit is best treated as parallel build and controlled traffic movement: create Metro, establish peering, attach workloads/gateways, compare routing, move traffic, then retire the old circuit after rollback time has passed.

Prerequisites and implementation

Confirm that the desired city supports Metro and that your provider supports the required peering locations. Obtain written path-diversity information from the provider when resilience is the business objective. Plan enough bandwidth on either surviving path to carry the critical load by itself.

az network express-route list-service-providers -o table

az network express-route show \
  -g <rg> -n <metro-circuit> -o jsonc

az network express-route peering list \
  -g <rg> --circuit-name <metro-circuit> -o table

Create the Metro circuit/Direct resource using the normal ExpressRoute workflow with a Metro-capable location. Then configure private peering and gateway/circuit connections the same way you would for other ExpressRoute designs.

BGP policy and capacity

If both paths advertise identical prefixes, BGP best-path policy selects which route is installed. A primary/backup design can use the customer side’s normal local-preference/AS-path policy; an active/active design should be tested for hashing and return-path behavior. Do not overload one path during a failure test: a routing failover that moves 20 Gbps onto a 10-Gbps surviving link is technically converged but operationally failed.

Verification

az network express-route show -g <rg> -n <metro-circuit> \
  --query "{providerState:serviceProviderProvisioningState,circuitState:circuitProvisioningState}" -o json
{ "providerState":"Provisioned", "circuitState":"Enabled" }
CE-A: BGP Established, Azure prefixes present
CE-B: BGP Established, same critical Azure prefixes present
Then withdraw/shut one side in a maintenance test and confirm applications continue while the surviving CE still carries the expected prefixes.

Troubleshooting

Representative failure:
Azure circuit: providerState=Provisioned, circuitState=Enabled
CE-A BGP: Established
CE-B BGP: Idle
Interpretation: the Azure circuit resource exists, but one Metro path is not operational. Check provider cross-connect/VLAN/BGP details for the B side. Do not conclude Metro resiliency is working until both independent BGP paths are up and separately tested.

IPsec over ExpressRoute with Virtual WAN: separate underlay from encrypted overlay

Why it matters

ExpressRoute provides private transport but may not meet a requirement for Layer-3 encryption. Virtual WAN can combine ExpressRoute reachability with an IPsec VPN overlay so traffic travels over Microsoft/private connectivity while remaining encrypted between VPN peers. This is valuable when governance says “private transport is not enough; routed payloads must also be encrypted.”

The design becomes much easier to reason about if you stop treating it as one connection. It is three stages: ExpressRoute underlay reachability, IPsec overlay establishment, and Virtual WAN routing after decryption. Each stage has different commands and different failure output.

Architecture

The on-premises VPN device must reach the Azure/Virtual WAN VPN peer address using the ExpressRoute underlay. IKE packets then form the encrypted control relationship, followed by IPsec CHILD_SAs. Once Azure decrypts the application packet, the Virtual WAN hub routes it toward connected VNets/branches according to hub route tables and propagation/association policy.

This means connectionStatus=NotConnected with no underlay route should never be debugged as a cryptographic problem first. Conversely, an established IPsec SA plus missing workload route is a post-decryption routing problem, not an IKE problem.

Prerequisites and implementation

You need a Virtual WAN hub with ExpressRoute and VPN gateways/connections, an ExpressRoute path that advertises/reaches the VPN peer addresses, and compatible IPsec policy on the remote device. The current Azure CLI uses the Virtual WAN extension for the site-to-site VPN gateway connection policy.

az network vpn-gateway connection show \
  -g <rg> --gateway-name <vwan-vpn-gateway> \
  -n <connection> -o jsonc

az network vpn-gateway connection ipsec-policy add \
  -g <rg> --gateway-name <vwan-vpn-gateway> \
  --connection-name <connection> \
  --dh-group DHGroup14 \
  --ike-encryption AES256 \
  --ike-integrity SHA256 \
  --ipsec-encryption AES256 \
  --ipsec-integrity SHA256 \
  --pfs-group PFS2048 \
  --sa-lifetime 27000 \
  --sa-max-size 102400000

Packet flow

A branch workload sends toward an Azure spoke prefix. Its router resolves the VPN peer through ExpressRoute, not the public Internet. The VPN appliance encapsulates/encrypts the packet. The encrypted packet crosses ExpressRoute to the Virtual WAN VPN endpoint. Azure decrypts it, then the original packet enters the virtual hub route table and is forwarded to the spoke. The return flow repeats that process in reverse. If the spoke route is associated to the wrong hub table, IPsec can remain perfectly healthy while application traffic fails after decryption.

Verification

az network vpn-gateway connection ipsec-policy list \
  -g <rg> --gateway-name <vwan-vpn-gateway> \
  --connection-name <connection> -o table

az network vpn-gateway connection show \
  -g <rg> --gateway-name <vwan-vpn-gateway> -n <connection> \
  --query "{status:connectionStatus,provisioning:provisioningState}" -o json
{ "status":"Connected", "provisioning":"Succeeded" }
On-premises VPN: IKE SA UP, IPsec SA UP
Underlay route to Azure VPN peer: via ExpressRoute
Virtual WAN effective route to spoke prefix: present
All three stages must be green.

Troubleshooting

Underlay failure:
connectionStatus: NotConnected
On-prem route lookup for VPN peer: no route
Fix ExpressRoute/BGP advertisement first. Overlay failure:
Underlay ping/reachability: OK
connectionStatus: NotConnected
Peer log: proposal mismatch
Fix IKE/IPsec parameters. Post-decryption failure:
connectionStatus: Connected
IPsec counters increasing
Virtual WAN effective route to 10.60.0.0/16: absent
Fix hub route-table association/propagation or destination connectivity.

VNet peering gateway transit: centralize hybrid connectivity without assuming transitive peering

Why it matters

A hub VNet commonly hosts the organization’s ExpressRoute or VPN gateway. Gateway transit lets peered spoke VNets use that hub gateway instead of deploying a gateway in every spoke. It reduces cost and centralizes hybrid connectivity, but the feature is frequently misunderstood because it does not make VNet peering generically transitive.

Two separate peering flags create the relationship: the hub advertises its gateway with allowGatewayTransit; the spoke consumes it with useRemoteGateways. If either direction is wrong, the peering can still show Connected while the spoke has no on-premises routes.

Architecture

The hub’s gateway learns routes from on-premises through BGP/static VPN configuration. Azure makes those routes available to eligible peered spokes that set useRemoteGateways. On a spoke NIC, the effective route table shows those remote prefixes with next hop type VirtualNetworkGateway. That effective table is more meaningful than simply looking at the peering resource because it proves what the workload NIC will actually use.

Gateway transit only shares the gateway. Spoke A is not automatically transitively peered to Spoke B. If you need spoke-to-spoke through an NVA, Azure Firewall, Virtual WAN or direct peering, design that separately.

Prerequisites and implementation

The hub must already contain a supported VPN or ExpressRoute gateway. Hub and spoke address spaces cannot overlap. Create/verify peering in both directions, then set the flags on the correct object.

az network vnet peering update \
  -g <rg> --vnet-name <hub-vnet> \
  -n <hub-to-spoke> \
  --set allowGatewayTransit=true

az network vnet peering update \
  -g <rg> --vnet-name <spoke-vnet> \
  -n <spoke-to-hub> \
  --set useRemoteGateways=true

Route behavior

Suppose on-premises advertises 10.200.0.0/16 to the hub gateway. A spoke VM at 10.50.1.10 should see 10.200.0.0/16 in its effective route table with VirtualNetworkGateway as next hop. If you also attach a UDR for the same prefix to an NVA, route-selection rules may change the actual next hop. Gateway transit does not override more specific or higher-precedence user routes.

Verification

az network vnet peering show -g <rg> --vnet-name <hub-vnet> -n <hub-to-spoke> \
  --query "{state:peeringState,allowGatewayTransit:allowGatewayTransit}" -o json
az network vnet peering show -g <rg> --vnet-name <spoke-vnet> -n <spoke-to-hub> \
  --query "{state:peeringState,useRemoteGateways:useRemoteGateways}" -o json
az network nic show-effective-route-table -g <rg> -n <spoke-nic> -o table
{ "state":"Connected", "allowGatewayTransit":true }
{ "state":"Connected", "useRemoteGateways":true }

Source          State   Address Prefix   Next Hop Type
VirtualNetwork  Active  10.200.0.0/16    VirtualNetworkGateway
The effective route is the decisive proof for the spoke workload.

Troubleshooting

Failure:
PeeringState: Connected
useRemoteGateways: false
Effective route table: no 10.200.0.0/16 entry
Correct the spoke-side flag. If useRemoteGateways=true but the route is still missing, inspect the hub gateway’s learned routes/BGP advertisements. Do not add an NSG rule to solve a missing route. If the route is present but the packet fails, then use IP Flow Verify/NSG and the on-premises return route as the next layers.

Standard Load Balancer HA Ports: scale NVAs without enumerating every port

Why it matters

A firewall or other NVA can receive arbitrary application traffic, so a traditional load-balancing rule per TCP/UDP port is not workable. Standard Load Balancer HA Ports uses one all-protocol/all-port rule to distribute flows to healthy NVA backends. In Azure CLI, that rule is represented with protocol All, frontend port 0 and backend port 0.

HA Ports solves flow distribution, not stateful-firewall symmetry. If a session enters NVA-1 and the return path bypasses the load balancer or lands on NVA-2, the firewall can still drop the flow. Routing, NVA clustering/session synchronization and floating-IP/direct-return behavior are separate parts of the design.

Architecture

A UDR can point spoke/segment traffic at the internal load balancer frontend. The load balancer hashes new flows across backend-pool members that pass the health probe. The NVA sees the traffic, applies policy and forwards it onward. Because the health probe directly controls eligibility, the probe should test a condition that actually represents forwarding readiness—not merely whether the VM operating system is alive.

For stateful appliances, design the return path explicitly. Depending on the vendor pattern, that might use the same ILB frontend, symmetric UDRs, appliance clustering/session sync, or vendor-specific guidance.

Prerequisites and implementation

Create an internal Standard Load Balancer with a frontend IP, backend pool containing the NVA instances, and a health probe. Then create the HA Ports rule.

az network lb rule create \
  -g <rg> --lb-name <internal-lb> \
  -n ha-ports \
  --protocol All \
  --frontend-port 0 \
  --backend-port 0 \
  --frontend-ip-name <frontend-config> \
  --backend-pool-name <nva-pool> \
  --probe-name <health-probe>

az network lb rule show -g <rg> --lb-name <internal-lb> -n ha-ports -o jsonc

Traffic example

A spoke VM opens TCP/443 to a service across the firewall and also sends UDP/53 to a resolver. The UDR next hop is the ILB frontend. The same HA Ports rule can select an NVA for both flows because it is not restricted to one protocol or port. The load balancer maintains per-flow hashing; it does not proxy the application protocol or maintain firewall session awareness.

Verification

{
  "protocol": "All",
  "frontendPort": 0,
  "backendPort": 0,
  "provisioningState": "Succeeded"
}
Backend health:
nva01  Healthy
nva02  Healthy
Generate at least two protocol types and confirm NVA session/counter data. Also validate the reverse direction follows the intended inspection path.

Troubleshooting

Failure A — backend removed:
Rule: Succeeded
nva01: Healthy
nva02: Unhealthy
The load balancer is correctly excluding nva02. Fix the probe listener/appliance health. Failure B — session resets although both are healthy:
Forward flow observed on nva01
Return flow observed on nva02 / bypass path
This is not an HA Ports configuration error. Fix route symmetry or use the NVA vendor’s supported state/session design.

Azure Public DNS DNSSEC: build and validate the chain of trust

Why it matters

Traditional DNS answers can be spoofed or altered because the protocol does not inherently authenticate record data. DNSSEC adds signatures that let validating recursive resolvers determine whether a record set is authentic and unchanged. It does not encrypt DNS queries and it does not hide names; it provides integrity/authenticity.

The operational risk is that DNSSEC can turn a delegation mistake into an outage for every validating resolver. A signed child zone with a wrong DS record at the parent may answer authoritative queries perfectly, yet validating clients receive SERVFAIL because the cryptographic chain is broken. DNSSEC therefore requires coordination between the Azure-hosted zone and the registrar/parent zone.

Architecture

The Azure DNS child zone publishes DNSKEY records and RRSIG signatures over record sets. The parent zone publishes a DS record derived from the child key. A validating resolver begins with an existing trust anchor and walks parent-to-child until it validates the requested record. The AD flag in a response from a validating recursive resolver indicates Authenticated Data.

Key rollover deserves change control: the parent DS must continue to correspond to a valid child key during transitions. Removing the old key before the parent DS is safely updated can make the zone bogus.

Prerequisites and implementation

You need an Azure Public DNS zone and the ability to update DS data at the registrar/parent. DNSSEC command surfaces can change, so begin by inspecting the current Azure CLI and Microsoft procedure rather than using a stale command copied from an old blog.

az network dns zone show -g <rg> -n <zone-name> -o jsonc
az network dns zone --help

# Enable/sign using the current Microsoft-supported DNSSEC workflow.
# Retrieve the resulting DS material and publish it at the parent registrar.

How validation actually fails

A non-validating resolver may still return an A record even when DNSSEC is broken. That can mislead operators into thinking DNS is healthy. Test with a known validating resolver and compare a normal query with a query that disables checking (+cdflag). If the normal query SERVFAILs but the checking-disabled query returns data, the transport and authoritative server are reachable; validation is what failed.

Verification

$ dig +dnssec www.example.com A @1.1.1.1
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 1
www.example.com. 300 IN A 203.0.113.20

$ dig +dnssec example.com DNSKEY
;; ANSWER: DNSKEY ... RRSIG ...

$ dig +dnssec example.com DS
;; parent contains the expected DS
The ad flag plus a coherent DS/DNSKEY relationship is the important evidence.

Troubleshooting

$ dig www.example.com A @1.1.1.1
status: SERVFAIL

$ dig +cdflag +dnssec www.example.com A @1.1.1.1
status: NOERROR
www.example.com. 300 IN A 203.0.113.20
Interpretation: record data is reachable, but validation fails. Compare the DS in the parent with the active Azure DNSKEY. If a rollover just occurred, confirm the parent was updated and caches/TTL timing were respected. Do not “fix” this by changing the A record; the A record is not the failing layer.

Front Door Premium Private Link origins: public edge without public origin exposure

Why it matters

Front Door gives a globally distributed public entry point, WAF and HTTP routing. Many organizations still do not want the origin application reachable directly from the public Internet. Front Door Premium Private Link separates those two requirements: users reach Front Door publicly, while Front Door reaches the supported origin through an Azure Private Link relationship.

This design closes a common bypass path. If the origin no longer accepts public traffic, a client cannot skip Front Door/WAF and connect straight to the backend. But Private Link only changes the network path; it does not remove HTTP requirements such as the correct host header, TLS certificate and health endpoint.

Architecture

The browser resolves/connects to Front Door’s public anycast endpoint. Front Door terminates TLS, evaluates WAF/routing and selects an origin. For a Private-Link-enabled origin, Front Door establishes an Azure-managed private endpoint relationship to the backend resource/subresource in a chosen region. The backend owner must approve the connection request (unless an appropriate auto-approval mechanism applies). Front Door health probes then use that private path.

Because Front Door is the HTTP client to the origin, origin-host-header affects how the backend virtual host and certificate are evaluated. A perfectly approved private endpoint can still show Unhealthy if the host header/path/certificate is wrong.

Prerequisites and implementation

Use Front Door Premium, create an origin group with a meaningful health probe, and select a supported Private Link origin resource/subresource. The example below creates the group and origin.

az afd origin-group create \
  -g <rg> --profile-name <afd-profile> \
  --origin-group-name <origin-group> \
  --probe-request-type GET \
  --probe-protocol Https \
  --probe-path /health \
  --probe-interval-in-seconds 60

az afd origin create \
  --resource-group <rg> \
  --profile-name <afd-profile> \
  --origin-group-name <origin-group> \
  --origin-name <origin-name> \
  --host-name <origin-fqdn> \
  --origin-host-header <origin-fqdn> \
  --https-port 443 \
  --enable-private-link true \
  --private-link-location <region> \
  --private-link-resource <origin-resource-id> \
  --private-link-sub-resource-type <subresource>

Approve the resulting Private Endpoint request on the origin resource. Only after approval should you expect the Front Door origin health probe to become meaningful.

Verification

az afd origin show -g <rg> --profile-name <afd-profile> \
  --origin-group-name <origin-group> -n <origin-name> -o jsonc
{
  "enabledState": "Enabled",
  "provisioningState": "Succeeded",
  "sharedPrivateLinkResource": { "status": "Approved" }
}
Front Door origin health: Healthy
Then make a real request through the Front Door endpoint and confirm the origin can no longer be reached through any unintended public path.

Troubleshooting

Pending:
sharedPrivateLinkResource.status: Pending
Origin health: Unhealthy
Approve the private endpoint request. Approved but unhealthy:
sharedPrivateLinkResource.status: Approved
Origin health: Unhealthy
Probe response: 403 / TLS hostname mismatch
Connectivity exists; now inspect health path, origin host header, certificate/SNI and backend access policy. Do not recreate the private endpoint simply because the HTTP probe fails.

Azure Firewall Premium TLS inspection: PKI becomes part of the data path

Why it matters

Most modern application traffic is encrypted. A firewall that does not decrypt HTTPS can still enforce destination/FQDN policy, but it cannot inspect the encrypted payload with content-aware security controls. Azure Firewall Premium TLS inspection creates a controlled man-in-the-middle design: the firewall terminates the client TLS session, inspects decrypted content, and then establishes a separate TLS connection to the actual server.

The security benefit comes with a new dependency: client trust. The firewall generates a substitute leaf certificate for the requested site and signs it with the organization’s inspection CA. If clients do not trust that CA chain, every inspected HTTPS connection fails with a certificate error even though routing and TCP/443 are working.

Architecture

Client → Firewall is TLS session 1. Firewall → destination is TLS session 2. The client sees a certificate whose subject matches the requested site but whose issuer is the inspection CA. The firewall separately validates the real destination certificate. Application rules decide which destinations are allowed and whether TLS termination/inspection is enabled. IDPS can then evaluate decrypted traffic where applicable.

Do not enable inspection indiscriminately. Certificate-pinned applications, mutual TLS, sensitive categories or vendor applications may require bypass. Design explicit inclusion/exclusion policy and a CA lifecycle process rather than treating the certificate as a one-time setup task.

Prerequisites and implementation

Use Azure Firewall Premium with Firewall Policy. Prepare the supported certificate/Key Vault design, distribute the trust chain to managed clients, and apply TLS inspection to the intended application rules. The exact CA binding and rule schema should follow the current Firewall Policy documentation/CLI/ARM provider.

az network firewall policy show \
  -g <rg> -n <firewall-policy> -o jsonc

az network firewall policy rule-collection-group list \
  -g <rg> --policy-name <firewall-policy> -o table

# Confirm Premium tier, TLS inspection/certificate configuration,
# then enable terminateTLS only on the intended application rules
# using the current Firewall Policy CLI/ARM/Terraform schema.

Client and server certificate behavior

When inspection is healthy, a browser still sees the destination hostname, but the issuer changes to your inspection CA. That is the easiest user-side proof that decryption is actually occurring. The firewall must also trust/validate the real server side; a broken remote certificate can fail at the second TLS session even when client trust is correct.

Verification

$ curl -Iv https://www.example.com
* SSL connection using TLSv1.3
* Server certificate:
*   subject: CN=www.example.com
*   issuer: CN=Corp-Azure-Firewall-Inspection-CA
< HTTP/2 200

Azure Firewall application/IDPS logs:
Action=Allow; FQDN=www.example.com; TLS inspection applied
The changed issuer plus successful HTTP response proves the client trusted the inspection certificate and the firewall completed the server-side session.

Troubleshooting

Client trust failure:
curl: (60) SSL certificate problem: unable to get local issuer certificate
Do not change UDRs: the client reached the firewall. Fix CA distribution/trust. Remote TLS failure:
Client trusts inspection CA
Firewall log: TLS upstream certificate validation failed
Inspect destination certificate chain/SNI and server-side reachability. Only one application breaks: investigate certificate pinning or mutual-TLS requirements and add a documented bypass if appropriate.

Lesson 10 · Monitoring

VNet Flow Logs and Traffic Analytics: prove who talked to whom

Why it matters

When troubleshooting or auditing a network, you frequently need evidence of communication rather than full packet payloads: source, destination, port/protocol, direction and flow state. VNet flow logs provide that Layer-3/4 evidence at virtual-network scope. Traffic Analytics can process the records into Log Analytics for pattern discovery, traffic matrices and operational dashboards.

This telemetry is complementary to packet capture. Flow logs answer “did a flow occur, between what endpoints, on what port, with what direction/state?” They cannot show a TLS handshake, HTTP header, retransmission sequence or payload. Knowing that boundary prevents overusing flow logs when packet-level proof is required.

Architecture

The VNet is the monitored resource. The flow-log resource writes raw data to a storage account. When Traffic Analytics is enabled, the flow-log configuration references a Log Analytics workspace and Azure periodically processes records into analytics. Because these are separate stages, you can have raw records in storage while the analytics workspace is delayed or misconfigured.

Design storage retention/cost intentionally. High-flow environments can generate substantial telemetry. Use Traffic Analytics interval appropriate to operational needs rather than assuming near-real-time packet visibility.

Prerequisites and implementation

az monitor log-analytics workspace create \
  -g <rg> -n <workspace> -l <region>

az network watcher flow-log create \
  --location <region> \
  --resource-group <rg> \
  --name <flow-log-name> \
  --vnet <vnet-name> \
  --storage-account <storage-account> \
  --traffic-analytics true \
  --workspace <workspace> \
  --interval 10

If storage or workspace is in another resource group, use the documented resource ID form. The flow-log object can be managed separately from the workload VNet lifecycle.

Operational use

Suppose the firewall reports bursts from 10.50.1.20 to multiple Internet IPs. VNet flow logs can corroborate whether the VM actually generated those flows, the destination ports involved and the time pattern. If you then need to know whether the burst was repeated SYN retransmissions, successful TLS sessions or malformed packets, move to packet capture/firewall telemetry rather than expecting flow logs to answer packet-level questions.

Verification

az network watcher flow-log show \
  --location <region> -g <rg> -n <flow-log-name> -o jsonc
{
  "enabled": true,
  "provisioningState": "Succeeded",
  "flowAnalyticsConfiguration": {
    "networkWatcherFlowAnalyticsConfiguration": {
      "enabled": true,
      "trafficAnalyticsInterval": 10
    }
  }
}
Storage: new flow-log blobs present
Traffic Analytics: records visible after processing interval

Troubleshooting

Control plane good, no raw data:
enabled=true
provisioningState=Succeeded
Storage container: no new flow-log blobs
Check VNet association, storage access/compatibility and whether there is test traffic. Raw data exists, analytics empty:
Storage blobs: present
Traffic Analytics workspace: no new records
Focus on workspace ID/configuration and analytics ingestion interval; do not rebuild the VNet flow-log capture if raw records prove capture is already working.

Lesson 11 · Security troubleshooting

Network Watcher IP Flow Verify: turn NSG guessing into a deterministic decision

Why it matters

Azure effective security can combine NIC NSGs, subnet NSGs, priorities, default rules, service tags and direction. When an application fails, manually reading every rule is slow and error-prone. IP Flow Verify evaluates one exact flow tuple in the context of a VM and tells you whether Azure NSG policy would allow or deny it and which rule produced the result.

Its power comes from its narrow scope. It does not send a packet. Therefore an Allow result proves only the Azure NSG decision. It does not prove a route exists, a load balancer selected a healthy backend, the guest OS firewall allows the connection, or an application is listening.

Architecture

You supply direction, protocol, local IP/port and remote IP/port for a target VM. Network Watcher evaluates the effective NSG policy and returns an access decision plus rule name. That makes IP Flow Verify the fastest way to answer “which NSG rule is blocking this exact flow?”

Use the exact tuple the application uses. Testing remote port 443 when the real flow is to 8443 or testing the wrong source address can give a correct answer to the wrong question. For outbound traffic, swap the flow direction and local/remote roles accordingly.

Prerequisites and implementation

Network Watcher must be available in the VM’s region and you need the target VM/resource context. No configuration change is required; this is an active diagnostic query against Azure’s effective policy.

az network watcher test-ip-flow \
  -g <rg> --vm <vm-name> \
  --direction Inbound \
  --protocol TCP \
  --local <vm-private-ip>:443 \
  --remote <client-ip>:50000

az network nic show-effective-nsg \
  -g <rg> -n <vm-nic>

Verification

{
  "access": "Allow",
  "ruleName": "securityRules/Allow-Https"
}
If this is the intended rule, stop editing NSGs. Move to an actual connectivity test and then routing, listener or application evidence.

Troubleshooting workflow

Start with the user’s exact failed tuple. If IP Flow Verify returns Deny, fix the named NSG rule or rule-priority logic and rerun the same tuple. If it returns Allow, the NSG layer has been cleared from suspicion.

Deny example:
{
  "access": "Deny",
  "ruleName": "defaultSecurityRules/DenyAllInBound"
}
No custom higher-priority rule matched. Create/correct the intended inbound rule. Allow but application fails:
IP Flow Verify: Allow / Allow-Https
nc -vz 10.50.1.20 443: timeout
Now inspect effective routes, load balancer, guest firewall and listener. Running IP Flow Verify repeatedly will not diagnose those layers.

Pair it with route evidence

az network nic show-effective-route-table -g <rg> -n <vm-nic> -o table

If NSG says Allow but the destination prefix has an unexpected next hop, you now have a routing problem with objective evidence. This two-command sequence—IP Flow Verify plus effective routes—separates the two most common Azure policy layers quickly.

Lesson 12 · Private service access

Azure Private Link Service: publish your own service through consumer private endpoints

Why it matters

Private Endpoint is commonly associated with consuming Azure PaaS privately. Private Link Service is the provider-side counterpart: it lets you publish your own application behind a Standard Load Balancer so consumers can create private endpoints in their VNets without peering their networks to yours and without exposing your provider VNet directly.

This changes the trust model. Consumers get a private IP in their own VNet. The provider retains approval control over connection requests. Address-space overlap between provider and consumer is less problematic than with VNet peering because the consumer does not receive a route to the provider VNet; it connects to a Private Link endpoint/service abstraction.

Architecture

Provider: application backends → Standard Load Balancer backend pool/frontend → Private Link Service. Consumer: private endpoint NIC with a consumer-VNet IP → Private Link → provider service. The provider can manually approve endpoint connections or configure permitted auto-approval scenarios.

DNS is not automatically the same thing as connectivity. A consumer application usually uses a service FQDN; that name must resolve to the consumer private endpoint IP. If it still resolves to a public address, Private Link can be perfectly healthy while the application completely bypasses it.

Prerequisites and implementation

The provider subnet must disable Private Link Service network policies. The provider needs a Standard Load Balancer frontend backed by the application. Then create the Private Link Service and a consumer private endpoint.

az network vnet subnet update \
  -g <rg> --vnet-name <provider-vnet> \
  -n <provider-subnet> \
  --private-link-service-network-policies Disabled

az network private-link-service create \
  -g <rg> -n <pls-name> \
  --vnet-name <provider-vnet> \
  --subnet <provider-subnet> \
  --lb-name <standard-lb> \
  --lb-frontend-ip-configs <frontend-config> \
  --location <region>

PLS_ID=$(az network private-link-service show -g <rg> -n <pls-name> --query id -o tsv)

az network private-endpoint create \
  -g <consumer-rg> -n <private-endpoint> \
  --vnet-name <consumer-vnet> \
  --subnet <consumer-subnet> \
  --private-connection-resource-id "$PLS_ID" \
  --connection-name <connection-name> \
  --manual-request false

Connection approval and source addresses

The service-provider team should treat endpoint approval as an access-control workflow. A consumer request in Pending state should not be assumed malicious or broken; it is waiting for approval. Once Approved, the endpoint is usable subject to DNS/application controls. Also understand the provider-side source-address behavior documented for Private Link Service, especially if the application/firewall expects to log or authorize original consumer addresses.

Verification

az network private-link-service show -g <rg> -n <pls-name> -o jsonc
az network private-link-service connection list -g <rg> --name <pls-name> -o table
az network private-endpoint show -g <consumer-rg> -n <private-endpoint> -o jsonc
Private Link Service provisioningState: Succeeded
Connection status: Approved
Private Endpoint provisioningState: Succeeded
Private Endpoint NIC IP: 10.50.1.4

Consumer DNS:
app.internal.example -> 10.50.1.4
Successful private DNS resolution is part of end-to-end verification, not an optional afterthought.

Troubleshooting

Pending connection:
Connection status: Pending
Approve the endpoint on the provider side. Approved but wrong path:
Connection status: Approved
nslookup app.internal.example -> 203.0.113.50
Private Link is ready, but DNS sends the application somewhere else. Fix private DNS/conditional forwarding. DNS correct but application fails:
app.internal.example -> 10.50.1.4
TCP connect timeout
Now inspect Standard Load Balancer/backend health and provider application policy rather than rebuilding the private endpoint.
Primary: Private Link Service overview · CLI: Create Private Link Service
