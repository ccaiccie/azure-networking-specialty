ExpressRoute IPv6 private peering: dual-stack BGP without treating IPv6 as an afterthought

Why it matters

IPv6 on ExpressRoute private peering is not a separate transport service; it is an additional address family carried across the same private peering relationship. That distinction matters because teams often design an IPv4 ExpressRoute circuit correctly and then bolt IPv6 on later without planning peer subnets, gateway support, VNet IPv6 prefixes, route advertisement, or monitoring. The result is a circuit that looks healthy in the portal while IPv6 traffic has no usable end-to-end route. A dual-stack design should therefore treat IPv4 and IPv6 as parallel forwarding planes with shared physical redundancy but separate BGP prefixes, next hops, and failure evidence.

Architecture

Azure private peering uses two redundant BGP sessions, one on each ExpressRoute link. Microsoft documents /30 peer subnets for IPv4 and /126 peer subnets for IPv6. On each subnet, the customer router uses the first usable address and Microsoft uses the second usable address. The same VLAN ID and customer ASN identify the peering, but the address-family state is independent enough that IPv4 can be established while IPv6 is misconfigured. The VNet side also needs IPv6-capable addressing and an ExpressRoute virtual network gateway configuration that supports the intended IPv6 path. Route learning should be inspected per address family rather than inferred from the green state of the circuit resource.

A useful mental model is physical link → private-peering VLAN → IPv4 and IPv6 BGP address families → ExpressRoute gateway/FastPath where applicable → dual-stack VNet subnets and NICs. The control plane exchanges prefixes; the data plane forwards packets based on the installed route for each family. If an IPv6 application fails while IPv4 works, focus on the IPv6 peer subnet, BGP advertisements, VNet IPv6 prefix, guest operating-system route, and security policy before touching the working IPv4 configuration.

Prerequisites and implementation

Start with a provisioned ExpressRoute circuit and confirm both physical links and existing private peering are healthy. Reserve two non-overlapping /126 networks for the IPv6 peer links; these are infrastructure addresses and must not be carved from the workload VNet prefixes. Confirm the customer ASN is not Azure-reserved and that the router supports MP-BGP for IPv6. On the Azure side, add IPv6 prefixes to the VNet/subnets that need dual-stack connectivity and verify the gateway and target services support IPv6. Document which on-premises IPv6 aggregates will be advertised and which Azure prefixes are expected back so verification has a concrete route list rather than a vague “IPv6 enabled” target.

Implementation
# Inspect the existing private peering before adding IPv6.
az network express-route peering show \
  -g <resource-group> \
  --circuit-name <circuit-name> \
  --name AzurePrivatePeering -o jsonc

# Microsoft requires two /126 IPv6 peer subnets for IPv6 private peering.
# The exact update surface can vary with Azure CLI/API version, so inspect it
# rather than copying an obsolete switch from an older article.
az network express-route peering update --help

# After the IPv6 family is configured, verify both IPv4 and IPv6 peering state.
az network express-route peering show \
  -g <resource-group> --circuit-name <circuit-name> \
  --name AzurePrivatePeering -o jsonc

The peering update is deliberately scoped to the IPv6 address family so the working IPv4 peer is not replaced. Before applying it, verify the two /126 blocks are dedicated to ExpressRoute and configure matching IPv6 addresses on the customer routers. After Azure accepts the change, enable the IPv6 address family on both CE BGP neighbors and advertise only the planned aggregates. The VNet commands are separate because ExpressRoute peering and workload addressing are independent resources; enabling one does not automatically create the other. In production, stage this with one test subnet and one test VM before publishing AAAA records broadly.

IPv6-specific routing and rollout details

Dual-stack migrations are safer when routing is enabled before application DNS changes. Bring up IPv6 peering, validate routes and direct IPv6 reachability, then publish AAAA records only for services that have proven listeners and security policy. This avoids a subtle failure mode where clients prefer IPv6 after a DNS change and expose a partially built path. Also verify return-path policy on stateful firewalls: an IPv6 flow entering through ExpressRoute must return through a route that preserves the expected session path, just as with IPv4.

Verification

Successful output should show both Azure provisioning state and usable IPv6 routes. A green peering object without any IPv6 route entries proves only that Resource Manager accepted configuration. The route table should contain the on-premises IPv6 aggregate on both redundant paths, and the VM NIC should select VirtualNetworkGateway for that prefix. From the CE side, verify Azure VNet IPv6 routes are learned over both sessions. Then run an application-level IPv6 test, such as `curl -6` or a TCP probe, so you know the route is not merely present but usable.

az network express-route peering route-table show   -g <resource-group> --circuit-name <circuit-name>   --path primary --peering-name AzurePrivatePeering

az network nic show-effective-route-table   -g <resource-group> -n <dual-stack-nic> -o table

Troubleshooting

When IPv4 succeeds and IPv6 fails, compare the two address families instead of restarting the whole circuit. First confirm the /126s are correctly assigned on both customer routers and that MP-BGP has an IPv6 address-family session. Then inspect the ExpressRoute route table and the workload NIC’s effective routes. A route absent from the ExpressRoute peer table means the problem is at BGP advertisement or filtering; a route present there but absent on the NIC moves the investigation toward the gateway/VNet side. If the route is installed but packets still fail, inspect NSGs, NVA policy, and the guest OS IPv6 address/default route.

A representative failure is: IPv4 BGP Established; IPv6 peer state idle; no IPv6 prefixes in the ExpressRoute route table. That points to peering-address or address-family configuration, not DNS. Another failure is: IPv6 BGP established and routes present, but the VM has no IPv6 address on the NIC/subnet. In that case the network underlay is ready but the workload is not dual stack. Correct the missing layer and retest with a literal IPv6 destination before adding DNS into the path.

Point-to-Site VPN with Microsoft Entra ID and OpenVPN: identity-aware remote access

Why it matters

Certificate and RADIUS authentication remain useful, but Microsoft Entra ID changes the P2S trust model by making user identity, Conditional Access, and MFA part of VPN admission. The feature is specifically tied to OpenVPN and the Azure VPN Client, so it is not a generic authentication option that can be mixed with any P2S tunnel type. That matters operationally: an administrator can have a perfectly healthy VPN gateway and correct routes yet users still fail because the tenant, audience, issuer, client application, or Conditional Access decision is wrong. Troubleshooting therefore has to separate tunnel transport from identity authorization.

Architecture

The client first reaches the public IP of the Azure VPN Gateway and establishes the OpenVPN transport. Authentication is delegated to Microsoft Entra ID using the configured tenant, issuer, and audience values. After successful identity evaluation, the Azure VPN Client receives/uses the P2S configuration and the gateway assigns an address from the client pool. The resulting route set determines which Azure or hybrid prefixes the client sends into the tunnel. Entra authentication governs who may enter; it does not automatically create application authorization inside the VNet.

Microsoft now supports a Microsoft-registered Azure VPN Client application/audience, reducing the need for manual app registration. Microsoft also publishes retirement dates for manually registered clients, so new deployments should follow the current Microsoft-registered client values rather than copying older tenant-specific app-registration instructions. Conditional Access can add MFA or device/user conditions, but policies should be tested carefully because a mis-scoped policy can deny every VPN sign-in even while the gateway health remains normal.

Prerequisites and implementation

Use a route-based VPN Gateway SKU that supports P2S OpenVPN; Basic SKU does not provide the required combination. Choose a client address pool that does not overlap the VNet, connected VNets, or on-premises networks. Obtain the Entra tenant ID and use the currently documented Tenant, Audience, and Issuer values for the Microsoft-registered client. Confirm DNS behavior for remote users as a separate design item: connecting a user to the VNet does not by itself guarantee that private DNS zones or on-premises DNS names resolve correctly. Plan route distribution and name resolution before client rollout.

Implementation
TENANT_ID=<entra-tenant-guid>
AUDIENCE=c632b3df-fb67-4d84-bdcf-b95ad541b5c8

az network vnet-gateway create \
  --name <vpn-gateway> \
  --resource-group <resource-group> \
  --location <region> \
  --vnet <vnet-name> \
  --gateway-type Vpn \
  --vpn-type RouteBased \
  --sku VpnGw2AZ \
  --public-ip-addresses <gateway-public-ip> \
  --address-prefixes <172.20.100.0/24> \
  --client-protocol OpenVPN \
  --vpn-auth-type AAD \
  --aad-tenant "https://login.microsoftonline.com/$TENANT_ID" \
  --aad-issuer "https://sts.windows.net/$TENANT_ID/" \
  --aad-audience "$AUDIENCE"

az network vnet-gateway vpn-client generate \
  -g <resource-group> -n <vpn-gateway> \
  --processor-architecture Amd64

The gateway update changes the P2S authentication boundary, so replace the placeholder tenant, audience, and issuer with the exact values Microsoft documents for the cloud in which the gateway runs. The address pool is leased to VPN clients and must remain unique across every network they may reach. After configuration, distribute the generated Azure VPN Client profile rather than asking users to hand-build OpenVPN settings. If Conditional Access is part of the design, introduce it after a baseline Entra-authenticated connection works; this keeps authentication-policy troubleshooting separate from tunnel configuration.

Identity, client lifecycle, and access boundaries

Conditional Access should be introduced with a pilot group and an emergency access path. The strongest design is not simply “MFA enabled”; it is a documented identity flow with a supported Azure VPN Client, known tenant/audience values, tested device/user conditions, predictable client routes, and private DNS behavior. Remote access also needs logging: Entra sign-in logs explain the identity decision while VPN Gateway connection data explains the tunnel. Correlating timestamps between those sources quickly distinguishes denied identity from broken network forwarding.

Verification

Validation should include three independent proofs: the gateway advertises OpenVPN and the intended client pool, Entra sign-in logs show a successful authentication for the Azure VPN Client, and the connected endpoint receives a lease and routes. Increasing ingress/egress counters confirm data movement but do not identify which application works. Test one Azure private IP and one private FQDN. If IP works and the name fails, preserve the tunnel and fix DNS. If sign-in fails before a client address is assigned, preserve the network configuration and investigate identity.

Troubleshooting

If users receive an Entra sign-in error before a tunnel is established, inspect identity first: tenant URL, issuer, audience, account tenant, Azure VPN Client version, and Conditional Access logs. Do not modify NSGs or VNet routes for an authentication failure that occurs before the client receives a VPN address. If authentication succeeds and the client shows Connected but Azure prefixes are unreachable, inspect the downloaded profile routes, gateway learned routes, VNet peering/gateway transit, and the client’s local route table.

A useful failure split is: sign-in succeeds, assigned VPN address exists, but `route print` or `netstat -rn` lacks the target Azure prefix. That is a route-distribution issue. If the route exists and TCP still fails, use Network Watcher from the Azure workload side and verify return reachability to the P2S pool. If private FQDNs fail while IP connectivity works, inspect DNS servers and suffixes in the VPN profile. Each symptom belongs to a different layer, and mixing those layers is what makes P2S incidents unnecessarily long.

Virtual WAN Route Maps: filter, summarize, and modify BGP attributes at connection boundaries

Why it matters

Virtual WAN normally provides managed route exchange, but large enterprises still need policy: suppress a branch prefix, summarize many routes, tag a route with a community, or prepend an AS path before advertising toward another connection. Route Maps bring that policy to the virtual hub connection boundary. They are not equivalent to a traditional router route-map in every detail, and assuming that they can influence Azure best-path selection in every direction leads to bad designs. The key is to understand where inbound and outbound processing occurs relative to the hub router.

Architecture

An inbound Route Map processes routes as they enter the virtual hub from a supported connection before those routes are installed in the hub routing table. An outbound Route Map processes routes after the hub has selected its path and before those routes are advertised to the target connection. Because best-path selection occurs before outbound processing, an outbound AS-path change cannot be used to make the Azure hub itself prefer a different path; it only changes what the receiving neighbor sees. Supported connection types include ExpressRoute, S2S VPN, VNet, and P2S/user connections, with documented limitations around NVA connections.

Rules can match route prefixes, BGP communities, and AS paths. Multiple match conditions in one rule are ANDed. Actions can drop routes or modify them, including aggregation and BGP attribute changes. Unmatched routes are allowed by default, so a Route Map is not an implicit-deny policy. Summarization has an important side effect: Microsoft documents that summarized routes lose existing AS-path and community attributes. That makes aggregation a topology decision, not merely a cosmetic route-count reduction.

Prerequisites and implementation

Inventory the current hub route table and connection advertisements before creating policy. Decide whether the desired behavior is inbound or outbound and write the expected before/after route set. Avoid Azure-reserved ASNs and remember Route Maps support 2-byte ASNs for the documented prepend function. Do not combine NAT and Route Map modification on the same prefix. Build narrow match conditions; a rule with no match conditions matches every route presented to it. Because unmatched routes default to allow, explicitly test both the prefixes intended to change and at least one prefix that should remain untouched.

Implementation
# Route Maps are configured through the current Virtual WAN management
# surface. Inspect the installed CLI extension/API first.
az extension add --name virtual-wan --upgrade
az network vhub show -g <resource-group> -n <virtual-hub> -o jsonc

# If the CLI version exposes route-map subcommands, create the route map
# and rule using those documented parameters. Otherwise use the portal or
# ARM/Bicep resource schema documented by Microsoft.
az network vhub route-map --help

# After creation, inspect the connection on which the Route Map is applied.
az network vhub connection show   -g <resource-group> --vhub-name <virtual-hub>   -n <connection-name> -o jsonc

Route Maps deserve change-control discipline because the policy can affect every prefix on a connection. Build the map with a deliberately narrow prefix or community match, attach it in one direction, and verify a control route that should remain unchanged. If the desired function is summarization, document the loss of original AS-path/community attributes as part of the design. If the desired function is prepend, choose a permitted 2-byte ASN that is not Azure-reserved. The current management surface evolves, so the lab explicitly asks the installed CLI for route-map support rather than inventing a command path that may not exist.

Route-map ordering, aggregation, and policy effects

Route Maps are especially useful during WAN migrations because they let Azure act as a controlled policy boundary between old and new routing domains. For example, a branch aggregate can be summarized before advertisement to another hub while a specific migration prefix remains unsummarized for steering. Treat every change as a routing-policy rollout: capture a route baseline, apply to one direction on one connection, validate expected and control prefixes, then expand. This is more reliable than using application symptoms as the first indication that a BGP policy changed too much.

Verification

The strongest verification is a before/after route view from the Route Map dashboard and the receiving BGP neighbor. A successful Azure resource state is secondary to the actual Prefix, AS Path, and Community values. For outbound policy, verify the remote branch sees the modification while remembering Azure selected its own best path earlier. For inbound policy, verify the modified route enters the hub table as intended. Always test a nonmatching route too, because the default behavior is allow and an accidental broad match is easier to detect with a control prefix.

az network vhub connection show   -g <resource-group> --vhub-name <virtual-hub>   -n <connection-name> -o jsonc

# Use the Route Map dashboard to inspect Prefix, AS Path, and Community
# in the applied direction; capture before/after values for the target prefix.
Representative successful output/state
Before inbound policy:
10.50.1.0/24   AS_PATH 65010   Community 65010:100

After inbound prepend policy:
10.50.1.0/24   AS_PATH 65033 65010   Community 65010:100

Troubleshooting

If a policy appears to have no effect, first confirm it is attached to the correct connection and direction. A common mistake is applying an outbound map while expecting Azure’s own best-path decision to change. Since the hub selects a path before outbound processing, the route may be modified for the neighbor but not for the hub’s choice. Another common mistake is a match that is too broad; a rule with no condition matches every route and can unexpectedly drop or modify the full advertisement set.

Use the Route Map dashboard to compare Prefix, AS Path, and Community before and after policy. If a summarized route appears but communities vanished, that is expected documented behavior rather than a dashboard defect. If a prefix is absent entirely, inspect whether a Drop action matched it and whether a prior terminating rule prevented later processing. The safest correction is to narrow conditions and retest on one connection before expanding the policy across the WAN.

VNet-to-VNet VPN Gateway: encrypted inter-VNet connectivity across regions and subscriptions

Why it matters

VNet peering is usually the simplest way to connect Azure VNets, but there are designs that deliberately require IPsec between VNets: administrative separation, cross-subscription boundaries, legacy topology consistency, or a need to combine inter-VNet tunnels with a broader VPN Gateway design. VNet-to-VNet connections use Azure VPN Gateways on both sides and create IPsec/IKE tunnels similar to S2S VPN. The important architectural consequence is that you are choosing gateway-mediated encrypted connectivity rather than the lower-latency direct backbone semantics of VNet peering.

Architecture

Each VNet has its own `GatewaySubnet`, public IP, and route-based VPN Gateway. Azure then creates a VNet-to-VNet connection object referencing both virtual network gateways. For VNets in different subscriptions, resource IDs and permissions matter because each side may be managed independently. Azure automatically understands the other VNet’s address spaces for the VNet-to-VNet connection type, whereas a design built with S2S/local network gateway objects requires manual maintenance of the remote address prefixes.

The data path is workload → VNet routing → local VPN Gateway → IPsec tunnel → remote VPN Gateway → remote VNet. That means gateway throughput, SKU, zone design, and tunnel state can limit traffic even when both VNets themselves are healthy. Non-overlapping address space remains mandatory. DNS is independent: an encrypted IP route between VNets does not automatically make private DNS names resolvable across both networks.

Prerequisites and implementation

Plan non-overlapping CIDRs and create a `GatewaySubnet` in each VNet; Microsoft recommends leaving enough space for gateway scale and future features. Use Standard static public IPs and supported route-based gateway SKUs. When the VNets are in different subscriptions, ensure the operator can read/reference both gateways and switch subscriptions carefully during creation. Decide whether BGP is needed; simple VNet-to-VNet connectivity can use the automatically understood VNet address spaces, while more complex routing requirements may justify S2S-style local network gateway objects instead.

Implementation
# Create a Standard static public IP and route-based VPN gateway for VNet A.
az network public-ip create \
  -g <rg-a> -n <gw-a-pip> --sku Standard \
  --allocation-method Static -l <region-a>

az network vnet-gateway create \
  -g <rg-a> -n <gw-a> -l <region-a> \
  --public-ip-addresses <gw-a-pip> \
  --vnet <vnet-a> --gateway-type Vpn \
  --vpn-type RouteBased --sku VpnGw2AZ \
  --vpn-gateway-generation Generation2

# Repeat the gateway build for VNet B, then create the VNet-to-VNet connection.
az network vpn-connection create \
  -n <a-to-b> -g <connection-rg> -l <region-a> \
  --vnet-gateway 1 <gw-a-name-or-resource-id> \
  --shared-key "<strong-shared-key>" \
  --vnet-gateway 2 <gw-b-name-or-resource-id>

az network vpn-connection show \
  -g <connection-rg> -n <a-to-b> -o jsonc

The connection command references both virtual network gateways, which is what distinguishes VNet-to-VNet from a conventional S2S connection built around local network gateway objects. Use resource IDs when gateways live in different resource groups or subscriptions to avoid ambiguity. Keep the shared key in a secure deployment mechanism rather than shell history for production. Gateway creation is long-running; do not treat `--no-wait` as completion. Poll the gateway provisioning state before creating the tunnel so a connection error is not merely a race against unfinished infrastructure.

Encryption, ownership, and route behavior

Choose VNet-to-VNet VPN intentionally. Peering generally gives simpler direct VNet connectivity with fewer gateway bottlenecks. VPN Gateway becomes attractive when encryption semantics, organizational boundaries, or reuse of a VPN-centric topology outweigh the additional cost and throughput considerations. During design review, state the reason you did not use peering; that single sentence prevents future engineers from “optimizing” the architecture by replacing an encrypted boundary with a different trust model.

Cross-subscription operation deserves explicit ownership. The connection resource belongs to a resource group even though it references gateways in two VNets, so RBAC and change responsibility must be clear before automation runs. If one team owns VNet A and another owns VNet B, both sides should agree on the shared key lifecycle, maintenance windows, and route expectations. BGP can be enabled where supported, but automatic VNet-to-VNet address-prefix updates and BGP-learned routes are different mechanisms; document which one is carrying reachability so future engineers do not diagnose the wrong control plane.

Verification

Connected status should be paired with byte counters and the source NIC’s effective route. The remote VNet prefix should resolve to VirtualNetworkGateway, not Internet or None. Generate a known TCP flow so the byte counters change in both directions. If the status is Connected but the route is absent, the problem is route propagation or resource association. If the route is present and only one counter direction moves, concentrate on the remote workload, NSG, and return path. This evidence prevents unnecessary recreation of expensive gateways.

az network vpn-connection show   -g <connection-rg> -n <a-to-b>   --query "{status:connectionStatus,ingress:ingressBytesTransferred,egress:egressBytesTransferred,provisioning:provisioningState}" -o json

az network nic show-effective-route-table   -g <rg-a> -n <vm-a-nic> -o table
Representative successful output/state
{
  "status": "Connected",
  "provisioning": "Succeeded",
  "ingress": 987654,
  "egress": 1234567
}

10.42.0.0/16   VirtualNetworkGateway   Active

Troubleshooting

A `Connecting` or `NotConnected` state immediately focuses the investigation on gateway provisioning, shared key, gateway references, IPsec negotiation, or reachability between gateway public IPs. If the connection is `Connected` but byte counters stay at zero while test traffic is generated, inspect the effective route on the source NIC. A missing remote prefix means the workload is not even forwarding toward the gateway. If counters increase one way only, inspect remote NSGs, return routing, and guest firewalls.

Overlapping VNet address spaces are a design failure, not a tunnel-tuning problem. Do not try to solve overlap by changing IKE parameters. Likewise, private DNS failures should be tested after literal-IP connectivity. If `ping`/TCP to a remote IP works but the application FQDN does not, configure appropriate private DNS zone links or resolver/forwarding rather than rebuilding the VPN connection.

Azure DNS alias records: resource-aware apex and public-IP mappings without stale addresses

Why it matters

A normal DNS A record contains an IP value that must be updated when the target changes. Azure DNS alias records instead point the record set at an Azure resource or another record set, allowing DNS resolution to follow the resource lifecycle. This is especially useful for apex records because DNS standards do not allow a traditional CNAME at the zone apex. An Azure DNS alias A/AAAA can point at supported Azure resources while keeping the zone apex usable for other record types.

Architecture

The Azure DNS zone remains authoritative for the name. The alias record set stores a resource reference rather than a copied IP address. During resolution, Azure DNS resolves the alias target and returns the appropriate address. If a Standard public IP resource changes or is deleted, the alias behavior follows the resource instead of leaving a forgotten static A record behind. Alias record sets support A, AAAA, and CNAME types with documented target types.

This is control-plane coupling between DNS and an Azure resource, not a traffic proxy. After DNS returns an address, the client connects directly to the target service in the normal way. Therefore an alias record cannot enforce WAF, health probing, or load balancing by itself. If the alias targets Traffic Manager or another service, those capabilities come from the target resource, not from Azure DNS.

Prerequisites and implementation

Register the Microsoft.Network resource provider and confirm the DNS zone and target resource are supported. If the zone and alias target are in different subscriptions, the resource provider must be registered in both. Decide whether the desired record type is A, AAAA, or CNAME and whether the target is a public IP, Traffic Manager profile, CDN/Front Door-related resource, or another supported record set. For production cutovers, lower TTL on the previous record in advance if clients may cache the old answer.

Implementation
# Inspect the zone.
az network dns zone show -g <dns-rg> -n <zone-name> -o jsonc

# Obtain the target Azure resource ID.
TARGET_ID=$(az network public-ip show   -g <network-rg> -n <public-ip-name> --query id -o tsv)

# Create an alias A record set that references the Azure resource.
az network dns record-set a create   -g <dns-rg> -z <zone-name> -n @   --target-resource "$TARGET_ID"

# Query the record set configuration.
az network dns record-set a show   -g <dns-rg> -z <zone-name> -n @ -o jsonc

The CLI creates the DNS record as an alias by setting `targetResource` to the Azure resource ID rather than writing an address into the record set. That resource reference is the important difference from `az network dns record-set a add-record`, which stores an IP value. Use `@` for the zone apex when appropriate. In deployment automation, obtain the target resource ID directly from Azure or Terraform state so DNS follows the resource dependency. Do not hard-code the public IP alongside the alias because doing both creates competing sources of truth.

Alias lifecycle and authoritative DNS behavior

Alias records are valuable in infrastructure-as-code because the dependency is explicit. The DNS object can reference the resource ID created by the same deployment instead of exporting an IP string and passing it through a separate pipeline. That reduces stale configuration during redeployment. For apex use, this also avoids workarounds involving redirects or unsupported CNAME semantics. Always test both the Azure record-set resource and an external DNS lookup; one proves control-plane intent and the other proves delegation and resolver-visible behavior.

Verification

Verification has two layers. The Azure record-set object must show the intended target resource ID, proving the control-plane relationship. A DNS query from outside Azure must then return the address currently associated with that resource, proving delegation and authoritative resolution. If you are changing from a literal A record to an alias, compare the answer before and after and honor TTL behavior. For apex records, also query SOA/NS data to ensure the zone delegation remains intact; aliasing the A record does not change authority.

az network dns record-set a show   -g <dns-rg> -z <zone-name> -n @   --query "{targetResource:targetResource.id,ttl:ttl}" -o json

dig <zone-name> A +short
dig <zone-name> SOA +short
Representative successful output/state
{
  "targetResource": "/subscriptions/.../providers/Microsoft.Network/publicIPAddresses/app-pip",
  "ttl": 3600
}

$ dig example.com A +short
203.0.113.25

Troubleshooting

If the Azure record set shows the correct `targetResource` but public resolvers return the old address, inspect delegation and caching before recreating the record. Query the authoritative Azure name server directly and compare it with a recursive resolver. If authoritative data is correct but recursive data is stale, TTL/cache expiry is the expected mechanism. If the record cannot be created, verify that the target type is supported and that Microsoft.Network is registered in both subscriptions when applicable.

A second failure is assuming alias records provide health-based failover. If the target public IP is reachable but the application behind it is down, Azure DNS does not automatically switch to another resource unless the alias points to a service such as Traffic Manager that implements health-aware routing. Choose the target resource based on the behavior required, then use the alias to remove the fragile copy of its address.

Standard Load Balancer Floating IP: direct server return semantics for NVAs and multi-VIP services

Why it matters

Floating IP changes how Azure Load Balancer delivers packets to a backend so the frontend VIP can be used by the backend application or appliance without the normal destination-address translation behavior expected in a simple load-balanced web farm. This is important for NVAs, SQL Always On listeners, and designs with multiple frontend IPs mapped to the same backend port. Engineers often enable Floating IP because a vendor guide says to do so, but the feature only makes sense when the backend application is prepared for the resulting packet semantics.

Architecture

With a conventional load-balancing rule, Azure maps the frontend IP/port to a backend IP/port. With Floating IP enabled, Azure uses a floating-IP/direct-server-return style mapping that allows multiple rules to reuse backend ports and lets the backend respond using the frontend identity required by certain clustered applications. The backend operating system or NVA must be configured according to the application/vendor model so that it accepts traffic addressed in the expected way. The load balancer itself remains a Layer-4 flow distributor and does not synchronize application state.

For stateful NVAs, Floating IP is often paired with HA Ports or multiple frontend configurations, but it does not automatically solve asymmetric routing. Forward and return paths still need a supported vendor architecture. For database listeners, the guest/cluster configuration must bind or recognize the listener address correctly. The Azure rule and the guest network stack are therefore two halves of the feature.

Prerequisites and implementation

Use a Standard Load Balancer and confirm the workload specifically supports Floating IP/DSR behavior. Create the frontend IP configuration, backend pool, and health probe first. Check whether the design requires multiple frontends, HA Ports, or a protocol-specific rule. On the backend, follow the vendor’s instructions for loopback/listener configuration and weak-host or equivalent behavior where applicable. Do not enable Floating IP on an ordinary application simply because it sounds like a high-availability option.

Implementation
# Create the rule with Floating IP / direct-server-return semantics.
az network lb rule create \
  -g <resource-group> --lb-name <load-balancer> \
  -n <rule-name> --protocol All \
  --frontend-ip-name <frontend-config> \
  --frontend-port 0 \
  --backend-pool-name <backend-pool> \
  --backend-port 0 \
  --probe-name <health-probe> \
  --idle-timeout-in-minutes 30 \
  --enable-floating-ip

az network lb rule show \
  -g <resource-group> --lb-name <load-balancer> \
  -n <rule-name> \
  --query "{floatingIP:enableFloatingIp,frontendPort:frontendPort,backendPort:backendPort,protocol:protocol}" -o json

`--floating-ip true` changes load-balancer packet handling for that rule; it does not modify the guest operating system to accept the frontend identity. Before enabling it, complete the backend-side listener or loopback configuration required by the application vendor. The frontend and backend ports may be identical, which is common for clustered listeners. If you are combining Floating IP with HA Ports, validate the exact vendor design because an all-ports rule and direct-server-return semantics can interact with session ownership in ways that a basic web-farm tutorial does not cover.

Floating IP backend behavior and service design

Multi-VIP designs are where Floating IP becomes easiest to understand. Several frontend VIPs can map the same service port to the same backend set without forcing each backend to listen on unique translated ports. That simplifies certain clustered appliances but increases the importance of clean documentation: every frontend, rule, probe, backend listener, and return-path policy should be named and tested independently. A successful health probe proves only the probe endpoint, not every listener represented by the load-balancing rules.

Floating IP also changes the backend host requirement. Because the backend must accept traffic addressed to the load-balancer frontend rather than only its NIC address, clustered appliances commonly bind the frontend address to a loopback or vendor-specific virtual interface. If the Azure rule has Floating IP enabled but the guest never owns or accepts that frontend address, health can look normal while service packets are rejected locally. Validate both Azure rule state and the appliance’s local listener/interface model; this is why Floating IP is often documented together with database listeners and active/passive NVA patterns.

Verification

Successful Azure output proves the rule has Floating IP enabled and the probe can keep backends eligible. It does not prove the backend accepted a packet addressed according to the DSR model. Use a packet capture or application listener command on one backend while sending a connection to the frontend VIP. Confirm the destination/port seen by the backend matches the vendor expectation and that the response leaves using the supported return path. This end-to-end check is essential when multiple VIPs reuse the same backend port.

az network lb rule show   -g <resource-group> --lb-name <load-balancer>   -n <rule-name> -o jsonc

az network lb probe show   -g <resource-group> --lb-name <load-balancer>   -n <health-probe> -o jsonc
Representative successful output/state
{
  "enableFloatingIp": true,
  "frontendPort": 1433,
  "backendPort": 1433,
  "protocol": "Tcp",
  "provisioningState": "Succeeded"
}

Backend health:
node01 Healthy
node02 Healthy

Troubleshooting

If the rule is Succeeded and backends are Healthy but the application never accepts connections, inspect the backend OS/application binding before changing the load balancer. A common symptom is SYN packets arriving but no listener bound to the floating/listener address. On a Windows cluster or NVA, use the vendor-recommended interface/listener commands and packet capture to confirm the backend recognizes the destination. If packets do not arrive at all, return to probe state, backend-pool membership, and the load-balancing rule.

For intermittent stateful sessions, capture both directions. If the forward flow enters one NVA while the return bypasses the expected frontend or reaches another unsynchronized appliance, that is a routing/session design problem. Floating IP affects packet delivery semantics but does not promise state synchronization. Correct the return UDR/BGP/vendor clustering pattern instead of toggling Floating IP repeatedly.
